# Technical writing

疲れたエンジニアが一度読んで分かるように書く。

- 仕事をしない語はすべて削る。
- 短い日常の語を使う。「活用する」ではなく「使う」。
- 規則に従うと文が悪くなるなら、別のやり方で文を直すか、そのままにする。
- 類義語や説明ではなく、実際のシンボル名、ファイル名、フラグ名、コマンド名を書く。
- 専門用語を作らない。開発者が口に出して言う語を使う。名前の付いたパターンは、最初に出たときに意味を言う。

## 文のリズムに変化を付ける

- 文の長さを混ぜる。二つの考えを運ぶ文は分ける。一つの考えを運ぶ長い文は残す。
- 解説では意見を持つ。リファレンスは淡々と書く。
- 具体的に書く。「スキーマの変更は問題を起こしうる」ではなく、「列の名前を変えるとビルドが失敗する」と書く。

## 最初にモードを決める（Diátaxis）

一つの文書に一つのモード。モードを混ぜない。代わりに分けて、リンクする。

- **チュートリアル：やりながら学ぶ。** 学ぶ人が何を作るのかを言う。どの手順も目に見える結果を生み、何が見えるはずかを言う。解説は一節だけにし、リンクを張る。
- **ハウツー：目的に向かう手順。** 読み手の問題を解く。読み手の力量を前提にする。操作だけを書く。分岐を許す。ガイドの名前は作業の名前にする。
- **リファレンス：調べるための事実。** 記述だけをする。淡々と、漏れなく、言い切って書く。記述する対象の構造をそのまま映す。
- **解説：理解と理由。** 範囲を区切った一つの話題。設計判断、経緯、制約、代わりの案といった背景を書く。意見はここでだけ書いてよく、ほかでは書かない。

## 読み手に向けて文を書く（Google developer style）

- 読み手に直接語りかける形で、現在形で書く。
- 誰が何をするかを言う。受け身でよいのは、主体が不明か、本筋に関係ない場合だけ。
- 指示は命令の形で書く。条件を指示の前に置き、よくある場合を先に書く。
- 流行語、比喩的な言い方、「お願いします」のような丁寧の添え物を書かない。手順では「単に」「簡単に」「すぐに」を決して使わない。
- 予告をしない。続く文を同じ言い回しで始めない。
- リンクは、リンク先が何かを言う語に張る。
- 見出しは要点を運ぶ。本文と同じ表記で書き、英語の見出しは先頭の語だけを大文字にする。h1はページに一つだけ、見出しの階層を飛ばさない。
- 順序のあるものは番号付きリスト、それ以外は箇条書きにする。リストは完結した文で導入する。項目の形をそろえる。
- コードはコード用の書体にする。UIの要素は太字にする。並列の区切り方をそろえ、最後の項目まで同じ記号で区切る。「など」で終わらせない。

## 文が一つずつ頭に入るようにする（STEの規則）

- 一文に一つの指示。それ以外の文でも一文に一つの考え。
- 指示はおよそ40字、それ以外の文はおよそ50字を超えたら分ける。
- 警告や条件は、それが守る手順の前に置く。
- 助詞を省かない。
- 一つの語には一つの意味を持たせ、一つの操作には一つの語を選ぶ。
- 手順は直接の命令として書く。語りの形や受け身では決して書かない。
- 「〜の実施」「〜の確認を行う」のような、動作を名詞にした言い方はできるだけ避ける。

## どの文も二通りに読めないようにする（Global English）

- 「だけ」や否定の語は、それが限定・否定する語のすぐそばに置き、どこまでかかるかを明確にする。
- 長い名詞の連なりを分ける。
- 「それ」「これ」「この」は、どれも明らかな一つのものを指すようにする。「これ」「それ」で前の節や文全体を指さない。
- 述語や、構造を示す小さな語（「という」「の」など）を省かない。
- 誤読を防げるなら、並列の各項目に助詞を繰り返して付ける。「と」や「または」が何と何をつなぐかを明確にする。
- 句点で区切り、セミコロンやダッシュを使わない。スラッシュ（「A/B」）を使わず、「（複数可）」のような括弧書きで済ませない。括弧の中は、文法的にまとまった単位にする。
- 一つのものは、どこでも一つの名前で呼ぶ。
- 慣用句、くだけた言い方、ラテン語の略語（e.g.、i.e.）、比喩を使わない。

## 文体とリポジトリ固有の決まり

- このスキルが触れるすべての文書に**unslop**スキルを適用する。AIがよく使う語、埋め草、ぼかし、書式の癖といった、AIらしい型の一覧はそのスキルが受け持つ。
- PRの説明とコミットメッセージも文章である。Diátaxis以外のすべての層がそれらに当てはまる。PRの本文は、レビューする人が1分以内に読める説明にする。swarmのログ、SHAの一覧、数値の表を貼り付けない。リンクを張る。
- 製品のUIの文言は文書ではない。それには製品の文言の指針を使う。
- コードの断片はタブで字下げする。実在するパスを書く。件数やツリーについての記述は、それを取り込むコミットの時点で正しいものにし、それを作り直すコマンドを添える。
