# No comments

Comment Sickoを起動する。受け入れた指摘に対応する。

Comment Sickoの新鮮な視点に従う。

## 範囲

呼び出し元が渡したファイルや差分を使う。なければ、作業ツリーを含む、基準ブランチ（既定は`main`）に対する現在の差分を使う。

## 手順

1. `Agent`ツールを`subagent_type: "koto:comment-sicko"`で起動する。範囲を渡す。各サブエージェントの推論の水準は、**koto-mode**スキルの「サブエージェント」の節に従って、仕事に合わせて選ぶ。その担当の決まりを言い直さない。
2. その報告と差分を調べる。アプリケーションのコードの編集、範囲の外への逸脱、例外で守られるコメントの削除、誤って述べた`MUST KILL`の理由、残した意図的なコードを有罪扱いする指摘は却下する。自分たちのコードの意外な動きに対する作り直しの指摘は、対応すべきものとして残す。それらのコメントは元に戻さない。コメントを残せるのは、自分たちが変えられないものについてであると証明できる場合だけである。範囲内で見逃されたlintやTypeScriptの抑制を確かめる。正しさや安全性に関わる抑制は、対応すべき`MUST KILL`のままにする。削除を元に戻すのは、正確な例外と範囲内の証明がある場合だけとする。根拠の薄い`IMPORTANT`や`do not remove`の削除・保持を受け入れる前に、そのシンボルをたどるか、それに対して`/koto:why`を実行する。削除が曖昧なら、元に戻さない。保持が反証されたか、まだ曖昧なら、削除する。却下した報告は1回だけ、失敗を名指しして差し戻し、再実行させる。2回目も却下なら、未解決として報告し、`/koto:no-comments`を失敗とする。
3. 削除したコメントのうち、受け入れた妥協（「既存に合わせてこうしている。本当はこうしたい」）や、外から来た制約（契約、法律、ほかのチームとの取り決め）を述べていたものは、Skillツールで`knowledge`を呼び、その「コメントから残す」の手順でKnowledgeの制約にする。元の文は差分の削除行から読む。コードの動きの説明や、この変更をした理由は残さない。理由はコミットかPRに書く。
4. 受け入れた些細な指摘は、使われていない経路を消す、引数を落とす、本物のAPIを使う、のように直接直す。形を決める必要がある修正があれば、受け入れた指摘全体とその周りのコードに対して`/koto:architect`を1回実行する。スケッチで止める。architectは形を決める。実装は手順5で行う。
5. 範囲内で、根本原因に対する最小の修正を実装する。名指しされた回避策はすべて取り除く。根本原因が範囲の外にあるなら、範囲内の最小の修正を入れ、残りは未解決として報告する。**principle-fix-root-causes**と**principle-redesign-from-first-principles**スキルは、意図を導くだけである。どちらも、範囲の柵を広げることや、柵の外の事例を直すことを認めない。症状を抑えるガードを後付けしない。
6. 制約のコメントは、`do not remove`、`do not change wording`、`talk to X before changing`のように書かれる。自分たちが変えられないものについての保持はそのままにする。範囲内でもっとも安い、型・実行時の確認・テスト・CIのlintのいずれかでの組み込みを提案する。対話中なら承認を待つ。無人の実行や評価では、呼び出し元の事前承認が必要である。承認されたら、組み込んでから削除する。そうでなければ削除し、その制約を未解決として報告し、範囲外の作業をスケッチする。
7. 削除した数、元に戻したコメント、Knowledgeに残した1件、再実行、architectのスケッチ、修正、組み込みの提案、組み込んだもの、強制されていない制約、その他の未解決の作業を報告する。
