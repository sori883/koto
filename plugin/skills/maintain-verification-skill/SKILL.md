# 検証スキルを保守する

機能の地図は、アプリが変わった瞬間から古くなる。このスキルは、`/koto:create-verification-skill`で生成したスキル（または機能の地図を持つプロジェクト専用の検証スキル）を保守する流れである。厳密さの単位は、すべての文ではなく機能である。すべての機能ファイルをソースから確かめ、すべての機能をライブで動かす。ただし箇条書きを一つ残らず端末で実行する必要はない。

## 結果

一つを選び、どれかを明言する。

- **clean** — すべての機能をソースとライブで確かめ、出す価値のある変更はない。ブランチもPRも作らない。
- **changed** — 証明した文書・操作の仕組み・地図の修正を、1つのPRで出す。
- **blocked** — 確認を終えられなかった、または証明した修正を安全に出せなかった。何が妨げたかを正確に言う。

## 編集の範囲

編集するのは、検証スキル自身のディレクトリ（そのSKILL.md、features/、それが持つ操作用のスクリプト）だけにする。実行中に製品のコードを編集しない。地図に書かれた振る舞いをアプリがもうしないなら、それは文書のずれ（地図を直す）か、製品の退行（報告し、文書で取り繕わない）のどちらかである。

## 手順

0. **対象を見つける。** 保守する検証スキルを見つける。起動・操作の節と機能の地図を本文に持つ、プロジェクト専用のスキルである（ふつうは`.claude/skills/verify-*/`）。候補が複数 → どれかを聞く。ない → 対象をでっち上げず、止まって`/koto:create-verification-skill`を案内する。

1. **索引の整理。** 機能の地図のREADMEを読み、同じ場所のファイルをglobで集める。欠けた項目、余分な項目、重複、リンク切れを直す。軽く済ませ、一覧を生成しない。

2. **ソースの確認。** 機能ファイルごとに読み取り専用のサブエージェント（`Explore`）を1つ、同時に起動する。それぞれが「利用者向けのこの機能はどう動くか」をソースから説明し、文書のずれと思われる箇所を引用付きで挙げ、ライブで確かめる簡潔な手順を1つ返す。サブエージェントはアプリを操作せず、ファイルも編集しない。返す形：機能の要約／ソースの入口／ずれの候補またはなし／手順1つ。

3. **突き合わせる。** すべての機能ファイルに、返された要約がある状態にする。重なる手順をまとめ、アプリの状態をできるだけ少なくする。引用されたずれは抜き取りで確かめ、問題なしとされた主張を証明し直さない。最近の変更を見渡し、地図から漏れている利用者向けの接点を探す。漏れていると判断するには、具体的なソースのパスを必須とする。

4. **ライブで確かめる。** ソースに問題がなさそうでも必須である。操作はすべてまとめ役が受け持つ。検証スキル自身の起動の形に従う。サーバーやUIなら、長く動かす1つのインスタンスを順番に操作する。短命なCLIなら、操作のたびに新しい分離したセッションを使う（決めるのはこのスキルではなく、検証スキルの起動の節である）。すべての機能を少なくとも一度動かし、どんな失敗が起きても、点検の間ずっと次の3つの不変条件を守る。(1) 最後に予想外のことが起きてから健全性を確かめていないインスタンスは操作しない。最初の操作の前に診断し、セッションが単位の場合は新しいセッションごとに診断し、操作が失敗したらもう一度診断する。診断では見えない失敗（プロセスは正常なのにUIが固まった状態など）では、望みに頼らず、分かっている状態に戻すか起動し直す。(2) それまでに残した証拠は、どの後片付けのあとも残っている。名指しした場所で確かめ、思い込まない。(3) 操作が起動したものは、その操作の役目が終わったあとまで残さない。失敗した試行の残りは、セッションが固まっていても、終了していても、共有されていても片付ける（共有のインスタンスなら、インスタンスではなく残りを片付ける）。スキルのずれが原因の診断の失敗はずれである。編集の範囲内で直し、一度だけ再試行してから（その修正で無効になったものだけを再起動し、それ以上はしない）、点検を`blocked`とする。たどり着けない機能を`verified-unreachable`とするのは、具体的な前提条件（認証、権利、OS、外部の状態）と試した経路があるときだけである。地図がその前提条件を書いていないなら、それはずれである。仕分けで直した操作の仕組みは、出す前にライブで操作し直す。最後の停止は、その実行の最後の操作（その証明し直しを含む）のあとに行い、実行より長く残るものをなくす（証拠はスキルの定めどおり残す）。

5. **仕分ける。** 利用者の視点の説明が誤っている、または欠けている → 文書のずれなので直す。動く振る舞いを操作の仕組みが動かせない → 仕組みの穴なので直す。仕組みの修正は、生成のときと同じ補助スクリプトの決まり（スクリプトは実行可能にし、呼び出し方をスキル本文に書く）に従う。アプリの振る舞いが本当に壊れている → 製品の穴である。利用者のために記録し、このPRには入れない。

6. **出すか止まるか。** changedなら、証明した修正を1つのPRで出す。その前に、変更したファイルをすべて読み直す。cleanまたはblockedなら、PRを作らず、結果と確認できた範囲を正直に報告する。

簡潔な実行メモ（確かめた機能、たどり着けない前提条件、確認したずれ、結果）を一時的な場所に残す。コミットはしない。
