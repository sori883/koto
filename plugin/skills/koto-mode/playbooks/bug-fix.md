### Bug fix

**この作業は自分が持つ。計画し、レビューし、検証する。** 調査と修正はサブエージェントに任せ、主導は自分が保つ。各サブエージェントの推論の強さは、「サブエージェント」の節に従って作業ごとに選ぶ。

科学的に進める。出す行はすべて、実行時の証拠にさかのぼれなければならない。「役に立つかもしれない」念のための対策は仮説であって修正ではない。出さない。証拠が仮説を否定したら、その仮説から入れたものを元に戻す。証拠が正当化する最小の変更だけを出し、それ以上は出さない。

1. **ticket**スキルで、この不具合のチケットを作る。同じ不具合のチケットがあればそれを使う。目的に症状と影響を、終了条件に「元の再現が同じ画面や経路で通る」ことと修正のPRを書き、`running`にする。
2. 操作用のスキル（**control-ui**、**control-cli**）を使い、対応する画面や経路で自分で再現する（「必ず守ること」の節）。デバッグや計測の手順が利用者に再現を頼むよう求めていても、自分で再現する。利用者に頼むのは、操作手段が対象に届かない具体的な理由を述べられる場合だけにし、それも操作手段で行けるところまで進めたあとにする。直接再現できないなら、引き金を合成する、条件を絞る、または発生するまで計測を入れる。
3. 原因を二分探索する。候補となる仮説を立て、一つが残るまで除外していく。仮説の種は、影響するサブシステムをたどった結果と、リグレッションの履歴を調べる**why**スキルから得る。毎回、残る問題の範囲を最も大きく削れる分け方を選び、実行時の証拠を取り、除外する。プログラムの状態が分からないときは、計測やログを入れ、コードを動かしながら読む。推測しない。長い調査やしぶとい調査は、Claude Codeの`/loop`コマンドで進める。手順4の`architect`や`interrogate`での並行検討の前に、残った*仕組み*を実行時の証拠で確かめる。
4. 修正を計画する。関数の境界をまたぐなら、先に`architect`を実行する。実装は、`model: "opus"`、`effort: "xhigh"`のサブエージェントに具体的な範囲を付けて任せる。
5. 同じ画面や経路で検証する。元の再現が通るようになっていること。「判断できない」や、違う画面や経路での確認は合格ではない。そう明示する。単体テストが示すのは分岐の振る舞いであって、不具合がないことではない。
6. 失敗する再現が修正より前にgitの履歴に入るよう、コミットを並べる。不具合に安価な局所テストの経路があるときは、失敗するテストを先に書く進め方について**tdd**スキルを参照する。テストが高くつく、統合に大きく依存する、または不明確な場合は省く。
   これは**sequence-verifiable-units**の原則スキルの典型である。失敗するテストを先に置き、その上に修正を載せる。
7. **Opening a PR**を実行する。

**返答：** 何が壊れていたか、根本原因、修正、検証の方法。失敗してから通るまでの再現の出力を、そのまま貼り付ける。
