### Shipping

**自分が持つのは着地するものである。各PRを独立に検証し、根から続く検証済みの範囲だけを着地させ、そのあとはスタックに手を出さない。**

1. **forgeを決め、着地の前に各PRを独立に検証する。** 既定はGitHub CLI（`gh`）とする。`command -v origin`が成功し、Originがリポジトリを解決できるなら、すべてのPR操作に`origin pr`を使う。そうでなければ`gh`のままにし、そのフォールバックを記録する。Graphite（`gt`）を必須にしない。検証者はPRごとに一人とし、それぞれClaude Codeのクラウドのセッションとする。検証者は、対応する操作用のスキル（**control-ui**、**control-cli**）を使って利用者と同じように変更を動かし、親とheadを比べ、そのPRに`PASS`、`PASS+NOTES`、`FAIL`のいずれかを投稿する。判定として数えるのは、コードを書いていないエージェントの判定だけである。作者は自分が作ろうとしたものを確かめてしまうからである。グリーンのCIと承認するボットのレビューは判定ではない。どちらも利用者と同じように変更を動かしてはいないからである。
2. **着地させるのは、一番下から連続する検証済みの範囲だけ。** マージされていない最も下のPRから上へたどり、`PASS`でも`PASS+NOTES`でもない最初のPRで止まる。それより下のPRが範囲であり、その一番上が上限になる。検証されていないPRより上にある検証済みのPRは待つ。下のコードなしには着地できないからである。ブランチがそのコードを含まず必要ともしないPRは、trunkへ移して単独で着地させてよい。ただし、先に新しい判定が必要である。古い判定はそのコードが下にある状態で実行されたものであり、trunkにはそのコードがないからである。
3. **判定がまだコードを表しているかを確かめ直す。** 判定はパッチを対象とする。連鎖したrebaseは、どのチェックも失敗させずに、その上のすべてのPRを新しいSHAへ動かす。古い判定を信じる前に、判定時のSHAと現在のheadで`git patch-id`を比べる。パッチの違いがテスト・文書・lint設定だけのときは、レーンが実行したものが両方のSHAでノイズを除いて同じようにビルドされるなら、そのレーンの結果は有効のままとする。ノイズとは、判定時のSHAを2回ビルドしたときにも現れる違い、または埋め込まれたコミットSHAのことである。読み手が判断を確かめられるよう、ノイズの種類ごとにそのファイルを報告する。変更そのものには、改めてチェックとレビューを行う。古い判定はその変更を見ていないからである。ビルド出力のないレーン（開発サーバーなど）はこれを示せないので、もう一度実行し、ほかにずれたものも検証し直す。
4. **下から上へ、一度に一つずつ着地させる。** 常に範囲の中でマージされていない最も下のPRを、`origin pr merge <pr>`または`gh pr merge <pr> --squash`でマージする。Originでは、オプションなしのコマンドは指定したPRより下のすべてのPRもマージする。GitHubでは、ベースがまだ親のブランチであるPRは、trunkではなくそのブランチにマージされる。結果はPRを読み直して確かめる（`origin pr view <pr>`または`gh pr view <pr> --json state,mergedAt,baseRefName`）。マージキューがPRをキューに入れただけでも、マージコマンドは成功を報告することがあり、自動マージの要求はマージではないからである。着地したPRは、マージ済みで、ベースが親のブランチではなくtrunkになっている。`--auto`（Originのmerge-when-readyまたはGitHubの自動マージ）を仕掛けるのは、判定が現在のheadを対象としているPRだけとする。準備ができたheadなら何でも着地させてしまうからである。マージが着地したら、マージされたブランチをベースにしていたPRのベースをtrunkに変え（`origin pr edit <pr> --base <trunk>`または`gh pr edit <pr> --base <trunk>`）、そのパッチをマージ結果の上へ移し、`--force-with-lease`でpushする。判定はコミットではなくパッチを対象とするので、判定が残るかどうかは手順3のpatch-idの規則で決まる。チェックが通り、判定が残ったらマージする。 マージしたPRのチケット（**ticket**スキル）があれば、終了条件を満たしたかを確かめ、結果にマージしたPRと検証を書いて`done`にする。
5. **着地させている間はスタックに手を出さない。** ブランチやベースへの変更は、手順4での次のPRの移動だけとする。マージは、判定の有無にかかわらず、その時点でブランチとベースにあるものを着地させるからである。GitHubでは、`/loop`の下で`scripts/watch-pr/watch-pr --queued-stack`を使い、上限で`COMPLETE`と報告されるまで範囲を見守る。範囲のPR番号を下から上の順に`--stack-prs`に渡し、watcherを再起動するたびに同じ一覧を渡す。Originでは、`origin pr checks <pr> --watch`が戻るたびに`origin pr view <pr> --checks`で現在のPRを読み直し、上限がマージ済みになるまで続ける。親がマージされたときにベースがtrunkへ移るのは想定どおりであり、直すべき損傷ではない。マージが止まったら、何かを変える前に理由を突き止める。
6. **上限で止まる。** 範囲を広げるには新しい判定が必要なので、それは手順1からの新しい一巡になる。

**返答：** 検証済みの範囲とその上限、各PRの判定とそれを出した者、着地したものとその確かめ方、次の切れ目に必要なこと。
