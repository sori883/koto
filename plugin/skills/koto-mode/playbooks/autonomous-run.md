### Autonomous run

**終了条件は自分が持つ。完了を定義し、止まらずにそこまで進める。**

1. 最初の反復の前に、終了条件を確かめられる判定条件として述べる（テストが通る、再現手順で不具合が出なくなる、N件のPRがすべてマージされる、ピクセル差分がゼロになる）。続けて、**必ず**チケットを作るか、同じ仕事の既存のチケットを使う。規模や、途中で止めるかどうかに関わらず省かない。Skillツールで`ticket`を呼び、その「始める」の手順に従う。目的と、この判定条件を終了条件に書く。
2. Claude Codeの`/loop`コマンド（組み込みのコマンドで、kotoのスキルではない）を使って起こし方を選ぶ。見張るイベント（CI、マージ、refの前進）があるなら、イベントで自分を起こす監視用のサブエージェントを置き、予備として長い間隔の定時確認を付ける。イベントがないなら、結果を確認し直す価値が出る時間に合わせた一定間隔の定時確認にする。各サブエージェントの推論の深さは、「サブエージェント」の節に従って仕事に合わせて選ぶ。
3. 各反復では、証拠が裏付ける最小の変更を行い、判定条件に照らして検証し、前進したらコミットし、役に立たなかった変更は捨てる。「効くかもしれない」念のための対策は、残さずに戻す。
   作業の順序は**sequence-verifiable-units**原則のスキルで決め、確認を最後にまとめず、各単位を検証してから次へ進む。
4. 目的を支える途中の発見は自分の仕事である。壊れたスキル、関連する不具合、不安定な検証手段、レビューのノイズ、ツールの故障、放置された後続作業、直せるずれは、koto-modeで自分で対処する。本筋から外れた修正は別のPRにする。元に戻せる作業を人間に預けたり、`AskUserQuestion`を使ったりしない。伝えるのは、元に戻せない操作、どの実験でも決着しない製品上または好みの判断、本当の行き詰まりだけにする。判定条件を主な推進力として保ち、横道の修正のたびにそこへ戻る。
5. 反復ごとに**show-me-your-work**スキルで、チケットのフォルダの`decisions.tsv`に記録を残し、何を変えたかと判定条件が動いたかを1行ずつ書く。区切りごとにチケットのcheckpointも書き換え、次の反復で何をするかを残す。
6. 判定条件を満たしたら、チケットの結果を書いて`done`にし、止まる。頭打ちは停止の理由にならない。続けて、やり方を切り替えて突破する。空回りせずに本当の行き詰まりを伝え、勝利を宣言するために判定条件を緩めることは決してしない。

**返答：** 終了条件、実行した反復の数、取り込んだもの、捨てたもの、判定条件の最終状態。
