# Setup

プロジェクトのルートに、kotoの保存領域`.space/`を作る。

## 作るもの

```text
{project}/.space/
  tickets/
    .gitkeep           空のtickets/をGitに残すための空ファイル
  kb/
    .gitkeep           空のkb/をGitに残すための空ファイル
```

- `tickets/`には、チケットごとのフォルダ（`tickets/<ticket-id>/`）を置く。中身は**ticket**スキルに従う。
- `kb/`には、Knowledge（次の作業で知らないと困る判断・制約・参照）を置く。中身は**knowledge**スキルに従う。
- `tickets/`も`kb/`もコミットする。どちらも利用者やチームが共有する情報である。

## 手順

1. プロジェクトのルートを決める。
   - 利用者がフォルダを指定したら、それを使う。
   - 指定がなく、現在のフォルダがGitリポジトリの中なら、`git rev-parse --show-toplevel`の結果を使う。
   - ただし、`git rev-parse --git-dir`と`git rev-parse --git-common-dir`が異なるとき、現在のフォルダは追加の作業ツリー（worktree）の中にある。作業ツリーを消すと`.space/`も消えるので、作業ツリーと元のリポジトリのどちらに作るかを利用者に確かめる。
   - Gitリポジトリでなければ、どのフォルダに作るかを利用者に確かめる。
2. このスキルの`scripts/setup.ts`をBunで実行する（`bun <このスキルのフォルダ>/scripts/setup.ts <プロジェクトのルートの絶対パス>`）。
   - 出力は1行ごとに「結果（`created`または`kept`）、タブ、パス」である。
   - 既存のディレクトリやファイルはそのまま残す（`kept`）。
   - `.space/`、`.space/tickets/`、`.space/kb/`のどれかが、ディレクトリではなくシンボリックリンクや別の種類のものとして既にあれば、何も変えずに失敗する。消したり置き換えたりして回避せず、利用者に状況を伝える。
3. 結果を確かめる。`.space/tickets/`と`.space/kb/`があることを確かめる。
4. 利用者に、プロジェクトのルート、作ったパス、コミットするかどうかを伝える。コミットは利用者に頼まれたときだけ行う。

## 返答

使ったプロジェクトのルート、スクリプトの出力（作ったもの・残したもの）、確かめた結果、コミットしていないこと。
