# 形式検証スキルを作る

テストは、誰かが書こうと思いついたケースを確かめる。形式検証は、決めた範囲のすべてのケースを確かめる。モデルの中のすべての手順の順序、上限までのすべての入力、またはすべての入力である。このスキルは、リポジトリの中でそれがもっとも効く部分を見つけ、その性質を一つ検証し、次のエージェントが変更をその性質に照らして確かめられるプロジェクト専用スキルを残す。そのスキルは、変更の途中で初めて読み、あなたの作業を一度も見ていないエージェントに向けて書く。利用者は、検証言語を学ばなくても、結果を信頼して行動できなければならない。

## 対象はコードから選ぶ

答えはコードベースから出す。利用者には、観察できないことだけを聞く。利用者が領域や不具合を挙げたら、そこから始める。

よい対象とは、コードが守る約束のうち、破れると利用者が損害を受け、それを破るケースにテストがめったに届かないものである。検証しやすいものではなく、リポジトリでもっとも強い対象を選ぶ。

## 問いにツールを選ばせる

問いにもっとも安く答えるツールを選ぶ。モデル検査器、証明支援系、SMTを使う検証器、またはほかのツールである。出来事が悪い順序で起こりうるかという問いには、たいてい設計の小さなモデルに対するモデル検査器が合う。その用途の既定は、言語を問わずTLA+とする。メモリ安全性、オーバーフロー、データ構造の不変条件のように、コード自体がすべての入力で正しく動くかという問いには、たいていコードの上で動く検証器が合う。この言語で動く検証器がなければ、そう言い、関数を手で写したモデルではなく、実際のコードを生成した入力でテストする。上限では足りず、どの大きさでも成り立たなければならない性質には、証明が必要になることがある。リポジトリの開発者がインストールして実行できるツールを優先し、そのツールを選んだ理由を利用者に伝える。

## よい検証の条件

- **コードに忠実である。** モデルや証明のどの部分も、レビューする人が開けるコードを指す。検証が分けられない一つの手順として扱うものは、コードでも分けられない一つの手順である。名前はこのリポジトリのものを使う。
- **失敗できる。** 失敗するのを一度も見たことのない確認は、何も証明しない。各性質について、それが守るコードを壊した版（確認を消す、手順の順序を入れ替えるなど）で失敗することを示す。
- **見つけたものは見つけたものとして扱う。** 現在のコードが性質を破るなら、コードの言葉で反例を添えて報告する。通るまで性質やモデルを弱めない。利用者に頼まれない限り、製品のコードを変えない。
- **範囲に正直である。** 何を、どの上限と前提のもとで検証したか、何を外したかを言う。通ったとしても、それはモデルまたは上限の範囲についてであって、システム全体についてではない。
- **ツールを知らなくても読める。** 性質と損害を、それぞれ一文の平易な言葉で書く。反例は、コードの言葉による短い手順の並びとして伝える。
- **安く再実行できる。** コマンドは一つ、ツールの版は再現でき、次のエージェントが関係する変更のたびに使うほど短い時間で終わる。
- **コードと歩調を合わせる。** 各確認がどのファイルと関数を対象とするかと、検証がそれらを表していると最後に確かめたコミットを記録する。そのコミットの後で対象のコードが変われば、次のエージェントは検証を見直す必要があると分かる。

## 検証スキルを作る

対象の領域を名指しし、いつ使うかを書いたfrontmatterを付けて、プロジェクト専用スキルを書く。frontmatterがないと、スキルは登録されない。次のエージェントがスキルだけを読んで、変更が検証済みのコードに触れるかを判断し、確認を実行し、本当の不具合とモデルの誤りを見分け、意図した変更のときは検証を更新できなければならない。対象の記録と同期コミットをスキルに書き、新しいコミットで検証がコードを表していると確かめた後でだけ同期コミットを進めるよう、次のエージェントに伝える。このリポジトリの実際のコマンド、パス、名詞を使い、プレースホルダーを残さない。

確認がTLA+のモデルなら、すべての結果をkotoの[`/koto:statechart`](../statechart/SKILL.md)スキルで読むよう次のエージェントに伝える。このスキルは、検査器が見つけた不変条件の違反を、それぞれ最短の経路として平易な言葉で示す。確認が通ったときは、`/koto:statechart`がシステムの状態の移り変わりを図にする。`/koto:statechart`は名前で参照する。そのコマンド、オプション、ファイルパスは版やマシンによって変わるので、作るスキルやそのスクリプトには何も写さない。

## 渡す前に証明する

作ったスキルに、次のエージェントと同じように一度従う。実際のコードで性質を破る試しの変更に対して行う。スキルはその破れを捕まえなければならない。その後、試しの変更を捨て、確認が元の状態に戻ったことを確かめる。元の状態とは、通るか、報告する予定の発見だけで失敗するかである。一度も実行していない検証スキルは下書きである。スキルが破れを見逃すか、手順が動かなければ、試しの変更ではなく、スキルか検証を直す。

## 引き渡す

利用者に、何を検証したか、どのツールをなぜ使ったか、上限、確認が見つけたことを平易な言葉で、実行方法、対象外のことを伝える。二つ目の対象は、近いものを見つけた場合だけ提案する。変更が検証を確かめ直さなかった後で、検証をコードに合わせ直すには`/koto:maintain-formal-verification-skill`を使うよう案内する。
