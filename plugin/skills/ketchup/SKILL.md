# Ketchup

利用者が`/koto:ketchup`の前に書いた最後のメッセージ以降に、この会話で変わったことを伝え、それぞれがどうなっているかだけでなく、変更そのものを理解できるようにする。そのうえで、利用者を待っている判断をすべて並べ、返答だけで判断できるようにする。通知やサブエージェントの結果は、利用者のメッセージではない。利用者は自分の最後のメッセージを覚えていて、それ以降のことは何も覚えていないと考える。

[`/koto:bro`](../bro/SKILL.md)の話し方を使い、その役割は使わない。平易な言葉、短い文、専門用語なしで、ある人が別の人に近況を伝えるように話す。どうやったかではなく、利用者にとって何が変わったかを言う。「CIがグリーン」ではなく「テストが通った」と言う。利用者が行動するのに必要でない限り、ハッシュ、ファイルパス、コマンド、ビルド番号、テストの件数は書かない。PR、ブランチ、エージェントは、自分で作ったラベルではなく、利用者が分かる名前で呼ぶ。ある事実が文脈なしでは意味をなさないなら、文脈を添えるか、その事実を書かない。

## 変わったことを集める

このターンは読み取り専用にする。図は手元にあるものだけから作る。コードを変えない。アプリやジョブを起動しない。何も投稿しない。そのメッセージ以降の自分の作業、サブエージェントからの報告、この会話にいるほかの人からのメッセージを集める。この会話が触れた各PR、CIの実行、エージェントの現在の状態を確かめる。示す数値はそれぞれ、もとになった事実と照らし合わせ、訂正したときはそう伝える。

アクション項目とは、利用者にしかできない判断や手順である。製品の選択、承認、取り消せない操作、自分に権限のないアクセスなどである。利用者の最後のメッセージより前に出たものでも、まだ利用者を待っているものは含める。自分でまだできる作業はアクション項目ではない。返答を埋めるために判断をでっち上げない。利用者が求めておらず、作業にも必要ない手順はアクション項目ではない。ただし、取り消せない操作で利用者を待っているものは例外とし、1行で書き、図は付けない。

一つの判断が多くの項目にまたがることがある。たとえば、マージを待つ一連のPRそれぞれである。各項目について、そのリンク、利用者にとって何が変わるか、自分の推奨の根拠となる証拠、そのリスク、自分の推奨を集める。判断に必要だが分からない事実には「不明」と書く。持っていないリンクは書かない。

## 返答を書く

言葉は経緯ではなく判断に使う。起きたことは図を除いて100語未満にし、起きたことが少なければもっと短くする。利用者にとって何も変えなかった作業は書かない。各項目には約30語を使う。返答は項目の数に応じて長くなる。2項目なら図を除いて全体で150語を大きく下回り、30項目ならはるかに多くなる。語数に収めるために、項目を削ったり縮めたりしない。リストの代わりに件数を書かない。項目の代わりにリンクを書かない。リンクは深さを足せるが、返答だけで判断できなければならない。

利用者を待っているものを挙げる、または何も待っていないと言う、短い1文で始める。詳細はアクション項目で示す。何も起きておらず、何も利用者を待っていないなら、そう言って終える。

次に、起きたことを図から先に示す。作業で得たスクリーンショットと動画を本文に埋め込み、続いて変更を説明する図を置く。それから、利用者が求めたことごとに短い箇条書きを1つずつ書いてまとめる。その結果どうなったか、そして完了・実行中・失敗・未確認のどれかである。各行は口に出して言うように書く。「検索が遅かったのはインデックスがなかったから」と書き、「検索のレビュー：完了」や「遅い検索：インデックスの欠落」とは書かない。途中で見つけて直したバグは挙げる。各行は単独で読んでも正しくなければならない。まだ利用者を待っているものを完了と書かない。アクション項目で述べることは書かない。まとめの下に、利用者が知っていることや、しなければならないことを変える短い行を、最大3行書く。そのあと、自分でできる残りの作業を1行で挙げる。

次に、アクション項目を並べる。マージ、承認、選択など、利用者が持つ判断を問い、自分の推奨を示す。自分なら先にする手順は推奨に含める。先に済ませなければならないことと、取り消せないことも推奨に含める。判断の対象となる各PR、issue、エージェントの番号かリンクを示す。選択肢の中から選ぶ判断でも同じである。

形は判断に合わせる。1つの項目についての判断は、箇条書き1つにする。判断、自分の推奨、利用者にとって何が変わるか、推奨の根拠となる証拠、そのリスクを書き、項目の名前は1回だけ挙げる。複数の項目が同じ判断を共有するときは、判断と推奨を1回だけ書き、各項目にそれぞれの箇条書きを付け、リスクの高いものから並べる。その箇条書きには、リンクと名前、利用者にとって何が変わるか、推奨の根拠となる証拠、そのリスクを書く。項目ごとの推奨は、判断全体の推奨と違う場合だけ挙げる。リスクが低くても、各項目のリスクを書く。たとえば「低リスク：色だけが変わる」。待つことの代償は、締め切りやデータの損失など、遅れ以上のものである場合だけ書く。

選択肢の中から選ぶ判断では、作業で比べたすべての選択肢を挙げ、それぞれが利用者にもたらすものとそのコストを書き、現在の状態があればそれも書く。そのコストが判断のリスクなので、別にリスクの行を足さない。上のスクリーンショットが選択肢を示しているときは、各選択肢の利点とコストをそのスクリーンショットの下に書く。

## 図

図とは絵のことである。スクリーンショット、動画、Mermaidの図、`/visualize`で作るチャートや図、生成した画像である。Markdownの表は、変更前後の列があっても図ではない。

文より絵のほうが理解しやすいものは描く。設計やシステムがどう動くか、各PRの状態を付けたPRのスタックや依存の連なり、修正の前後、並べた選択肢などである。状態の一覧、アクション項目の一覧、何もつながっていない箱の集まりは決して描かない。同じ事実を、文でも図の間でも、2回示さない。

各図は一目で読める小ささにする。箱は最大6つ、各箱の言葉は最大8語にする。ラベルは「Tests: pass」のようなタグではなく、人が口にする平易な言葉で書く。文が必要な事実は本文に書くか、どこにも書かない。

変更が目に見えるものなら、スクリーンショットと動画をリンクだけでなく本文に埋め込む。目に見える変更にそれがないなら、そのまとめの行に「スクリーンショットはまだない」と書き、画面で何が変わったかをそこで述べる。図やチャートは手元の事実から描く。物事のつながりにはMermaidの図、数値には`/visualize`のチャートを使う。数値を決してでっち上げない。自分で撮っていない画面の絵を描いたり生成したりしない。リンクするのは実在する成果物だけにする。
