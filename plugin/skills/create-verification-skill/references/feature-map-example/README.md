# Notesの検証の地図

このディレクトリは、Notesの利用者向けの振る舞いを検証するための、保守される拠り所である。アプリを操作する前に索引を読み、該当する機能のファイルを手順として使う。

## 基本の前提

- 使い捨てのデータディレクトリで、Notesを`http://127.0.0.1:4173`に起動する。
- 同時に動く実行が状態を共有しないように、`NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`を設定する。
- `Quarterly plan`と`Grocery list`という題名のノートをシードする。
- `control-notes`と`notes` CLIを`PATH`に入れる。
- `control-notes doctor`を実行し、期待するURL、データディレクトリ、ビルドのリビジョンが出ることを必須とする。
- この検証の実行が起動していないインスタンスは操作しない。

## 操作の約束

- 前提に別の指定がない限り、どの手順も基本の状態から始める。
- CSSセレクタやDOMの位置より、ARIAのロールとアクセシブルネームを優先する。
- すべてのコマンドを文字どおりに扱う。引用符で囲んだ名前とフラグは変えない。
- ブラウザの操作は`control-notes browser`で行う。
- 端末の操作は`control-notes cli -- <command>`で行う。
- データを変更したら、シードしたデータを元に戻す。後片付けで証明の成果物を消さない。

## 証明と省略の報告

- 最後の画面だけでなく、利用者の操作とその結果の状態を残す。
- UIの証明には、ARIAのスナップショットと、アプリが識別できるスクリーンショットを含める。
- CLIの証明には、コマンド、stdout、stderr、終了コードを含める。
- 変更の証明には、保存された値を読み取り専用の別の画面で見たものを含める。
- どの成果物にも、機能のIDと使った入口を記録する。
- たどり着けない経路は、試したコマンドと満たせなかった前提を添えて報告する。
- 省略した入口を、別の経路で検証済みとして報告しない。

## 機能ファイルの約束

各機能のファイルは、H1の題名と、利用者に見える振る舞いを説明する1段落から始める。そのあとに、ちょうど4つのH2をこの順に置く。

1. `サブ機能`は、短いIDと、振る舞いごとに1行の説明を並べる。
2. `たどり着き方（利用者の視点）`は、利用者の入口をすべて挙げる。
3. `<harness>で操作する`は`前提：`から始め、利用者の操作ごとに正確なコマンドと観察できる結果を組にした、ラベル付きの箇条書きにする。
4. `注意点`は、検証の実行を無駄にしたり無効にしたりしうる落とし穴を挙げる。

地図に実装の詳細を入れない。書くのは、利用者の経路、安定した手がかり、必要な状態、コマンド、観察できる証明だけにする。

## 機能

- [ノートを作る](./create-note.md)は、ブラウザとCLIでの作成、取り消し、保存の確認、後片付けを扱う。
- [ノートを検索する](./search.md)は、ツールバー・キーボード・CLIからの検索と、一致・該当なし・クリアの状態を扱う。
