# 検証スキルを作る

まともなプロジェクトには、実物のアプリを操作して振る舞いを確かめる、スクリプト化された手段が必要である。アプリを起動し、利用者と同じやり方で機能を動かし、証拠を残す。このスキルは、それをリポジトリに合わせたプロジェクト専用のスキル（`.claude/skills/verify-<app>/`）として作る。生成するものは人間ではなく次のエージェントに向けて書く。そのエージェントは、アプリを一度も見たことがないまま、作業の途中で予備知識なしにそれを読む。

## 1. 利用者ではなくリポジトリに聞く

次の問いにはコードベースから答え、観察できないことだけを利用者に聞く。

- **接点：** 利用者が実際に触るものは何か。Web UI、CLI・TUI、デスクトップアプリ、API、モバイルアプリ、ライブラリのどれか。リポジトリに複数ある場合もある。主なものを一つ選び、残りを書き留める。
- **起動：** ローカルでアプリをどう起動するか。リポジトリ自身が文書にしている開発用コマンド（パッケージのスクリプト、Makefile、READMEのクイックスタート）を優先する。ポート、環境変数、シードデータ、認証を書き留める。
- **操作：** エージェントはプログラムからどう操作できるか。まず既存の仕組みを使う。Playwright・Cypressのspec、expectスクリプト、PTYの補助、curlで叩けるエンドポイント、デバッグポートなど。それがなければ汎用の手段を選ぶ。WebとElectronにはブラウザ・CDP、CLI・TUIにはtmux・PTYの仕組み、サービスには素のHTTPを使う。
- **観察：** どんな証拠を残せるか。スクリーンショット、端末の記録、レスポンスの本文、ログ、終了コード、DBの状態。
- **分離：** 2つのインスタンスを並べて動かせるか（ポート、データディレクトリ、プロファイル）。できないなら、生成するスキルにそう書く。共有のインスタンスを二重に操作して利用者のセッションを壊すより、断るほうがよい。

チェックアウトしたままの状態でビルドや起動ができないなら、生成の前にそれを直す（または正確に報告する）。壊れた土台に向けて書いたスキルは、誤った手順を教える。関係のない欠けたファイルが起動を妨げる場合（APIが配信しない静的ディレクトリ、サンプルの設定など）は、生成するスキルがそれを作ってよい。ただし検証用の足場であることをはっきり示し、後片付けで消す。

## 2. スキルを生成する

`.claude/skills/verify-<app>/SKILL.md`を書く。YAMLのfrontmatter（`name: verify-<app>`と、アプリ・接点・使う場面を挙げた`description`。frontmatterがないとスキルは登録されない）と、次の節を入れる。どの節も、聞き取りで実際に分かったことに基づかせる（プレースホルダーを残さない）。

- **起動：** 検証のためにアプリを起動する正確なコマンドと、準備ができたことの見分け方（ログの行、プロンプト）。起動は、空のデータディレクトリから、マイグレーションやシードデータを含めて使える状態まで到達しなければならない。準備ができたとは、プロセスが応答することではなく、使えることを指す。データベースのヘルスチェックは、初期化スクリプトが動いている途中でも通ることがある。停止の方法も入れる。短命なCLIやTUIには動かし続けるサーバーがない。その場合の起動とは、バイナリを一度ビルドし（または依存を入れ）、操作のたびに分離したPTYかtmuxのセッションで起動することを指す。
- **診断：** 「このインスタンスは操作する価値があるか」に答える、読み取り専用の確認を一つ。プロセスが動いている、バージョン・ビルドが正しい、ポートを自分たちが持っている、認証が有効である。何かおかしいと思ったら、エージェントはまずこれを実行する。
- **操作：** このリポジトリの実際のセレクタ・コマンドを使った操作の手順。例ではなく実物を書く。座標やタブ順より、安定した手がかり（ARIAラベル、data属性、プロンプトの文字列、ルートのパス）を優先する。
- **証拠：** 証明のために何を残し、どこへ置くか。証明の基準を書く。内部のsetterやテスト専用のエンドポイントではなく、利用者が実際に通る経路を動かす。最後の画面だけでなく、操作とその結果の状態を残す。見えるものと合わせて副作用（書かれたファイル、追加された行、送られたメッセージ）を確かめる。モックは、本番の境界がすでに外部システムを切り離している場所でだけ使う。安全な経路がdry-runやテストモードなら、名前を信じず、実際に何を省いているかを観察して確かめる（ファイル、ネットワーク、gitのref）。dry-runでもネットワークに触れたりブラウザを開いたりするものがある。
- **後片付け：** 実行が作ったインスタンスを停止する方法。プロセス名で止めない。自分が起動したものを止める。後片付けで消すのはインスタンスと一時的な状態であり、証拠は消さない。証明の成果物は停止のあとも、スキルが名指しした場所に残る。
- **補助スクリプト：** スキルに同梱するスクリプトは実行可能にし、その呼び出し方をスキル本文に示す。読む人が解読しなければならない補助スクリプトは、補助にならない。

## 3. 機能の地図を作り始める

`.claude/skills/verify-<app>/features/README.md`と、見つけられた利用者向けの機能ごとに1ファイルを作る（まずはルート、コマンド、メニュー、文書から上位3〜5個を目安にする）。[`references/feature-map-example/`](references/feature-map-example/)の形に従い、READMEの索引と、機能ごとに1ファイルを置く。各ファイルは利用者の視点から、その機能が何か、どうたどり着くか、仕組みでどう操作するか、どんな観察できる最終状態が動作の証明になるかに答える。4つのH2は`サブ機能`、`たどり着き方（利用者の視点）`、`<harness>で操作する`、`注意点`とする。ある利用の流れに必要な前提がシードデータにないなら、その流れは失敗を報告し、理由をその機能の`注意点`に書く。通すために流れを弱めてはならない。地図はリポジトリで保守される検証の拠り所である。地図がほかの入口を挙げているのに、都合のよい入口を一つだけ動かした証明は不完全である。

## 4. 渡す前に生成したスキルを証明する

そのスキル自身の手順を最初から最後まで一度実行する。起動、診断、地図にある機能を一つ操作（一つで足りる。残りは後の実行で扱えるように地図がある）、証拠の記録、後片付け。後片付けのあと、証拠が名指しした場所にまだあることを確かめる。証明を消してしまう後片付けは、この段階で不合格である。失敗したところを直し、失敗した試行のたびに生成した後片付けも実行して、壊れた試行がプロセスやポートを置き去りにしないようにする。一度も実行していない生成スキルは下書きであり、成果物ではない。本当の対象の代わりのもので証明した場合（新しいVMの代わりにコンテナ、リモートの環境の代わりにローカルの環境）は、代わりのものでは行ったが本当の対象では行われない準備の手順をすべて挙げる。それらの手順は、本当の対象での実行で確かめるまで未検証のままである。

## 5. 保守の流れを案内する

アプリが変わっても地図を正しく保つために、利用者に`/koto:maintain-verification-skill`を案内する。頻度の提案は、聞かれたときだけにする。
