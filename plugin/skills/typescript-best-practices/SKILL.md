# TypeScriptのベストプラクティス

最初に**type-system-discipline**の原則スキルを適用する。

| ルール | 要点 |
|------|---------|
| 判別可能なユニオン | 種類の違いは`kind`のリテラルの判別子で表し、ありえない状態を表現できなくする。省略可能なフィールドの寄せ集めにしない。 |
| ブランド型 | プリミティブに`& { readonly __brand: "X" }`でブランドを付け、取り違えられないようにする。検証は境界で一度だけ行う。ブランドは、確かめる型ガード（`input is AgentId`）から得るものであり、`as`から得てはならない。 |
| 構成によるモデル化 | 不正な値を作れない形にする。空でない配列には`[T, ...T[]]`、偶数の長さには`[T, T][]`、範囲には`start`と`duration`。実行時のガードでも、refinement typeへの願望でもない。 |
| 最も単純な全域の型 | それに対するすべての操作が全域である限り、`T[]`のままにする。緩い型のせいで`!`、キャスト、「起きるはずがない」throwが必要になる場所でだけ、`NonEmpty<T>`へ強める。 |
| `any`より`unknown` | 外部のデータは`unknown`とする。 |
| ガードの前にスキーマ | プロパティを一つずつ調べる型ガードを手で書く前に、リポジトリの実行時スキーマのライブラリを使い、`z.infer`などで型をスキーマから導く。 |
| `as`キャストを使わない | どの`as`も、いずれ実行時に落ちる。キャストは検証のあとにだけ行う。 |
| 絞り込みの優先順位 | 判別子のswitch > `in`演算子 > `typeof`・`instanceof` > ユーザー定義の型ガード > `as`。 |
| 型ガード | 主張を本当に確かめなければならない。嘘をつくガードは`as`より悪い。安全だと名乗る名前の陰にバグが隠れるからである。`isX`または`hasX`と名付ける。 |
| 網羅性 | defaultの分岐に`const _exhaustive: never = x;`を直接書き、新しい種類が加わるとコンパイラがエラーにするようにする。 |
| `as`より`satisfies` | リテラル型を広げずに値を検証する。 |
| 境界での検証 | データが入ってくる場所で、名前の付いたドメインの型へ解析する。`Record<string, unknown>`（どう綴っても）はその解析で止める。内部では型を信頼する。**boundary-discipline**の原則スキルを参照。 |
| スキーマから導く型 | 新しいinterfaceを宣言する前に、`Pick`・`Omit`・`Parameters`・`ReturnType`・`Awaited`・`typeof`を使う。 |
| オブジェクトの引数 | 位置ではなくオブジェクトで渡し、引数の順序が説明なしに分かるようにする。ホットパス（フレームごとの描画、トークナイザ、パーサ）では使わない。 |
| 本物のテスト | 動かせるものをモックしない。リークや破棄の確認が付いた、フレームワークの本物のテスト部品を優先し、UIは動いているビルドで確かめる。モックはローカルで動かせないものだけにする。 |
| 構造化されたテレメトリ | IDから調べられるだけの文脈を持つ、構造化されたロガーの診断情報を優先する。出荷するコードに`console.log`を入れない。 |
