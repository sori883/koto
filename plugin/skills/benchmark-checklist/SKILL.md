# ベンチマークのチェックリスト

性能の数値を出すときに使う。PRの変更前後、性能低下の主張、hillclimbのハーネス、ライブラリや設定の選択などである。各質問には、コードについての推測ではなく、実行から得た証拠で答える。

利用者が求めたのがおおよその目安なら、1回の実行で足りる。それでも質問4と7は確かめ、1回の実行であることを伝える。その実行がおかしく見えない限り、残りは省いてよい。選択肢の中から選ぶ作業は、決しておおよその目安ではない。

## 実行する前に

- 出すつもりの主張を、そのまま出せる言葉で書き出す（「60k行のデータセットで、エクスポートがp50で30%速い」）。質問はその文を検査する。
- 測定スクリプトを読む。何を計時し、何を数え、何を無視しているかを書き留める。
- `uptime`でロードアベレージを、`nproc`でコア数を確かめる。マシンが混んでいるなら、何が動いているかを突き止める。止められないなら、両方の側が同じノイズを受けるよう交互に実行し、報告でそう伝える。

## 質問

1. **なぜ2倍にならないのか。** 制約要因を挙げる。プロファイラやトレーサは処理を遅くするので、プロファイルは報告しない実行で取る。プロセスごとのCPU（`top`、`pidstat`）、ランタイムのプロファイラ（`node --cpu-prof`、`py-spy`、`perf`）、I/O待ち、システムコールの回数（Linuxでは`strace -c`）を使い、ホットスポットをソースに対応づける。負荷を生成する側も見る。それが先に飽和するなら、測ったのは負荷生成側である。変更で数値が動かなかったなら、その理由は制約要因が説明する。だから、その変更を役に立たないと言う前に制約要因を見つける。
2. **調整されていたか。** どの側も本番と同じ方法で動かす。リリースビルド、本番のフラグと環境変数、バッチ処理とトランザクションの設定、コネクションプール、本番と同じ温まり具合のキャッシュ、同じバージョンとデータである。片方がデフォルト設定で動いていたなら、比べたのは実装ではなく設定である。制約要因が設定（1行ごとのコミット、デバッグビルド、インデックスの欠落）なら、その側は調整されていない。調整して測り直してから勝者を決める。調整できないなら、その実行から勝者を決めない。利用者が何を採用するかを選んでいるときは、主張を「現在出荷されているままのコード」に絞っても、この問題は解決しない。利用者が採用するのは選択肢であって、今日の設定ではないからである。
3. **限界を超えていないか。** 計算する。1秒あたりのバイト数をディスクとネットワークの帯域と比べ、1秒あたりの操作数に1操作あたりのコストを掛けたものをコア数と比べ、短縮された時間を変更した部分にかかっていた時間と比べる。実行時間の10%を占める部分を取り除いても、実行が速くなるのはせいぜい約11%である。限界を超えた結果は、作業以外のもの、たとえばキャッシュ、何もしない処理、バグを測っている。
4. **エラーは出ていないか。** 失敗と成功以外の応答を数え、出力が存在するだけでなく正しいことを確かめる。拒否は速いことが多く、タイムアウトと再試行は遅い。スクリプトがエラーを数えていないなら、数える処理を足す。
5. **再現するか。** 各側を少なくとも5回、交互に（A、B、A、Bのように）実行し、ウォームアップ、遅延初期化、キャッシュ、ドリフトがどちらにも有利にならないようにする。中央値と範囲を報告する。実行ごとのばらつきより小さい差は、測定できる差ではない。判定がきわどいときは、順位和検定かハーネス自身の統計を使う。
6. **意味があるか。** ミクロな結果の横に、利用者が待つエンドツーエンドの経路を、現実的なデータ量と並行度で測り、ミクロな結果を全体に占める割合として報告する。リクエストの1%を占めるヘルパーは、どれだけ速くなっても、リクエストを最大1%しか速くできない。
7. **そもそも実行されたか。** 計時した区間の中で作業が実行されたことを確かめる。リクエストがサーバーに届いたこと、行が書き込まれたこと、バイトが読まれたこと、コードが結果を使ったことである。遅延評価のコード（誰も反復しないジェネレータ、誰もawaitしないPromise、JITが捨てられる結果）とタイムアウトは、実行されなかった作業の数値を生む。

## 報告

- 判定から書き始める。速くなった、遅くなった、測定できる差はない、または結論が出ない、のいずれかである。
- 数値を単位、実行回数、範囲、制約要因とともに示す。たとえば「p50 41 ms → 33 ms、各側7回の中央値、変更後の範囲は32〜35 ms、1コアでのJSON解析が制約」。
- 差があると主張しながら制約要因を挙げられないとき、片方が未調整で動いていたとき、質問4と7を確かめられなかったときは、判定を「結論が出ない」とする。足りない点を挙げる。
- PRの本文に載せる主な数値は一つにする。実行結果、範囲、制約要因の証拠は、リンクした成果物かメモのファイルに置く。

## ほかの性能に関する資料

- **Perf issue**プレイブックのベースラインは、プレイブックがそれをもとに計画を立てる前に点検する。そのあとのすべての数値も点検する。
- **Hillclimb**プレイブックのハーネスは、固定する前に点検する。固定したハーネスはエラー数と作業量を出力するので、残すか戻すかを決めるたびに、質問4と7が手間なく確かめられる。
