# TDDによるバグ修正

明確で低コストなテストの経路があるバグを直すときは、本番のコードを変える前に、壊れた振る舞いを実行できる形にする。目標は、修正前に失敗し、修正後に通る、焦点を絞った回帰テストである。

現実的でないときは、テストを無理に作らない。使えるテストに、大がかりなハーネスの準備、壊れやすいモック、遅いエンドツーエンドの基盤、本番にしかない状態、あいまいな再現手順、無関係なフィクスチャの大量の変更が必要なら、新しいテストは足さず、最も近い有用な検証を使う。

## 手順

1. **バグを理解する。** 意図した振る舞い、現在の振る舞い、影響を受ける経路、観察できる最小の再現を特定する。
2. **最も狭い実行可能な確認を選ぶ。** そのコード経路ですでに使われている、最も近い単体・コンポーネント・結合・回帰テストを優先する。現実的なテストの経路が明らかでないなら、手順を満たすためだけにゼロから作らない。
3. **失敗するテストを先に書く。** そのバグを捕まえられたはずの、最小で焦点を絞ったテストを足す。テストは現在の実装をなぞるのではなく、意図した振る舞いを表す。
4. **修正の前に新しいテストを実行する。** 意図した理由で失敗することを確かめる。通ってしまう、または無関係な理由で失敗するなら、実装を編集する前にテストか再現を直す。
5. **バグを直す。** 近くの契約を保ちながら、意図した振る舞いを満たす最小の本番の変更をする。
6. **回帰テストを再実行する。** テストが通るようになったことを確かめる。

## 失敗するテストが現実的でない場合

代わりに、最も近い実行可能な回帰の確認を使う。対象を絞ったスクリプト、手動の再現コマンド、ブラウザの自動操作、スナップショットの比較、ログの検証、焦点を絞った結合の確認などである。

悪いテストよりは、新しいテストがないほうがよい。悪いテストとは、主にモックを検査するもの、現在の実装の詳細を表すもの、タイミングや無関係なグローバル状態に依存するもの、小さな修正に高価な基盤を必要とするもの、修正を証明したらすぐ消されるものである。

## 守ること

- 誤った実装に合わせるためだけにテストを変えない。
- 期待する振る舞いが本当に変わり、その理由が明確な場合を除き、既存のアサーションを弱めない。
- 回帰テストはバグに焦点を絞る。フィクスチャの大量の変更や、無関係なカバレッジの拡大を避ける。
- バグが不安定に再現するものなら、できる限りテストを決定的にし、固定する信号を記録する。
- バグがより広い種類の失敗を示しているなら、まず焦点を絞った回帰の経路を入れ、そのあとで同種の箇所のカバレッジを検討する。

## 最終報告

結果だけでなく、証拠を報告する。

- 修正前に失敗したテストまたは実行可能な確認と、それが出した失敗を挙げる。
- 修正後に通ったテストの実行と、近くで行った検証を挙げる。
- 修正前に失敗する証拠を示せなかったなら、その理由を述べ、代わりに使った最も近い回帰の確認を説明する。
