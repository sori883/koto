# Recall

**利用者の最近の作業の状況を組み立て直し、いまどこにいて次に何をするかを短く返す。何も書き換えない。**

範囲に入る筋に要るものだけを読み、そこで止める。

作業の状況は、次の記録にある。

- チケット：何を、どこまでやれば終わりか、いまの状態、checkpoint（現在地と次の操作）。判断の経緯は同じフォルダの`decisions.tsv`にある。
- 会話記録：何をして、何を決めたか。チケットを作らない作業は、ここにしか残っていない。
- Git・PR：実際に何が入ったか、何が開いたままか。
- 共有の記録：同じコードの周りで起きたこと。Issue、差し戻しや取り消しになった修正、まだ出ているエラーなど。

Knowledge（`.space/kb/`）は読まない。入っているのは終わった判断と制約で、作業の状況は入っていない。

## 手順

1. **振り分ける。** 特定の1件の続きをやってほしいと言われたら、これではなく、koto-modeの**Session pickup**プレイブック（`../koto-mode/playbooks/session-pickup.md`）に従う。利用者が現在地（パス、ブランチ、変更の中身）をすでに渡していれば、それを使い、記録を掘らない。
2. **範囲を決めてから探す。** チケットや話題の指定があれば、それに絞る。会話記録の期間は、既定で直近7日とする。作業フォルダは現在のものだけにし、頼まれない限りほかのプロジェクトの記録を読まない。決めた範囲を返答の最初に書く。「全部」と言われたものを、黙って「最近」に縮めない。
3. **チケットを読む。** `.space/tickets/`があれば、Skillツールで`koto:ticket`を呼び、`ticket.ts list`で範囲に入るチケットを探す。`running`と`paused`のチケット、範囲の期間に更新されたチケット、話題に合うチケットである。それぞれの`ticket.md`の目的、終了条件、成果物、checkpointと、`decisions.tsv`の最後の数行を読む。
4. **会話記録を読む。** チケットやGitに出てこない作業（相談、調査、検討だけで終わったもの）は、ここにしか残らないので、チケットやGitで足りたように見えても省かない。会話記録は`~/.claude/projects/<作業フォルダのパスを変換した名前>/<セッションID>.jsonl`にあり、1行が1件のメッセージである。変換した名前は、作業フォルダの絶対パスの英数字以外の文字（`/`や`.`）を`-`に置き換えたものになる（`/Users/me/proj`なら`-Users-me-proj`）。`~/.claude/projects/*/`をまたいでglobしない。
   - 候補は実際の更新時刻の順（`ls -t`）に並べる。セッションIDの名前順にしない。
   - 話題があれば、先にその語でgrepし、当たったセッションの、当たった部分だけを読む。話題が無ければ、期間内のセッションそれぞれについて、利用者の最初の依頼と最後のやり取りを読む。
   - 今の会話と、`<セッションID>/subagents/`の下の記録は飛ばす。ほかのセッションは、利用者の最初の依頼を読んでから、範囲に入るかを中身で決める。更新時刻が近い、件数が多い、といった見た目だけで飛ばさない。
   - 1〜2件なら直接読む。それより多ければ、速く安いモデルのサブエージェントに分けて並行で読ませる（**principle-guard-the-context-window**スキル）。各サブエージェントには、セッションごとに同じ形で返させる。話題、利用者の目的、判断、残っている筋、つまずきと訂正、成果物（PR、チケット、ブランチ）で、それぞれにセッションIDを添える。生の記録は主のスレッドに持ち込まない。
5. **共有の記録を調べる。** 話題に機能、ファイル、領域、不具合の名前が出ていれば、必ず調べる。「自分の作業」と言われても省かない。手順4と並行して進める。
   - GitHubのPRとIssueは、`git`と`gh`で調べる。関係するPR、差し戻しや取り消しになった変更、開いたままのIssueを見る。
   - エラー監視やチャットなどは、接続（MCP）があるときだけ調べる。情報源ごとにサブエージェントを1体起動し、並行で動かす。問いは「今の状態はどうか、何を試して効かなかったか、利用者がまだ何を報告しているか」とする。
   - 見つからなかったことも結果として扱う。使えない接続は飛ばし、飛ばしたことを報告に書く。
   - 「今週何をしたか」のように対象の名前が無いときは、この手順を飛ばす。
6. **実際の状態で確かめる。** 手順3〜5で見つかったPR、ブランチ、チケットを、`git`と`gh`で確かめる。checkpointや会話記録が実物と食い違えば、実物を正として報告に書く。チケットは直さない。作業をした側が実際に何をしたか（実行したツール、読んだファイル、出たエラー）で答えが変わるときは、会話記録を省略せず全部読む。
7. **報告を書く。** 下の形で、筋ごとにまとめる。名指しされた話題から外れない。

## 報告の形

最初に要約、次に筋ごとの状態、次に問題、最後に次の一手を書く。詳しいことは下に回すか、削る。

- **要約。** 5行まで。この作業が何で、全体としていまどこにいるか。
- **筋。** 1筋1行とし、行頭に次の印を一つだけ付ける。印の無い筋は終わっていないので、必ず付ける。
  - `[マージ済み #N]`
  - `[PR中 #N]`
  - `[作業中 <ブランチ>]`
  - `[確認済み・未コミット]`
  - `[中断 <チケットID>]`
  - `[取り消し #N]`
  - `[未着手]`
- **問題。** 5件まで。繰り返し起きているものを書く。利用者が報告し続けている症状と、出したが取り消された修正を含める。次の試みが、前の試みの失敗したところから始められるようにする。
- **次の一手。** いちばん役に立つ次の操作を一つ、具体的に書く。

隣の機能やチケットは、これを止めているときだけ入れる。要約と筋が1画面に収まらないときは、筋を削る前に細部を削る。文章は**unslop**スキルで整える。根拠を添える。会話はセッションID、チケットはチケットID、共有の記録はPR番号、Issue番号、チャットのリンク、エラーの識別子で示す。公開の場に出すときは、非公開の文脈を取り除く。

**返答：** 上の形の報告。続きをやるよう頼まれたら、**Session pickup**プレイブックに従う。
