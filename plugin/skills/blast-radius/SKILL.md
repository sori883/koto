# 影響範囲

出荷する前に、変更がどこか別の場所で何を壊すかを見つける。「Xの影響範囲」「これで何が壊れうるか」と頼まれたとき、またはまだ信用できない小さな差分をレビューするときに使う。

`how`と`why`の相棒である。`how`はコードが何をするかを教える。`why`はなぜその形なのかを教える。影響範囲は、それがどこか別の場所で何を壊すかを教える。

呼び出し元を挙げることが仕事ではない。それならエージェントがgrepで一瞬で出せる。仕事は、grepでは見えない壊れ方を見つけることである。

## 自分のまとめを信用しない

もっともらしく聞こえる影響範囲のまとめには価値がない。正しくても正しくなくても、説得力があるように読めてしまう。だから、まとめを返さない。全体が依存している1つか2つの事実を見つけ、コードを動かして証明する。

### どれだけ確かか

変更の安全性が依存している各事実について、手間がかからない範囲でこの一覧のできるだけ下まで進め、どこで止まったかを言う。

1. 自分がそう言った。それだけでは価値がない。
2. 該当する行を示した。実在する`file:line`、またはライブラリ自体のソース。
3. 悪い場合が起こりえないことを示した。失敗の経路を一歩ずつたどり、そこに至らないことを示した。
4. 実行した。実際のコードを呼び出し、自分が間違っていれば大きく失敗するスクリプトかテスト。
5. 動いているアプリで再現した。

手順4はたいてい、アプリが同梱しているのと同じライブラリをimportし、気になっている関数そのものを呼ぶ小さなスクリプト一つで済む。

## 手順

1. 変更を読む。差分、追加・変更・削除されるシンボル、そして差分に明記されていない部分も含めて、今までと何が違う動きになるかを読む。PRとそのコミットを取得する。
2. 安全だと言える根拠の一つの事実を見つける。危険に見える変更の多くは、一つの事実のおかげで安全である。たとえば「この呼び出しは、すでに使われていないキャッシュ項目を落とすだけで、ほかに何もしない」。その事実を見つける。それが成り立てば、危険な場合の大半が一度に消える。時間はここに使い、「もしかしたら」の長い一覧には使わない。
3. grepが止まる先を見る。呼び出しているライブラリのソースを読み、固定されたバージョンと手元のパッチを確かめる。いつ実行されるかを突き止める。マイクロタスク、アンマウントと後片付け、SolidかReactか。シンボル検索が見逃すものをたどる。APIが返すJSON、DBの列、通信の形式、同じバイト列を読む別の言語、フィーチャーフラグ、3段先の下流のコード。
4. 各リスクに正直になる。起こる現実的な可能性と、起きたときの現実的な損害を示す。確認できたリスクは残す。調べて問題なしとしたものは別に挙げる。実在する`file:line`を引用する。何も見つからなかった検索もそれ自体が答えである。呼び出し元やAPIを作り話にしない。
5. その一つの事実を証明する。実際のコードを動かすスクリプトかテストを書いて実行し、起きたことを貼り付ける。
6. 大きい、または広い変更は`arena`として動かす。同じ質問を複数のモデルに聞き、答えをまとめる。モデルが違えば、捉える本当のバグも違う。

## 返すもの

- **何をするか。** 何が変わったか。明らかでない部分も含める。
- **安全だと言える根拠の一つの事実。** それを述べ、どの段階まで確かめたかを言い、証明を示す。証明できなかったら「未証明」と書く。
- **リスク。** それぞれ、どう壊れるか、`file:line`、どれだけ起こりやすく、どれだけ悪いか、どう確かめるかを書く。重要なものには証明を貼り付ける。
- **問題なしとしたもの。** 何を調べ、なぜ問題ないか。
- **マージの前に。** 本当のバグを捉えるもっとも安いテストか再現。自分が書いたスクリプトも含める。

`unslop`を通して書き、実在するコードを引用し、公開の場に出す前に非公開の情報を取り除く。

**返答：** 上のまとめ。安全だと言える一つの事実は、証明済みか未証明かを明記する。
