# Statechart

図は、システムが状態の間をどう移るかを、それを読む人の言葉で示す。その人、つまり読み手が、振る舞いが正しいかを判断する。

## 実行

リポジトリの外の作業用フォルダで作業する。TLA+のspecとその設定ファイルを書く。それから次を実行する。

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts`はTypeScriptなので、TypeScriptを実行できるランタイムで動かす。`scripts/statechart`は、それを一つ選ぶPOSIXシェルスクリプトである。ネイティブのWindowsでは、Node 22.18〜22.x、またはNode 23.6以降で`node --disable-warning=ExperimentalWarning <skill dir>/scripts/statechart.ts`を実行する。

最初の実行では、miseでTLCとJavaをインストールするので、ネットワークが必要になる。

## specを書く

- 読み手が同意する各ルールを、INVARIANTとして書く。ルールは、画面、結果、保存された値、メッセージについてのものでよい。ルールに対応する変数がモデルになければ、変数を足す。ルールを成り立たせるために弱めることはしない。
- `Next`は、`YouPressPlay \/ YouPressStop`のように、動作の選言として書く。そうしないと、TLCはすべての手順を`Next`と名付ける。
- 出ていく手順のない状態は、正しい終了状態であっても`NoDeadlock`を破る。INVARIANTかPROPERTYがすでにその名前を持つときは、ルールは`CHECK_DEADLOCK`になる。終了状態でだけ真になり、何も変えない動作を`Next`に足す。`Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`のようにし、`step()`でラベルを付ける。

## 図を選ぶ

判断が必要な作業はあなたが行う。各状態と矢印の言葉、フェーズとその色、タイトル、読み手へのレポートである。その作業をviewモジュールにまとめ、`--view`で渡す。

読み手の言葉を示すには、viewが`state(vars)`をexportする。`state()`が返す値で形が決まる。

- 文字列はフラットな図になる：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 配列は親の状態になる：`export const state = (v) => v.main.split(".");`
- オブジェクトは、キーごとに一つの並行領域になる：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

各状態には、「Paying」や「Lease held, write pending」のように、読み手が見えるもの、または気にかけるもののラベルを付ける。ラベルに変数名を入れない。`vars`では、TLA+のシーケンスは1から始まるキーを持つオブジェクトになるので、`v.pc[1]`が`pc[1]`である。集合は配列になる。

viewは`step(action, from, to)`もexportできる。この関数は、TLCの動作の名前と、手順の前後の値を受け取り、矢印のラベルを返す。各手順のラベルは、「you press play」や「the connect fails」のように、利用者が目にする出来事として書く。コードやTLA+の動作の名前を書かない。図の上で同じ結果になる二つの動作には同じラベルを付け、一本の矢印を共有させる。

手順がある条件でだけ起こるときは、ラベルの最後に、読み手の言葉で条件を角かっこに入れて書く。`you press play [while the file loads]`のようにする。領域のある図では、コマンドがほかの領域についての条件を、それらのラベルの言葉で矢印に書く。`[when Offline]`のようにである。あなたの角かっこはそれを置き換え、すると一つの状態から出る二本の矢印が同じに見えることがある。そのため、領域のある図では、ほかの領域についての条件を角かっこで書かない。どのラベルにも出ない値が手順の行き先を決めるときは、「the roster read fails」のように、その結果をラベルで名指しする。

viewは次もexportできる。

- `group(vars)`はフェーズの名前を返す。図の各状態は、そのグループの色になる。一つの図の状態の背後にあるモデルの状態が別々のグループにあるときは、その状態には色が付かない。
- `colors`は、各グループ名に色のクラスを与える。
- `title`は、図の上部に表示する文字列である。

コマンドは、`state()`と`group()`をモデルの状態ごとに多くても一回、`step()`を手順ごとに多くても一回呼ぶ。図とレポートは、どちらもその答えを使う。そのため、各関数は引数だけに依存させる。

図は、一つのラベルの中にとどまる手順を描かない。読み手がそのような手順を見る必要があるときは、ラベルを分ける。

矢印はおよそ20本以下を目指す。それより多い図は読みにくい。まず`state()`からもっと粗いラベルを返す。同じように振る舞う値には一つのラベルを付け、戻りが何も変えない処理中の呼び出しのように、読み手に要らない詳細は省く。不具合の経路の各状態と、各マークは残す。統合によって`breaks`の状態が`mayBreak`に変わると、ルールが破れる場所が隠れる。別々のルールを破る二つの状態は統合しない。読み手が、どこでどのルールが破れるかを見られなくなる。それでも図が込み合うときは、すべての状態にあるリセットや、矢印がほかの矢印の示すことを繰り返すだけの手順のように、読み手に要らない手順について`step()`から`null`を返す。手順を隠すときは、次の規則を守る。

- 図の各状態を、開始状態から矢印でたどれるようにしておく。
- モデルで出ていく手順のある図の各状態から、少なくとも一本の矢印を残す。
- 一本の矢印の手順は、すべて隠すか、一つも隠さない。一部だけ隠すと、その条件が狭くなる。
- 引き渡しで、図がどの手順を隠しているかを言う。

## レポートを読む

- 図で、ルールを破る状態にはクラス`breaks`が付く。その背後のモデルの状態の一部だけがルールを破るときは、クラス`mayBreak`が付く。Legendが各マークのルールを挙げる。二つのルールが破れるときは、一つのマークに両方を挙げるので、どの状態がどのルールを破るかを引き渡しで言う。領域のある図では、ある状態を含む領域の状態の組み合わせがどれもルールを破りうるとき、その状態にマークが付く。ある組み合わせがルールを破りうるのに、その状態のどれにもマークがないときは、その組み合わせの各状態にマークが付く。
- TLCはルールを破る状態の先へ進むので、図は不具合の後の状態も示す。
- TLCが不具合の先へ進むため、状態に上限のないモデルは終わりなく動くことがある。定数を小さく保つか、CONSTRAINTを足す。
- VIEWかSYMMETRYがあると、TLCは同じとみなす状態を一つの状態として数え、図はその一つの状態を描く。矢印が、手順の行き着く状態ではなく、その状態を指すことがあり、レポートはそう言う。
- TLCは、CONSTRAINTやACTION_CONSTRAINTの先の各状態でルールを確かめるが、その状態を探索せず、デッドロックも確かめない。あるルールについてのTLCの最短の経路がそのような状態で終わるときは、図はその状態を描き、レポートはその経路を示す。図は、上限の先のほかの状態を描かない。そのような状態でのデッドロックは現れない。TLCは、ACTION_CONSTRAINTが除外する各手順の後でも、次の状態に別の経路で届く場合を含めて、ルールを確かめる。あるルールについてのTLCの最短の経路がそのような手順で終わるときは、図はその手順を描く。
- コマンドは、書かれたままの設定ファイルで、ワーカー1つのTLCを使ってルールを確かめる。ルールが破れると、コマンドはそのルールを除き、破れるルールがなくなるまでTLCを再実行する。最初の破れの後、大きなモデルが終わりなく動かないように、各実行は100,000個の異なる状態で止まる。実行がその上限に達するか、エラーで止まると、レポートは確かめなかったルールを「Rules not checked」の下に挙げ、図はそれらにマークを付けない。確かめていないルールは、成り立つことも破れることもある。確かめるには、破れるルールを設定ファイルから除くか、モデルを小さくする。上限のために足すモジュールはTLCの変数の順序を変えるので、PROPERTYについては、上限なしの実行とは別の反例をTLCが見つけることがある。
- `tlc.out`は、書かれたままの設定ファイルでTLCが出力したものである。図が破れるルールの不具合の経路を示さないときは、`tlc-RULE.out`が、それを見つけた実行でTLCが出力したものである。TLCが最初の警告を繰り返すとき、素のTLCはそれを二回出力するが、`tlc.out`は一回だけ示す。TLCが、このコマンドが読む出力から二つ目を外すからである。これが起こるのは、Javaが`-XX:+UseParallelGC`付きで動くときだけである。そうでなければ、TLCの最初の警告はそのフラグを渡すよう勧める助言であり、それは一回しか出力されない。

## 図を見せる

`chart.mmd`を、`mermaid`のコードブロックとして利用者に見せる。図の上限は、書かれたままの設定ファイルでTLCが数えた500状態である。それを超えると、図は破れるルールへの経路だけを描き、破れるルールがないときは、コマンドは`chart.mmd`を書かない。それでも各ルールは確かめ、レポートは状態の数と各不具合の経路を示す。グラフ全体を見るには、モデルを小さくする。

図はPeleで描画する。利用者が画像を求めたとき、または図が大きすぎて文字として読めないときは、`references/render.md`に従う。利用者に頼まれない限り、別の描画ツールは使わない。

## 引き渡す

各図とそのMermaidのテキストを、判断する人に渡す。不具合ごとに一行を足す。ルール、そのルールについての読み手の文、レポートが番号を振った経路である。モデルが外していることを言う。新しい`--out`フォルダを指定して、ファイルを作り直すコマンドを示す。

モデルがコードを表すときは、各不具合の経路を、テストか実際の再現として、動作ごとに一歩ずつ実際のコードに対して再生する。不具合が起こらなければ、そうでないと示すまでは、モデルが誤っていると考える。
