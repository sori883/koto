# Show me your work

正本のログを一つだけ持つ。

## 形式

TSVファイル一つで、判断ごとに一行とする。セルは一行に収める。証拠は文章ではなく、指し示す先である。

きれいなログを始めるには、`references/decision-log-template.tsv`（見出しの行）を写す。列は次のとおり。

- **ts.** ISO8601のタイムスタンプ。
- **phase.** フェーズまたは作業の流れ。
- **decision.** 何を選んだか、何をしたかを一行で。
- **why.** 理由を平易な言葉で。原則に基づく判断なら、専門用語のタグではなく、平易に言う。
- **evidence.** それを証明するリンクかパス。コミットのSHA、PR番号、`file:line`、成果物・トレース・スクリーンショットのパスである。段落にはしない。
- **result.** 結果または述語の状態。`tests green`、`reverted`、`pixel-diff 0`、`INCONCLUSIVE`、`open`など。

例を示す。レビューする人がひと目で読めるよう、平易に書いてある。

```
ts	phase	decision	why	evidence	result
2026-05-24T09:02:00Z	frame	先に作業量を数えた。約100コンポーネント、およそ75時間	長い実行を始める前に大きさを知りたかった	commit 3a9f1c2	始める前に片付けることが5つ見つかった
2026-05-24T09:40:00Z	harness	何も変える前に古い版のスクリーンショットを撮った	古い版と新しい版を比べて見た目の変化を捕まえるため	scripts/snapshot.sh, baseline/	基準のスクリーンショットを120枚保存した
2026-05-24T11:15:00Z	widget	見た目を変えずにwidgetのスタイルを移した	変更を小さく、結果を同一に保つ	commit 7c21e0a, pixel-diff 0	見た目は同一、テストは通る
2026-05-24T12:30:00Z	widget	補助の担当のスクリーンショットが空白だったので、その作業を捨てた	要約を信じずに実際のファイルを確かめた	worktree reset	取り消し、次回に向けて指示を厳しくした
```

## 行を記録する

各行は、チームの仲間に何をしたかを話すように書く。平易な言葉と具体的な行動で書き、AIっぽい言い回しや抽象的な専門用語は使わない（**unslop**スキルはログの文にも適用する）。

補助スクリプト`scripts/log.sh <logfile> <phase> <decision> <why> <evidence> <result>`を使う。これは`ts`を刻み、最初の使用時に見出しを書き、紛れ込んだタブや改行を取り除き、`=`、`+`、`-`、`@`で始まるセルの先頭にシングルクォートを付ける。素の`printf`で行を追記してもよいが、セルが生成された文や利用者の入力した文から来るときは、同じバイトに気をつける。

記録するのは判断の分かれ目と区切りであって、すべての操作ではない。選んだ分岐、検証の結果を添えた完了した単位、きっかけを添えた方針転換や取り消し、表に出た障害、直した関門である。ループの実行では、繰り返しごとに一行とする。些細なことや自明なことは省く。

一つの実行とは、一つのエージェントの会話であり、その後のターンと、その会話の要約を含む。引き継ぎ、代わりのエージェント、新しいチャットは、新しい実行を始める。すでに行のあるログに実行が追記するときは、その最初の行のphaseを`start`にする。別の実行の`start`行の後の最初の行も同じにする。そのため、後のターンでログに戻ってきた実行は、まずログの最後の数行を読み、その間に別の実行が書いたかを確かめる。`start`行は、その前にある行のうちこの実行が書いていない行の`ts`の範囲を挙げ、evidenceにはこの実行を挙げる。エージェントIDなどである。phaseの`start`はほかの用途に使わない。

## 置き場所

既定では、ログはコミットしない作業用の成果物である。作業フォルダの`decisions.tsv`に置くか、複数の作業が同時に進むときは`.audit/<task-slug>.tsv`に置き、gitに入れない。

コミットするのは、作業が大きく、レビューする人が結果を信頼するために記録を必要とするときだけにする。

## 規則

- 追記のみ。誤った判断には、それを置き換える新しい行を書く。履歴を編集・削除しない。
- 手作りのその場限りのものより、コミットしたスクリプトが作った証拠を優先する（**encode-lessons-in-structure**原則スキル）。

## ログを会話記録と照合する

実行の終わり、引き渡す前に、ログが真実を伝えたかを確かめる。この実行のClaude Codeの会話記録（`~/.claude/projects/<作業フォルダのパスを変換した名前>/<セッションID>.jsonl`。サブエージェントの記録はその`<セッションID>/subagents/`の下）を読む。`~/.claude/projects/*/`をまたいでglobしない。無関係な個人的な会話を読むことになる。この実行の行を、実際に起きたことと照らして順にたどる。行のそれぞれのまとまりは、この実行の`start`行のどれか、またはこの実行がログを作った場合は最初の行から始まり、別の実行の次の`start`行で終わる。

- 各行が、実際の判断や操作に対応していることを確かめる。
- 各行の証拠がたどれ、行の主張を示していることを確かめる。
- 作業を形づくったのに記録されていない分岐、方針転換、捨てた方法は、抜けである。追加する。

話ではなく、ログを直す。照合では、作り話の行であっても、行を編集・削除しない。行が実際の判断も実際の操作も記録していないとき、またはその主張や証拠が誤っているときは、実際に起きたことと、たどれる指し示し先を書いた、それを置き換える行を足す。この照合は、この実行のまとまりの外の行は確かめない。この実行自身の作業から、そのどれかが誤っていると分かったときは、ほかの誤った判断と同じように置き換える。

## 別系列のモデルによる記録のレビュー

引き渡す前に、作業をしたモデルとは別系列のモデルでサブエージェントを起動する。自分によるレビューは代わりにならない。サブエージェントは監査の記録と実行の会話記録を読み、利用者が注意すべき点を挙げる。作業のやり直しではなく、最適でないものや危ういものを探す点検である。各サブエージェントの推論の水準は、**koto-mode**スキルの「サブエージェント」の節に従って、仕事に合わせて選ぶ。

- 証拠が弱い、またはない判断。
- 飛ばされた、または会話記録に証明なく主張された検証の手順。
- 振り返ると危うく見える選択（早すぎる、範囲を広げすぎる、症状を覆い隠す）。
- 利用者がざっと見ただけでは見落とす抜け。

記録を作った実行への返答は、すべて「Attention」の節で終える。最初の行にレビューしたモデルを単独で書き（`reviewed by <model>`）、その後に各指摘を、具体的な行や場面を指して挙げる。「No flags」は正しい値である。モデル名は省けない。

## 記録をレビューする

上から下へ読み、証拠の指し示し先をたどり、抜き取りで確かめる。GitHubは、コミットされたTSVを表として表示する。端末では`column -s$'\t' -t decisions.tsv`で表示できる。

## このスキルを組み合わせる

ほかのスキルは、監査の記録を自分で作らず、ここに回す。名前で参照し、形式はこのスキルに任せる。列を書き直さない。
