# 形式検証スキルを保守する

形式的な確認は、それが表すものの性質を証明する。コードが変わって検証が変わらなければ、もう存在しないコードを表したまま、確認が通り続けることがある。その通過がもっとも危ない。証明のように見えるからである。このスキルは、`/koto:create-formal-verification-skill`が作った検証スキル、または名指ししたコードに対してモデル検査器・証明器・コードレベルの検証器を実行する任意のプロジェクト専用スキルを保守する手順である。プロジェクト専用スキルは、エージェントがそのスキルを使いながら行う変更を扱う。このスキルは、それを通らなかった変更を扱う。マージ、スキルを使わずに行った編集、多くのコミットにわたって積もったずれである。

## 結果

確認ごとに結果を一つ決め、それを言う。

- **in sync**：前回の同期以降、確認が表すものを変える変更がなく、確認が通る。
- **updated**：コードが変わり、検証が新しいコードを表すようになり、確認が通る。
- **bug**：検証が現在のコードを表しており、そのコードが性質を破る。これはコードについての発見である。ずれではない。
- **blocked**：確認をコードに合わせ直せなかったか、実行できなかった。理由を正確に言う。

確認は、updatedとbugの両方になりうる。更新で検証が再びコードを表すようになり、その上で性質が失敗する場合である。

## 編集の範囲

編集するのは検証だけとする。モデル、ハーネス、性質のファイル、検証スキル自体である。利用者に頼まれない限り、実行中に製品のコードを編集しない。現在のコードで性質が失敗したとき、通すために性質やモデルを弱めない。失敗を報告する。

## 手順

1. **確認を探す。** 検証スキルには決まった名前がないので、何をするかで探す。名指ししたコードに対して、モデル検査器、証明器、またはほかの検証器を実行するプロジェクトのスキルである。見つけたものをすべて読むか、利用者が挙げたものを読む。確認ごとに、性質、対象のコード、上限と前提、実行するコマンド、コードを表していると最後に確かめたコミットを集める。検証スキルがなければ止まり、`/koto:create-formal-verification-skill`を案内する。スキルに同期コミットの記録がなければ、検証のファイルを最後に変えたコミットを使い、そうしたと言う。

2. **そのまま実行する。** 何かを変える前に各確認を一度実行し、結果を記録する。ここで通っても、コードが正しいとは分からない。古い記述がまだ成り立つと分かるだけである。ここでの失敗は、ずれのことも不具合のこともある。手順5まで、どちらかを決めない。

3. **対象のコードへの変更をすべて読む。** 同期コミットから現在のコミットまで対象のファイルの差分を取り、各コミットメッセージを読む。移動したコードも探す。名前が変わった、分割された、別のファイルへ移った対象の関数は、まだ対象のコードである。確認が守る状態に触れる新しいコードも探す。同じフィールドに書く新しい関数などである。変更ごとに、次のどれにあたるかを決める。
   - **影響なし。** 変更は、検証が表すものを何も変えない。書式、コメント、検証の対象外のコードの経路などである。これはコミットメッセージではなく、モデルやハーネスに照らして確かめる。
   - **検証がもうコードを表していない。** 分けられない一つの動作だった手順が二つになった、分岐が足された・消された、確認が移った、守られた状態に届く新しい経路ができた、値の範囲が変わった、などである。モデルかハーネスを変えなければならない。
   - **約束が意図して変わった。** 変更がコードの約束を変え、それが意図したものだという根拠が変更の中にある。ドキュメントコメント、テスト、変更履歴、コミットメッセージである。性質を変えなければならず、その根拠を挙げなければならない。
   - **約束が破れたかもしれない。** コードが変わり、約束が変わったという根拠がない。その後の失敗は、不具合の候補として扱う。

4. **結果ではなくコードから更新する。** モデルかハーネスを変え、変わった部分がそれぞれ再びレビューする人が開けるコードを指すようにし、コードの分けられない一つの手順を、検証でも一つの手順に保つ。更新は再実行の前にコードから書き、確認を通すものに合わせて形を決めない。性質を変えるのは、意図して変わった約束についてだけとする。古い文言、新しい文言、根拠を書き留める。変更で上限が誤りにならない限り、上限は保つ。上限を下げなければならないときは、報告でそう言う。

5. **再実行し、各結果を判断する。**
   - **通過：** 確認は、失敗する力を失った記述の上で通っているかもしれない。性質が防ぐ形で新しいコードを壊し（新しい確認を消す、新しい手順の順序を入れ替えるなど）、確認がそれを捕まえることを確かめる。その後、壊した変更を捨てる。
   - **失敗：** 反例を、実際のコードに対して一歩ずつ再生する。コードで起こりえない手順があれば、検証が誤っている。検証を直し、何が誤っていたかを言う。すべての手順が起こりうるなら、それは不具合である。それを持ち込んだコミットを挙げ、反例をコードの言葉による手順の並びとして伝え、損害を一文で言う。実際のコードに対する安いテストや再現で不具合を示せるなら、証拠として報告に加える。それを製品のコードにコミットしない。

6. **検証スキルを更新する。** 各確認の対象のコード、コマンド、上限、前提、同期コミットを更新する。同期コミットは、確かめたコミットに設定する。blockedの確認の同期コミットは進めず、報告でそう言う。その後、次のエージェントと同じように検証スキルに一度従い、その手順がまだ動くことを確かめる。

## 報告

確認ごとに、利用者に次を伝える。

- 結果と、読んだコミット。
- 検証で何がなぜ変わったか。変更ごとに短い理由を添える。コードの形が変わった、または約束が意図して変わった（根拠を添える）。
- 再実行の結果と、更新した確認がまだ失敗できることを示すために使った壊し方。
- 各不具合を平易な言葉で。コードの言葉による手順としての反例、損害、それを持ち込んだコミット。
- 検証がまだ対象としていないこと。対象とすべきなのにしていない新しいコードを含める。

どの失敗が検証のずれで、どれがコードの不具合かをはっきり言う。更新前に通り、更新後に失敗する確認については、古い通過は古くなった記述の上でのものだったと言う。

検証の更新は、製品の修正とは別の変更にまとめる。
