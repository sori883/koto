# 全体フロー

工程は仕事の種類、タスクは目的と完了条件を持つ実施単位として扱う。一つのタスクで必要な工程を選び、成果物と証拠を渡して進める。工程ごとのファイル作成や担当交代は必須ではない。

## 1. 依頼の終了地点を決める

[依頼整理](intake.md)で目的・範囲・受け入れ条件・終了地点を整理する。既存の決定と承認は引き継ぎ、未決事項を調査で解消できるものと、ユーザーの判断が必要なものに分ける。同じ確認を繰り返さず、回答に依存しない作業を進める。

| 依頼 | 終了地点と工程の選び方 |
| --- | --- |
| 調査・説明 | 根拠を調べて回答する。変更・記録の保存を追加しない |
| 設計・計画のみ | 必要な調査から案と計画を作り、整合性と未決事項を確認して渡す |
| 機能追加・仕様変更 | 利用例と境界を決め、実装し、実経路で確認する |
| 不具合修正・性能改善 | 再現・測定条件と基準値を残し、原因に対応した変更を同じ条件で確認する |
| リファクタリング・移行 | 保つ振る舞い・互換性・失敗時の復旧方法を決め、統合後まで確認する |
| 文書・スキルの変更 | 読者・適用条件・参照先を確認し、形式と内容・動作を分けて検証する |
| レビュー・検証のみ | 該当工程から入り、指摘や判定と限界を返す。修正を追加しない |

読み取り専用の依頼では、TasksやMemoryへの書き込みも行わない。記録の保存が別途依頼されている場合はその範囲だけ保存する。利用先で読むよう指定されたルールと、Memoryの関連するrule・principle・decisionを確認する。未取得を参照済みとせず、読むためだけに初期化しない。

## 2. 作業の現在地を決める

開始・中断・再開・完了の具体的な受け渡しは[ツール間の手順](tools.md)に従う。共有するのは管理ルート、project_id、task_id、必要なrepository_idと参照先であり、各CLIの管理ファイルを直接編集しない。

| 場面 | 次へ進むために確認すること |
| --- | --- |
| 新規開始 | 対象と完了条件をTasksへ記録し、必要な知識と作業場所を確認してstartする |
| 継続 | 最新のtask show、依存先の有効性、実際の作業場所を確認する |
| 中断 | 実作業の停止状態と再開に必要な情報を確認し、Tasksのpausedとcheckpointを記録する |
| 再開 | [recall](../../recall/SKILL.md)から現在地・記録との違い・残件・再開条件を受け、続行かやり直しかを決める |
| 完了 | 依頼された成果と確認がそろい、必要な知識・成果物の記録を終えてcompleteする |
| 片付け | 依頼範囲を確認し、monorepoの保護条件を満たす作業場所だけ整理する |

recallによる状況説明、CLIの操作成功、タスクのcompleted、成果の合格、Gitへの保存・公開は別々の結果として確認する。

## 3. 規模とリスクから工程を選ぶ

| 規模 | 目安 | 記録の形 |
| --- | --- | --- |
| 小規模 | 一つの結果に収まり、方法がほぼ既知 | Tasksのdescription・resultと成果物参照で足りる。task.mdを必須にしない |
| 標準 | 調査・設計の結果を後の工程へ渡す必要がある | Tasksを入口に、必要な設計・計画・検証資料を添える |
| 大規模 | 独立した成果物・担当・納品単位が複数ある | Tasksに作業単位と依存を置き、全体計画で担当・受け入れをまとめる |

行数や経過時間だけで規模を決めない。新たな影響や依存が見つかったら、工程の選択と理由を見直す。変更を伴う仕事や、追跡・中断再開を求められた仕事はTasksを使う。回答だけで終わる読み取り専用の仕事は会話で完結できる。

工程は「実施」「前後の工程へ統合」「既存成果物を再利用」「理由を示して省略」から選ぶ。依頼整理・成果物に合う検証・結果の報告は短くても行う。再利用する資料や証拠は対象・版・条件が今回に適合するか確認する。

- 公開API・利用者の操作・永続データ・責務境界を変える場合は、利用例・互換性・影響範囲を設計する。
- 新しい構造を決める場合は[設計](design.md)で複数の構造を比較する。既知の局所変更や適合する既存設計の再利用では、不足がある部分だけ調べる。
- 複数の作業単位がある場合は、順序・依存・担当・検証の区切りを計画する。
- データ損失や戻しにくい移行など、影響が大きい変更では失敗条件・復旧方法と独立レビューを検討する。必要な確認を利用できなければ不足と限界を示す。

## 4. 成果物を渡して進める

基本は依頼整理から必要な調査・設計・計画へ進み、変更が依頼されていれば実装する。現在の成果物を検証し、必要なレビューを通して引き渡す。失敗時は原因に関係する工程へ戻る。レビューのみ・検証のみの依頼はその工程から始める。

| 工程 | 入力と受け渡す成果物 | 次へ進む条件 |
| --- | --- | --- |
| [依頼整理](intake.md) | 依頼 → 目的・範囲・受け入れ条件・工程 | 期待する結果と権限、未決事項が分かる |
| [調査](investigate.md) | 対象と問い → 事実・根拠・再現条件・未確認事項 | 次の判断に必要な事実と限界を説明できる |
| [設計](design.md) | 要件と調査 → 利用例・構造・比較・採否の理由 | 境界と不変条件、実装を左右する前提が分かる |
| [計画](plan.md) | 設計と完了条件 → 作業単位・依存・担当・確認方法 | 前提が成立し、循環依存や重複する書き込み担当がない |
| [実装・編集](implement.md) | 担当範囲と条件 → 変更・局所検証・差分 | 検証に必要な変更がそろい、設計との差を説明できる |
| [検証](verify.md) | 成果物と条件 → 実測結果・証拠・判定 | 変更を先へ進める範囲の必須条件を満たす |
| [レビュー](review.md) | 差分・理由・証拠 → 指摘・対応・残る条件 | 必須の指摘が解消し、未確認事項を識別できる |
| [引き渡し](deliver.md) | 成果物と確認結果 → 結果報告・知識・依頼された納品 | 求められた終了地点へ到達している |

検証・レビューのみなら、不合格や未確認を含む報告が成果物となる。その報告の完了を、対象の合格・修正完了・公開承認に置き換えない。必要な修正や検証の実施まで求められた場合は、未達を報告しただけで完了にしない。

実装と検証は小さく往復する。必要な確認が通った後、対象の変更・新しい失敗・未解決の懸念がなければ同じ確認を繰り返さない。設計・計画のみの依頼では、見直しもその成果物の範囲に保つ。

## 5. 専門手順を選ぶ

| 必要な仕事 | 接続するスキルと渡す情報 |
| --- | --- |
| 作業の現在地を復元する | [recall](../../recall/SKILL.md)へ管理ルート・project・taskと、既存の記録・対象期間を渡す |
| 影響する利用側や安全性の前提を調べる | [blast-radius](../../blast-radius/SKILL.md)へ差分・版・気になる境界・許可された診断を渡す |
| 局所テストで再現できる不具合を直す | [tdd](../../tdd/SKILL.md)へ再現条件・期待する振る舞い・対象の版を渡す |
| 複数の独立した担当でレビューする | [interrogate](../../interrogate/SKILL.md)へ同じ対象・意図・基準・証拠を渡す |

全専門スキルを毎回呼ばない。実装の細かな手法は必要な専門スキルに任せ、工程側は入力・期待する成果・判定・失敗時の戻り先を持つ。利用できない手順や独立担当を実行済みとせず、満たせない条件を明示する。

複数の担当へ渡す場合は[担当の受け渡し](delegation.md)、タスク間の依存や成果の集約は[複数タスクの管理](orchestrate.md)を読む。固定名の専用エージェントや特定モデルを前提にしない。

## 6. 記録を三つの役割で残す

### タスクの状態と成果物

最新の状態・version・attempt・依存・成果物参照はTasksの記録を正本とする。説明や計画が長い場合だけtask.md等の資料へ分け、Tasksのartifactから参照する。Markdownへ第二の最新状態を維持しない。

新しい資料の保存先は、指定がなければ `.space/<project>/tasks/<task-id>/`。task.md、design.md、plan.md、verification.md等を必要な分だけ置く。Tasks CLIは成果物本文を保存しないため、担当がファイルを作成・確認してから参照を登録する。[タスク記録](../assets/task-template.md)・[設計](../assets/design-template.md)・[計画](../assets/plan-template.md)・[検証](../assets/verification-template.md)のひな形は必要な節だけ使う。

### 中断と再開

Tasksのcheckpointは保存時点の要約とスナップショットであり、現在の状態やコードのバックアップではない。中断・引き継ぎに必要な時点で保存し、工程が終わるたびの作成は求めない。最新の状態と実体の照合はrecallが行う。

### 長く使う知識

[Memory](../../memory/SKILL.md)で関連する既存知識を検索し、重複を確認してから更新・作成する。原則として引き渡しで、後の仕事に役立つ確定した仕様・判断・手順と根拠を保存する。設計の採用と実装済みの状態を区別し、一度の経験を自動的にrule・principleへ格上げしない。

現在の仕様はknowledge、採否と理由はdecision、再利用できる手順はprocedureが目安。検証ログ全文、途中の候補、TODO、checkpointはタスク側に保つ。Memoryの本文だけで内容を理解できるようにし、対象の版・成果物・証拠を参照する。

保存・検証に失敗した場合は、未完了の操作と理由をTasksへ残し、元の記録を保持する。今回必要とした知識保存が未完了なら、すべて完了したと報告しない。記録の保存を依頼されていない読み取り専用の仕事では、知識化候補を回答に留める。

## 7. 状態の変更と終了を扱う

### 進捗の更新者

単独なら作業担当がTasksを更新する。複数担当なら各task_idの更新責任者を決め、同じタスクや共有資料への並行書き込みを避ける。成果物の所有範囲と報告先は計画・タスクのdescriptionへ明示する。担当からの報告を実際の成果と照合して受け入れ、報告だけで全体を完了にしない。

### 状態と完了の判定

Tasksの状態はpending・running・waiting・paused・completed・cancelledを使う。各工程名や成果の合否は状態名に追加しない。task showのblockedBy・completionCurrentと実作業を照合し、依存先のやり直しを無視して進めない。start・set・reopen・completeの適用条件と再送は[Tasks](../../tasks/SKILL.md)へ委ねる。

依頼全体を完了にする前に、残る作業単位・必要な検証・成果物・知識保存・依頼された納品を確認する。中断や前提待ちはその理由と次の操作を記録する。タスクの完了はWorktree削除やブランチ・履歴の削除を意味しない。
