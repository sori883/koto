# 設計判断を記録してレビューする

## 使う場面

長く参照する設計判断をMemoryの `decision` として残すとき、既存の判断を見直すとき、その本文をレビューするときに使う。書き手とレビュー担当は以下の同じ基準を使う。進捗や検証ログはタスク側、確認できた現在の仕様・構成は `knowledge`、操作方法は `procedure` に置く。

## DR-1：今回の判断を本文だけで理解できるようにする

何を決めたかをタイトルと冒頭で示し、対象で実際に確認した問題、なぜ今判断が必要か、適用範囲と守る条件を書く。一般論や関連資料へのリンクだけで背景を済ませない。確認した事実と仮定を区別する。

決定に含めない事項が読み手の判断に影響するなら、その範囲と扱う資料・工程を示す。未作成の資料は未作成と書き、存在する正本として案内しない。一時的な例外には適用条件と、いつ・どの条件で見直すかを添える。

## DR-2：判断と実装の説明を分ける

本文には、選んだ方針、責務・境界、重要な制約と理由、実際に検討した代替案の採否を残す。得られる効果だけでなく、受け入れる負担・制約も書く。期待する効果を、既に観測した結果として書かない。

迷ったら「この細部を変えても、採用した方針と理由は成立するか」を確認する。成立するなら、その細部は仕様・設計資料へ分ける。技術や保存形式そのものを選ぶ判断では、具体名と理由が必要になる。名称やコードを一律に禁止しない。

| 記録する内容 | 置き場所 |
| --- | --- |
| データの所有者、互換性の条件、採用技術と選択理由 | decision |
| 現在の関数・設定項目・データ構造の説明 | 仕様・構成資料、必要に応じてknowledge |
| 作業順序、担当、期限、チェックリスト、試行中の候補 | タスクの計画・設計資料 |
| 実行コマンドや復旧操作 | 手順書、必要に応じてprocedure |

作例：decisionには「読み手を同時に更新できないため、移行中は旧形式を読めることを互換性の条件とする」と残せる。「変換関数の名前を変え、金曜までに3件の作業を終える」は実装資料と計画へ分ける。

## DR-3：決まったことと確認できていないことを分ける

本文に判断の状態（採用・見送り・撤回・後継へ置換など）と、その根拠になる記録・時点を示す。検討中の候補は作業側に保ち、未決の判断を採用済みとして保存しない。根拠から確認できない決定者・日付・承認は補わない。

判断時点の実装確認の有無は短く示せるが、その後の進捗表は持たない。採用の根拠と実装の証拠は別に扱う。過去の判断を調べて理由だけが不明なら、確認できた判断と理由の不明点を残す。実装からの推測だけで合意済みの判断を作らない。

OKFのfrontmatterの `status` は文書の状態であり、値は `draft`・`stable`・`deprecated` を使う。ADRの採用状態を表す独自の値で上書きしない。`stable` や形式検証の成功は、人間の承認・実装完了を意味しない。`verified` は実際の人間の確認がある場合だけ記録する。

## DR-4：根拠を後から確かめられるようにする

判断を左右する事実は、対象のコード・設定・一次資料と照合する。本文の主張と出典を対応付け、参照した版と確認時点を残す。コードはパスとシンボル、文書は題名と節名などを併記し、可変の行番号や「前述の資料」だけに頼らない。

出典の一覧は `sources`、関連するコードは `code_refs` にも記録できる。出典が存在していても、その主張を裏付けるとは限らない。会話や会議の内容は確認できる記録を参照し、取得できないものは限界を明記する。推論には根拠と不確実性を添える。

## DR-5：判断の変更をたどれるようにする

誤字の修正、根拠の補足、同じ判断の説明改善は同じconcept IDを更新する。採用方針を変える場合は、変更理由を持つ新しいdecisionを作る。旧本文の当時の判断と理由を残し、旧・新の両方から相手をたどれるようにする。

旧記録には置換された範囲・時点を追記する。一部だけの変更なら、今も有効な範囲を残す。判断全体を現行の指針として使わなくなった場合は `status: deprecated` とし、本文でも撤回・後継への置換などの理由を説明する。置き換えのために旧記録を物理削除しない。

Memory CLIで作成・更新・関連付けを行い、目次の同期、旧・新の相互参照、関係する構成文書からの案内を確認する。複数文書の更新が途中で失敗した場合は、保存済みの範囲と未完了の関係を報告する。

## 本文の出発点

次の項目を短い本文にまとめる。小さな判断は一段落でもよく、見出しを埋めるために情報を作らない。

- 判断と状態：何を選んだか。採用等の根拠と時点。判断時点での実装確認の有無。
- 背景と範囲：実際の問題、制約、適用範囲、必要なら対象外・例外の条件。
- 理由と代替案：選択理由と、実際に検討した案を見送った理由。
- 影響：利点と代償。予測・観測・不明点を区別する。
- 根拠と関連する判断：出典、対象の版と確認時点、旧・後継の判断への参照。

## レビューと保存後の確認

DR-1〜DR-5を対象に応じて確認する。指摘には基準IDだけでなく、該当箇所、読み手が誤解する内容、修正理由を添える。章立てや語彙の好みだけを不合格理由にしない。

必要な保存の前に本文と根拠を照合し、保存後は読み返しと形式検証を行う。形式検証が通っても、判断の妥当性や参照先の主張まで検証されたことにはならない。レビューだけの依頼では保存・状態変更をしない。
