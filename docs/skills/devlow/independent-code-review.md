# コードの種類ごとの独立レビュー

2026-11-12のユーザー承認に基づく変更。従来は小規模変更を作成者の自己確認に統合できたため、テストや本体コードを書いた後に別エージェントが確認する保証はなかった。開発手順として独立レビューを必須にし、仕様が未決の場合の戻り先も明確にした。

## 定義の所有先

- `skills/devlow/references/workflow.md`：対象・時点・人数・未実施時の扱い。コード変更は小規模でも対象とし、通常1人、影響が大きい場合は複数担当とする。
- `skills/devlow/references/review.md`：担当への入力、指摘の採否、修正後の独立した再確認、区切りごとの判定。1人レビューもinterrogateの担当用プロンプトを使う。
- `skills/interrogate/references/reviewer-prompt.md`：テスト・本体・設定や移行用コードの確認観点。TDDで意図した失敗を評価する条件、仕様を推測しない条件。
- devlowの入口・実装・計画・検証・受け渡しとtdd：全体フローへの接続。途中のレビューを最終引き渡しと混同せず、同じ対象の確認は再利用する。
- `skills/devlow/references/intake.md`：期待する結果を変える仕様の曖昧さを、調査する事実とユーザーが決める方針に分ける。利用先にgrilling等があれば任意で使い、未導入の場合も依頼整理で進める。
- Codex・Claude Codeの`devlow-worker`：子は途中のレビューを親へ依頼し、親が担当を手配する。レビュー担当は読み取り専用とし、追加の担当を再帰的に起動しない。

レビューの条件・観点を共通Memoryへ重複配置しない。Tasks・Memory CLIの変更、新規の専用エージェント、grillingの同梱、hooksによる強制機構は含めない。作業ログや本記録は配布対象外のdocsに置く。

## 手順の静的照合

以下は手順本文を各ケースに当てはめた確認であり、実際のクライアント上でエージェントを起動した結果ではない。

| ケース | 確認した経路と判定 |
| --- | --- |
| 本体コードを一行だけ修正する | 規模による省略はせず、局所検証後に独立担当1人へ渡す |
| TDDで失敗するテストを書く | 意図した失敗と期待値をレビューし、本体修正に進める判定を得てから修正する。本体の成功をテストレビューの前提にしない |
| テストレビューで指摘を受ける | 作成者がテストを修正し、再び失敗の理由を確かめ、独立担当が再確認する |
| テストだけを変更・削除する | 検証の根拠に使う前に確認し、削除で失う確認範囲も対象にする |
| 通常の機能追加で本体とテストをまとめる | 同じまとまりを種類ごとの観点で一度にレビューできる。TDDの事前レビューはこの一括確認で代用できない |
| 子エージェントがTDDを担当する | 親は最終報告だけでなく途中の依頼も受け、独立担当からの判定を子へ返す。子と親が重複して担当を起動しない |
| 移行や設定で既存データに影響する | 互換性・部分失敗・復旧を確認し、影響が大きい変更は複数担当へ渡す |
| 仕様の二つの解釈で期待値が変わる | 確認待ちとして依頼整理へ戻す。コードで分かる事実は調査し、方針だけユーザーに確認する。確定後は影響する検証・レビューを更新する |
| 同じ仕様を満たす実装が複数ある | 仕様の曖昧さとは扱わず、不要な方針確認を追加しない |
| 別エージェントを利用できない | 独立レビュー未実施とし、依存する作業や合格判定を待つ。独立した調査や途中経過の報告は可能 |
| レビュー後に変更する／同じ成果物を渡し直す | 変更した範囲と前提への影響を再確認する。同じ版・差分・条件の結果は再利用する |
| レビューだけを依頼する | 指摘と限界を返して終了し、対象の修正や追加のレビュー担当の起動へ広げない |

### 追加した手順の静的照合

次のケースを手順本文に当てはめた。実際のエージェントによる判定の実測とは区別する。

| ケース | 手順上の扱い |
| --- | --- |
| 合意した仕様と現行実装の実測結果が異なる | 根拠の種類と条件を照合し、現状の動作に合うよう期待値を変えず、調査・依頼整理へ戻す |
| 期待値が未確認の仮説だけに基づく | 合否の確定根拠にせず、調査・依頼整理へ戻す |
| 保存操作は成功するが、後続の取得で値が消えている | 応答だけで合格にせず、操作後の状態と一連の利用の不一致を扱う |
| 作成操作を拒否したのに対象が残る | 失敗時に許されない状態変化として確認する |
| 部分成功が仕様として認められている | 全件の巻き戻しを要求せず、残ってよい状態と保持すべき状態を確認する |
| 削除後も一覧に対象が残る | 一連の利用で結果が引き継がれない問題として確認する |
| 状態を持たない変換処理を変更する | 作成・削除等の一連の操作を形式的に追加しない |
| TDDの本体修正前にテストをレビューする | 既存のRedを評価する条件を維持し、仕様の根拠とテストの検出力を確認する |
| 読み取り専用のレビューを依頼する | 証拠を照合し、未実施の操作を実行済みにしない。外部環境の操作を自動追加しない |
