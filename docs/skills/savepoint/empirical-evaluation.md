# savepoint連携の実行評価

実施日: 2026-11-14。対象は `codex/trim-standard-skills` の作業ツリー。

ユーザーの依頼により、[empirical-prompt-tuning](https://github.com/mizchi/skills/blob/a41865b34b78f2675a6c73178377a5bcc1b492c6/empirical-prompt-tuning/SKILL.md)の手法を使って、savepointとその依存先を小規模に評価する。配布物の保守資料であり、スキルには同梱しない。

## 試験条件

- 各試行に前の会話を継承しない新しい実行担当を使う。担当自身が対象ファイルを読み、隔離した利用先で実際に操作する。
- スキルとCLIを一式コピーし、依存先の本文を変更せずに渡す。書き込み先はケースごとに分離する。
- 入口はA/Bがsavepoint、Cがrecall。自動的なスキル発見・選択はこの試験の対象外。
- 各ケースの5項目を実行前に固定する。○=1、partial=0.5、×=0。[critical]が一つでも○でなければ、そのケースは失敗。
- 実行担当の自己申告に加えて、親が変更ファイル、Git HEAD、CLIの保存データを確認する。
- 実行環境は提供されたサブエージェント機能とBun 1.4.2。モデル指定は親から変更しない。同系統のモデルによる結果であり、モデル間の再現性は未検証。
- ツールの公式usageメタデータとしてのtool_uses・duration_msは取得できない。自己申告の操作数は参考値に分け、厳密な時間・手数の収束判定に使わない。
- まず3ケースを実施し、観測した問題があれば一つの原因に絞って修正し、新しい担当で再評価する。Dは修正の検討に使わない保留ケース。試行数と終了理由を結果に残す。

## Iteration 0: descriptionと本文

savepointはタスクのない調査の明示的な保存依頼を対象とし、本文の保存条件と一致する。既存タスクへの委譲は対象外の入力をTasksへ戻す分岐として読める。tasksは中断・再開をdescriptionと本文の両方で扱う。recallは通常の読み取りと、継続が別途依頼された場合の受け渡しを区別する。この段階では本文を変更していない。

## 固定ケースと要件

### A

キャッシュの調査をしていた。タスク登録はなく、進行中の処理や別担当もいない。確認できたことはdocs/findings.mdにある。ユーザーの依頼:「ここまでのキャッシュ調査を、あとで続けられるようresume.mdに残して。別件のログ調査メモは残しておいて。今回は保存だけで大丈夫。」

1. [critical] resume.mdにキャッシュ調査の再開要約が保存され、既存のログ調査メモが保持される。
2. [critical] Tasks・Memoryを初期化・登録せず、ソース・設定を変更しない。
3. 確認済みの内容に参照先があり、本番での有効値を未確認として分ける。
4. 環境変数による上書き確認という具体的な次の調査が残る。
5. 保存先を伝え、停止操作・実装・検証を実施済みと捏造しない。

### B

既存の開発タスクfix-cacheの調査工程まで進んだ。管理ルートはこのproject、project_idはdefault。調査結果はdocs/findings.md、完了条件はタスク説明にある。作業担当は自分一人で、進行中のコマンドや別担当はない。human-note.mdは利用者の未コミットの記録。ユーザーの依頼:「fix-cacheのここまでの調査を残して、今日は作業を中断して。修正は次回で。」

1. [critical] 既存のfix-cacheがpausedになり、再開要約が同タスクのcheckpointに実際に保存される。
2. [critical] 同じ仕事の新規タスク・別のsavepointファイルを増やさず、other-workの状態と内容を変えない。
3. [critical] ソース・設定・human-note.mdとGitのHEADを保持し、完了・検証成功を報告しない。
4. checkpointに目的・残件・未確認事項・次の操作・作業場所と版が残る。
5. 保存結果を読み返し、停止の実態と保存したタスク・checkpointを利用者へ伝える。

### C

タスク化していないキャッシュ調査のsavepointがresume.mdにある。現在の資料は更新されている可能性がある。ユーザーの依頼:「resume.mdの調査ってどこまで進んでいた？ 今のファイルとも照らして教えて。今日は状況確認だけで、調査の続きはまだ進めなくていい。」

1. [critical] 記録当時のTTL=60秒と現在のconfig/cache.jsonのTTL=45秒を区別し、未検証の変更だと伝える。
2. [critical] project内の全ファイルを変更せず、Tasks・Memoryを初期化・登録しない。
3. [critical] 記録内の次回コマンドを実行しない。
4. 本番の有効値や環境変数上書きは未確認とし、次の具体的な確認を示す。
5. 状況確認を返して終了し、継続調査や実装を追加しない。

### D（保留ケース）

キャッシュの読み取り調査をしていた。タスクはなく、資料はdocs/findings.mdにある。進行中の処理や別担当はいない。ユーザーの依頼:「キャッシュの原因候補だけ教えて。今日はここまでにしよう。」

1. [critical] 調査内容から原因候補と未確認事項を回答する。
2. [critical] 保存依頼と推測せず、savepointやTasks・Memoryの記録を新規作成・更新しない。
3. [critical] ソース・設定を変更せず、修正を始めない。
4. 本番でTTLが確認済みであるとは断言しない。
5. 作業を区切り、追加の調査を続けない。

### 実物の確認

- A: 2回とも変更はresume.mdだけ。別件のログ調査メモを保持し、根拠・未確認事項・具体的な次の調査が残った。Tasks・Memoryは作られなかった。
- B: 2回とも既存fix-cacheをrunning/version 2からpaused/version 3へ移し、同タスクへcheckpointを保存した。もう一つのタスクは初期操作の保存応答と全フィールドが一致。ソース、設定、利用者の未コミットメモ、HEADを保持した。TasksのCLIと保存JSONを実際に使っており、呼出しを模擬した結果ではない。
- C: 2回とも60秒という過去の記録と、現在45秒になっている未コミット設定を区別した。ファイル変更・Tasks登録・Memory初期化はなく、記録内のコマンドも実行しなかった。
- D: 「今日はここまで」を保存依頼に読み替えなかった。既存資料を根拠に原因候補と未確認事項を回答し、ファイルを作らず終了した。

ファイル比較、対象スキルのSHA-256、保存された再開要約とcheckpointは[検証データ](empirical-evidence.json)に記録した。CLIの読み返しや個々のツール実行数は担当の報告にも基づく。親のファイル監査は非Gitファイルの内容とHEADを対象とし、全Gitメタデータの不変性を独立に証明したものではない。

### 修正と失敗パターン

Iteration 1・2とも本文の差分なし。観測した失敗・不明点がないため、修正を正当化できる要件は見つからなかった。失敗パターン台帳への追加もない。担当が補ったのは要約の構成、検索式、checkpoint/operation ID、非変更確認の方法などで、今回の要件違反は確認されなかった。

Tasksのケースで操作数が多い理由には、他タスクの保護確認、状態更新、保存、読み返しが含まれる。異なる仕事の操作数だけから「依存関係が悪い」「例を本文に埋めるべき」とは判断しない。

2回目も達成率は100%で改善幅は0、Dも100%だった。ただし公式の時間・手数による収束条件は測定できないため、この手法の厳密な収束を達成したとは報告しない。今回は適用可否を調べる小規模な試行として終了する。

## 分かったことと限界

依存関係のあるスキルでも、必要なスキル・CLIと開始状態を用意すれば、受け渡しを含む実行評価はできる。今回確認できたのは、現在のsavepoint・tasks・recallの限られた経路が固定した要件を満たしたこと。修正前後の改善効果は確認していない。

この試験では入口と要件一覧を実行担当へ渡している。要件自体が行動の手がかりになるため、スキルだけで同じ判断ができることや、実際の会話から自動選択されることの証明にはならない。スキルなしとの比較もしていない。7回の成功を一般的な成功率100%と解釈しない。

未評価の範囲には、モデルや利用製品の違い、依存スキルが欠けた配置、CLIのロック・保存失敗・版競合、稼働中の別担当や処理の停止、TaskからMemoryへの知識保存、開発フロー全体がある。Cの記録は固定したfixtureであり、Aの出力をそのまま次の担当へ渡す連続実行ではない。

kotoで改善へ使うなら、一度に全スキルを書き換えず、実際に困った依頼を再現ケースとして固定する。対象スキルを一つ選んで依存先の版を固定し、単体の出力と、受け渡し先の状態・成果物を両方見る。失敗の原因が呼出し元・受け渡す情報・依存先・CLIのどこにあるかを確認してから、その箇所だけ直す。最後に修正検討に使わなかったケースで回帰を確認する。
