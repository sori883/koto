# 設計判断の記録・レビュー手順の改善

2026-11-03。ユーザーが提示した[にしこりさぶろ〜氏の記事「AIが書く『読みづらいADR』に発狂しかけたので、ADRのガイドラインを作った」](https://zenn.dev/tokium_dev/articles/adr-authoring-guideline)（2026-11-02公開）を同日に読み、kotoの配布用手順と比較した。

## 確認した不足

kotoは既に、途中の候補・進捗をタスクへ、確定した判断をMemoryのdecisionへ保存する設計を持つ。採用と実装確認の区別、根拠の照合もある。一方、判断を記述する粒度の判定、OKFのstatusと採用状態の区別、判断を変更した際の旧記録の扱いを、書き手とレビュー担当が共通に参照できる手順はなかった。

system-blueprintの「同じ対象・責務は同じIDで更新する」という指示も、現状の構成説明と判断の変更を区別していなかった。そのままでは、過去の判断を新方針で書き換える余地があった。

## 採用した構成と理由

共通手順の正本を `space/default/procedures/record-design-decisions.md` に置く。Memoryが取得方法を案内し、devlowの設計・レビュー・引き渡し、system-blueprintが同じ手順を必要時に参照する。共通文書をMemoryに置く配布設計に従い、各スキルへ基準を複製しない。

本文の出発点と、指摘に使えるDR-1〜DR-5の基準を一つの文書に含めた。基準IDだけの指摘は避け、読み手への具体的な影響も説明させる。作例はkotoの既存判断を引用せず作成した。

CLIとOKFの形式は変更しない。`status` の既存値を保ち、判断の採用状態・根拠は本文に残す。文書の補足・訂正と方針変更を区別し、後者では新旧を相互参照する。部分的な置換と全体の失効も区別する。

独立したADRスキルを作る案は、既存の保存担当との分断と導線の増加を招くため採用しない。Memoryスキル専用の参照資料に基準を置く案も、複数の独立したスキルで使う共通知識は `space/default/` に置く設計に合わせて見送った。

## 記事から一律には採用しなかったもの

- チケットやPRへの本文リンクの全面禁止：kotoは主張の近くに根拠を対応付ける。リンク先を読まなくても判断を理解できる本文にし、出典の追跡は保持する。
- 固定のADR番号・見出し構成：既存のconcept IDと短い本文を使えるようにする。記事固有の番号体系を導入しない。
- 実装方式や具体名の全面排除：採用技術・保存形式自体の選択では具体名が判断の内容になる。方針を変えずに変更可能な細部かどうかで分ける。
- Acceptedなどのstatus値：既存のOKFが認める文書状態とは意味が異なるため、値を追加・置換しない。
- 新しいCIレビューやクライアント固有ルール：今回の改善は既存の作成・レビュー・保存経路へ接続する範囲とする。

記事の規約全文を取り込む変更ではない。既存の設計に不足する判断基準を補い、この記事の紹介や変更経緯・検証記録は配布物へ入れない。

## 内容の確認

自己レビューで次の利用場面と本文を照合し、それぞれを扱う基準と導線があることを確認した。別エージェントによる実行評価とは区別する。

| 利用場面 | 確認する結果 |
| --- | --- |
| 設計判断に期限・担当・タスク表が混ざる | 作業側へ分け、判断に必要な互換性などの条件は残す |
| 汎用的な問題説明とリンクだけがある | 実際の問題・判断の必要性を本文に補い、事実と仮定を区別する |
| 関数名や設定方法の変更だけで判断本文が変わる | 仕様・実装資料へ分ける。技術そのものを選ぶ判断は具体名を残す |
| 未決・未実装・理由不明がある | 未決を採用済みにせず、採用と実装確認を分ける。過去の理由の不明を隠さない |
| 誤字の訂正・一部の方針変更・全面的な置換 | 同じIDでの訂正、新旧の関連付け、旧判断の一部維持・全体失効を区別する |
| 共通手順のない既存導入先でレビューする | 未取得を報告し、別projectの探索・無断setupを行わず、確認できた範囲を返す |

- Codex・Claude Code・Copilotの新規導入先で、Memoryのstrict・drift検証が成功した。既存の利用先文書の保持・再実行・更新と、プロジェクト導入の移動後の動作も既存テストで確認した。
- `bun run typecheck`、`bun run build`、`bun run build:check`、`git diff --check`：成功。配布物は388ファイル。
- skill-creatorの `quick_validate.py`：memory・devlow・system-blueprintの3スキルが成功。システムのPythonにはPyYAMLがなかったため、uvの一時環境で実行した。リポジトリへ依存を追加していない。
- 配布内容を自己確認し、出典の採否・変更経緯・検証記録をこの開発資料へ分離した。

これはローカルの変更・配布検証であり、公開・インストール済みプラグインの更新・各クライアントのAIによる実行評価は含まない。既存の判断文書の移行も行っていない。

## 0.1.9としての公開

同日、ユーザーからmainへのマージと、このMacへの導入を依頼された。版数を0.1.9へ更新して製品別配布物を再生成する。Macの更新対象は、導入済みのCodexプラグイン `koto@koto`。既存のGitマーケットプレイス登録を使ってmainから取得し、設定と有効化状態を保持する。PR・公開結果と導入検証は実施後に記録する。

版数更新後の初回CIでは、開発用Memory CLIが返す版数とルートの版数の不一致を既存テストが検出した。配布物のCLI版数はbuildで一致していたが、正本側のpackage.jsonもMemory・Tasksとも0.1.9へそろえる必要があったため修正した。
