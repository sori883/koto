# Memoryの用途区分とOpsフローの変更計画

状態：実装の依頼を受けて着手。Memoryの全5分類を共有・開発・運用に分ける方針と、本計画による実装をユーザーが了承した。第1段階はPR #27でdevelopへ統合済み。第2段階の実装とローカル検証も完了し、developへの統合へ進む。

対象の基準はdevelopの`d65611ffa2700b8cac042ba0e88ebb8f8ab7984c`。計画作成時は設計資料のみを更新し、その後の実装依頼により作業ブランチで変更を進める。結果は[分類・検証記録](memory-scopes-validation.md)へ残す。

## 1. 到達点

Memoryのrule・principle・knowledge・procedure・decisionすべてに、用途を示す`scope: shared | dev | ops`を持たせる。種類を示すtype、知識の成熟度を示すstatus、制約の強さを示すgovernanceとは独立させる。

| 用途 | 保存値 | 通常参照するフロー |
| --- | --- | --- |
| 共有 | shared | DevフローとOpsフロー |
| 開発 | dev | Devフロー |
| 運用 | ops | Opsフロー |

共有は同じproject内で両フローが使うという意味。別projectへの探索・共有やアクセス権の変更は行わない。scopeは用途の選択であり、OSのアクセス認可ではない。両方に必要な知識はsharedの1文書として保持し、同じ本文をdevとopsへ複製しない。

保存先は既存の`.space/<project>/memory/<分類>/...md`を維持する。scopeの正本はfrontmatterとし、ディレクトリ名やタグから自動推定しない。既存ID・リンクを保ち、用途別ディレクトリへの移動は必須にしない。index.md・log.md・利用イベント・Tasksの管理データは知識文書ではなく、この属性の付与対象にしない。

## 2. 計画作成時の実装と不足

| 対象 | 現状 | 必要な変更 |
| --- | --- | --- |
| 属性 | 任意のJSON互換属性を保存できる | scopeの許容値と書き込み規則を定義する |
| 検索 | 属性の完全一致・不一致・有無で検索できる。複数条件はAND | 共有と対象用途の和集合を1回の検索として扱う |
| 検索結果 | type・governance・tagsなどを返す。任意属性は結果に含めない | scopeを返し、未分類との違いを確認できるようにする |
| 既存知識 | 配布元の`space/default/`には23件の知識文書があり、scopeはない | 内容を確認して分類。利用先のデータは自動移行しない |
| スキル | Memory・devlow・recallなどに用途の選択規則はない | 用途を受け渡し、対応する知識を参照する |

根拠は[属性](../cli/memory/lib/frontmatter.ts)、[検索](../cli/memory/lib/memory.ts)、[条件結合](../cli/memory/lib/filter.ts)、[保存](../cli/memory/lib/mutate.ts)、[検証](../cli/memory/lib/validate.ts)、[指示生成](../cli/monorepo/lib/instructions.ts)。任意属性として保存・個別検索するだけならCLIの追加実装は不要だが、今回の正式な区分・入力検証・共有を含む一括検索はCLIへ持たせる。

## 3. 第1段階：Memoryの区分と既存フロー

### 保存・検証

- scopeは1つの文字列。shared・dev・opsだけを受け付け、配列・null・空文字・未知の値を拒否する。他の任意属性の保存は維持する。
- createでは全5分類でscopeを必須とする。updateでは更新後の文書にscopeを必要とし、分類済み文書では指定を省けば現在の値を保持する。未分類文書の更新には明示した分類を求める。`--unset scope`は拒否する。
- create/updateの`--scope`とJSON入力の`scope`を用意し、metadataのscopeと同じ保存値へ接続する。他の属性フラグと同様に、フラグの明示値を優先する。保存APIでも同じ条件を検査し、CLIだけの制約にしない。
- 既存のscope欠落は読み取り時のエラーにしない。showと用途指定なしのsearchは従来どおり取得でき、未分類をsharedへ補完しない。検索結果のscopeは、未分類なら省略する。
- validateは未分類を警告として報告し、strictでは不合格にする。明示された不正値は形式エラーとする。通常の検索でも壊れた知識を黙って除外して成功しないという既存の扱いを維持する。
- relateで本文を追加する場合はsourceを先に分類する。targetの未分類を自動補完しない。deleteに伴う参照除去、保存済みの復旧予定のrecoverは分類の推測を行わず、既存データの整理・復旧を継続できるようにする。

新しいcreate、および未分類のupdate/relateは以前の入力から変更が必要になる。利用手順・同梱スキル・テスト用データを同じ段階で更新し、この入力互換性の変更を明記する。

### 検索

| 入力案 | 対象 |
| --- | --- |
| `search --scope dev` | sharedとdev |
| `search --scope ops` | sharedとops |
| `search --scope shared` | sharedのみ |
| scope指定なし | 全用途と未分類。既存の読取動作を維持 |
| `search --filter scope=dev` | devの完全一致。共有を含めない棚卸し用 |
| `search --filter '!scope' --all` | 未分類の一覧 |

検索でのscopeは参照する用途を表し、共有を含む範囲へCLIが展開する。create/updateでは保存する文書自身の用途を表す。JSON入力にもscopeを追加し、読み取りAPIのMemorySearchOptionsにも同じ選択を用意する。

用途の選択はtype・語句・属性・code_refsの条件と組み合わせられる。scopeを渡せば検索語の省略も認める。用途と既存フィルタの適用を件数制限より先に行い、無関係な用途が上位を占めて必要な知識が欠けないようにする。検索順位は既存の関連度・governanceを維持し、dev/opsというだけでsharedより優先したり、共有ルールを無効にしたりしない。

検索結果にscopeを追加する経路は、語句検索・分類一覧・属性だけの一覧・コード参照検索の全て。絞り込み後の実際の応答だけを既存の利用ログへ記録し、1回の検索を共有分と用途分の2イベントに分けない。

showは既知IDを指定して読む従来の操作を維持する。スキルは返されたscopeと依頼の用途を照合する。反対用途の知識を通常の根拠へ自動採用せず、用途をまたぐ参照を依頼された場合はその範囲を明示して扱う。

### 既存データとスキル

1. 配布元の23件は本文を確認し、scopeの候補と理由を開発資料へ残す。ファイルの置き場所や「共通知識」という呼称だけで一括sharedにしない。分類できない文書は判断を保留し、配布元の分類を完了するまで第1段階を完了扱いにしない。
2. 配布元は`space/default/`を編集して再生成する。利用先のMemoryは指定されたprojectの未分類を一覧にし、分類が確定した文書だけ通常のupdateとif-hashで移行する。本文・ID・リンク・人間の検証履歴・利用ログを保持し、古いハッシュなら停止する。利用先の一括探索・自動移行は追加しない。
3. Memoryスキルに全5分類の用途判断、新規保存・更新、通常検索、未分類の扱いを集約する。devlowからdevを渡す。専門スキルには呼び出し元の用途を渡し、単独の開発依頼ではdevを選ぶ。用途が分からない仕事を勝手にdevとみなさない。
4. 通常のフロー開始時には、対象に関連する未分類のrule・principle・procedure等が残っていないかも確認する。分類がないため検索から外れたことを「制約なし」「手順なし」の根拠にしない。用途が判断できなければ必要な確認を示し、状態確認だけで分類を書き換えない。
5. recallはTasks・checkpoint・依頼から用途を復元し、必要なMemoryを照合する。通常の読み取り専用を維持し、区分の補完・タスク状態変更・利用ログの追加を勝手に行わない。用途が不明な場合はその不明点を返す。

分類がshared/dev/opsのどれかという事実と、検証済み・最新・適用可能であることは別に扱う。scopeだけで知識を正しいと判断しない。

## 4. 第2段階：Opsフローと運用手順

opsflowを新しいスキルとして追加する。専用CLIや中央の実行エンジンは作らず、Tasks・Memory・必要なmonorepoと既存の操作ツールを使う。

流れは、対象と依頼範囲の確認、共有＋運用の知識と手順の選択、前提・入力の確認、実行、実状態の確認、結果記録、完了または中断とする。開始時と再開時には実状態を観測し、記録済みの手順番号だけで再実行を決めない。既存の承認を引き継ぎ、手順書の存在を作業の実行許可とみなさない。

| 所有するもの | 担当 |
| --- | --- |
| 共通の進め方、ツール間の受け渡し | opsflow |
| 業務固有の操作と判定 | 利用先の運用手順Markdown |
| 今回の実行対象・進捗・証拠・中断位置 | Tasksとcheckpoint |
| 継続して使う手順・制約・学び | Memory |

運用手順はMemoryの`type: procedure, scope: ops`を基本とし、両用途に共通する手順ならsharedにする。既存のリポジトリ内Markdownを正本とする場合はその参照を使い、同じ手順本文をMemoryへ二重保存しない。手順はプロジェクトに属し、kotoが配布するのは汎用テンプレートだけとする。

テンプレートには目的・適用対象、必要な入力、実行前の状態、操作と各段階の期待結果、成功条件、停止条件、失敗後の復旧・再開条件を置く。実際のコマンドは利用先で定める。全ての操作が取り消せると仮定せず、手順で確認できない再送や取り消しを自動で行わない。

運用のタスク化は次の方針で第2段階に実装する。開発向けルールとは適用条件を分ける。

- システムや業務データの状態を変更する運用は実行前にTasksへ登録し、同じ目的の既存タスクは再利用する。状態を読むだけの調査・相談は自動でタスク化しない。ユーザーが実行記録をタスクとして残すよう依頼した場合は、その依頼を扱う。
- タスクには運用であること、対象、選択した手順のID/パスと実際に読んだ版または内容ハッシュ、成功条件を記録する。詳細な実行結果は成果物として参照し、最新状態を別のMarkdown台帳に二重管理しない。Tasksの新しい状態や必須フィールドは増やさない。

- 原則は手順の成功条件を実状態で確認して完了にする。ユーザーの明示的な完了指定があれば、実際の未確認・未達も残す。純粋な運用にはPRのマージを完了条件として要求しない。
- コード変更が必要になった場合はdevlowへ引き継ぐ。同じ目的なら既存タスクを再利用し、コード変更分には既存のPR／MR・検証・マージ条件を適用する。運用側の確認だけで、未完了のコード変更を含むタスクを完了にしない。
- 中断では最終確認状態・実行済み操作・成否不明の操作・次の確認をcheckpointへ残す。recallからの継続先にopsflowを追加する。

Tasksへのscope追加についてユーザーから質問があった。Memoryの共有・開発・運用は知識の適用範囲であり、タスクには同じ三択を追加しない。現行Tasksは任意属性を受け付けないため、説明文に作業の種類・現在の継続先を、checkpointにその時点の工程を残す。運用から開発へ移る同じ目的の仕事を同じタスクで追えるようにする。種類別の一覧・集計が必要になった場合の構造化は今回に含めない。

Memoryの通常の運用参照は利用記録付きで呼び出し、呼び出し元をopsflowとする。明示された読み取り専用・記録不要と通常のrecallは既存の扱いを維持する。利用イベントの形式・集計APIは変えず、過去のログへscopeや呼び出し元を推測して追記しない。

利用先のAGENTS.md/CLAUDE.mdには開発と運用の入口を用意する。正本のtemplates/AGENTS.mdと指示生成の参照先を更新し、既存管理ブロック・ユーザー編集を保護する既存のinstructions plan/apply/statusを使う。setup時の自動適用や、導入済みMacプラグインの自動更新は追加しない。

## 6. 実装順序と検証

1. 第1段階の期待結果を先にテスト化する。全5分類の有効値・不正値・未指定、create/update/relateと未分類読取、unset拒否、分類変更時のハッシュ競合を確認する。
2. 保存・検証を実装し、共有＋対象用途の検索を追加する。語句・分類・属性・code_refsの各経路で対象外を除き、上限適用前に選別するテストを通す。scope省略、完全一致フィルタ、未分類一覧の互換性も確認する。
3. 配布元の分類と既存スキルを更新する。利用先データは、一時プロジェクトに旧形式を用意して移行手順を検証する。未分類を読むだけではファイル・日時・ログを変更しないこと、分類更新で本文・リンク・履歴を失わないことを確認する。
4. 第1段階を検証してから、第2段階のopsflow・手順テンプレート・指示更新を追加する。個別の本番サービスへの操作や、新しい定期実行機構は作らない。
5. 一時プロジェクトの模擬運用で、共有と運用の知識選択、調査だけならタスクを作らないこと、状態変更前のタスク化、成功確認前に完了しないこと、中断後の重複実行回避、手順変更後の再確認、コード変更への引き継ぎを検証する。スキルの形式検査や文言一致だけで動作確認済みにしない。
6. Memoryの利用ログは検索で返した知識だけを1イベントへ記録し、絞り込み・失敗・読み取り専用の既存契約を維持することを確認する。Opsフロー経由のMemory利用とOpsフロー自身の実行回数を混同しない。
7. 両製品の配布物だけでCLIの保存・用途検索・未分類移行と指示の追加更新を確認する。全テスト・型検査・build:check・git diff --checkを実施する。生成後のスキルが全9件で、配布内のリンクが解決できることを確認する。

実装を依頼されたらdevelopから作業ブランチを切り、各段階の関連変更と生成物を同じPRへ含める。第1段階、第2段階の順に履歴を残すマージコミットでdevelopへ統合し、統合したコミットのCIを確認する。main統合、版数変更、公開、Macへのインストール更新、利用先の実データ移行はこの計画の実装だけでは行わない。

## 7. 完了条件と残る境界

- 全5分類で共有・開発・運用を保存でき、共有＋対象用途をCLIが一貫して検索する。
- 未分類と共有を混同せず、既存の知識が読めなくなる移行を避ける。配布元23件の分類と、旧形式の一時データによる移行検証が終わっている。
- DevフローとOpsフローが用途・タスク化・完了条件を使い分け、recallから適切な継続先へ渡せる。
- 手順の正本と一回の実行記録を分け、読み取り専用・プロジェクト境界・既存の更新保護を維持する。
- 配布物・実行経路・CIの結果を記録し、未実施の本番運用や導入先の移行を完了と報告しない。

汎用のOpsフローとテンプレートはこの計画で定義できる。実際の運用手順のコマンド・対象環境・権限・固有の成功条件は、利用先ごとに別途与える内容であり、推測で埋めない。
