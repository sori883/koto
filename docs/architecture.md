# kotoの目的と配布設計

koto（コト）は **Knowledge-Oriented Task Orchestration** の略であり、知識の継承と、タスクの分割・管理を名前の軸とする。

kotoは、Claude Codeで開発するときの作業スタイル（作業の進め方、原則、委任の仕方、検証の仕方）を、Claude Codeプラグインとして配布するためのリポジトリである。

この文書を、何を作るか・どこに置くか・どう配布するかを判断するための設計方針の正本とする。以下は目標の構成であり、すべてが実装済みという意味ではない。

## 作り方の方針

**[pstack](https://github.com/cursor/plugins/tree/main/pstack)を参照元として土台を作り、その上にkoto独自の概念を載せる。**

1. 土台：pstackの構成（入口となる中核スキル、作業種別ごとのプレイブック、原則、委任用エージェント、単体で使えるスキル）を参照し、Claude Code向けに書き起こす。
2. koto独自の概念：土台ができてから、Knowledge（知識の継承）とTickets（タスクの分割・管理）を順に載せる。載せ方は各段階で設計し、この文書へ追記する。

pstackは取り込まず、参照して書き起こす。

- pstackはCursor向けに書かれており、Cursor固有の機能・ツール名・作者個人のやり方を前提にした部分が多い。kotoはClaude Codeのツール名と機能で最初から書く。Cursorの名前を読み替える仕組み（pstackの`docs/harness/claude-code.md`に相当するもの）は作らない。
- 中核スキルとプレイブックは、Knowledge・Ticketsを組み込む前提で書き直すため、上流との差分追従を目的にしない。
- ほぼそのまま使え、koto独自の概念とほとんど関わらないスキルに限り、個別にコピーして調整してよい。その場合は、pstackのMIT Licenseの著作権表示と許諾表示を配布物に含める。

参照したpstackの版と、スキルごとの採否は[pstack参照記録](pstack/reference.md)に置く。

## 対象製品

対象はClaude Codeだけとする。Codex・GitHub Copilot・Cursor向けの配布物は作らない。

配布物では、Claude Codeが提供するツール・機能を名前のまま使う（`Agent`、`AskUserQuestion`、`Skill`、タスクリスト、`isolation: "worktree"`など）。Claude Codeにない機能を前提にした手順は作らない。

## 製品と開発環境を区別する

このリポジトリで開発するのは、別のプロジェクトへ配布して使う道具である。開発リポジトリ内だけで動くことを完成条件にしない。配布元への絶対パス、配布物に含まれないファイルへのリンクに依存させない。

リポジトリ内のスキル・エージェント定義・原則は開発対象であり、その指示をこのリポジトリでの作業ルールとして適用しない。開発時の指示はルートの[AGENTS.md](../AGENTS.md)とユーザーの指示に従う。ルートの`AGENTS.md`・`.agents/`・`.codex/`・`.claude/`・`.serena/`・`.vscode/`は、このリポジトリで作業するためのハーネスであり、配布物ではない。

配布物には、その配布物を保守する人向けの記述を一切含めない。配布するスキル本文・参照資料・エージェント定義等には、利用者または利用先で実行するAIに必要な内容だけを記載する。保守方針、pstackとの差分、変更経緯、開発時の検証記録などは、配布対象外の`docs/`で管理する。

配布物の本文は日本語で書く。ツール名・コマンド・ファイル名などの識別子は原語のままにする。

## 配置

| 場所 | 役割 |
| --- | --- |
| `.claude-plugin/marketplace.json` | このリポジトリをClaude Codeのマーケットプレイスとして公開する定義。`plugin/`を`koto`プラグインとして載せる |
| `plugin/` | 配布するプラグインの正本。ここにあるファイルだけが利用先へ届く |
| `plugin/.claude-plugin/plugin.json` | プラグインの名前・版・説明 |
| `plugin/skills/<name>/SKILL.md` | スキル。スキル専用の参照資料は同じフォルダの`references/`、実行コードは`scripts/`に置く |
| `plugin/agents/<name>.md` | 委任用のサブエージェント定義 |
| `plugin/hooks/hooks.json` | フックの定義。Knowledgeの目次と、編集するファイルに結びついた1件をAIに読ませる |
| `docs/` | 設計・参照記録・検証記録など、保守者向けの資料。配布しない |
| `tests/` | 配布するスクリプトのテスト。保守者向けであり、配布しない |

正式名称、プラグイン名、マーケットプレイス名は`koto`とする。GitHubの参照先は`sori883/koto`とする。

利用者は次の手順で導入する。

```bash
/plugin marketplace add sori883/koto
/plugin install koto@koto
```

## 土台の構成

pstackの構成を参照し、次の層で組み立てる。

| 層 | 役割 | pstackでの対応 |
| --- | --- | --- |
| 中核スキル（`koto-mode`） | 作業の入口。依頼をプレイブックに対応付け、手順をタスクリストへ写し、必要なスキル・原則・委任を呼び出す | `poteto-mode` |
| プレイブック | 作業種別（調査、不具合修正、機能追加、リファクタリング、PR作成など）ごとの手順。中核スキルの`playbooks/`に置く | `poteto-mode/playbooks/` |
| 原則 | 一つの原則を一つのスキルにまとめる。中核スキルは原則の索引を持ち、適用する原則の本文を読む | `principle-*` |
| 委任用エージェント | 中核スキルが作業を任せるサブエージェント。作業前に中核スキルを読む | `poteto-agent` |
| 単体スキル | 中核スキルから呼ばれ、利用者が直接使うこともできるスキル（how、why、interrogate、tddなど） | その他のスキル |

すべてのスキルは、モデルがSkillツールで呼び出せる通常のスキルとし、frontmatterに`disable-model-invocation: false`を書く。pstackはほぼすべてのスキルを`true`にしているが、Claude Codeでは`true`のスキルをモデルがSkillツールで呼べず、中核スキルから他のスキルや原則へ進めなくなるため、kotoでは採らない。中核スキルのfrontmatterには`name: koto-mode`を書く。プラグインのスキルの正式な呼び名は`/koto:koto-mode`である。`name`を書くと、同じ名前の他のコマンドがない限り`/koto-mode`でも呼べる。

スキルどうしは、`koto:`を付けず名前だけで呼ぶ（Skillツールの`ticket`、本文の**unslop**スキルなど）。利用先の`.claude/skills/`か`~/.claude/skills/`に同じ名前のスキルがあれば、名前だけの呼び出しはそちらに行き、無ければkotoのスキルに行く（2026-11-28に`claude -p`で確認）。これにより、プラグイン本体を直さずに、利用先でkotoのスキルを差し替えられる。`../<name>/SKILL.md`のようなパスでほかのスキルを読まない。パスで読むと、差し替えたスキルが使われないからである。委任用エージェントの`subagent_type`（`koto:koto-agent`など）、エージェント定義の`skills`、利用者に案内するスラッシュコマンド（`/koto:ketchup`など）は、プラグインの名前のままにする。

スキルが使うスクリプトは、Bunで動くTypeScriptで書き、シェルスクリプトは使わない。外部パッケージに依存せず、`bun <スクリプトのパス>`だけで動くようにする。外部パッケージが要るときは、初回の実行時に依存を入れる仕組み（`koto-mode/scripts/bootstrap.ts`）に従う。スクリプトのテストは`tests/`に置き、配布物に含めない。

`reflect`スキルは、この差し替えでkotoのスキルを直す。会話から学びを拾い、直し案を出し、利用者の承認を受けてから直す。kotoのスキルを直すときは、プラグインの中を書き換えず、スキルのフォルダごと利用先のプロジェクトの`.claude/skills/<名前>/`（すべてのプロジェクトで使うなら`~/.claude/skills/<名前>/`）にコピーし、コピーを直す。利用先のスキルは、そのまま直す。コードについての判断や制約はKnowledgeに、仕組みで防げる間違いと利用者の好みは「後でやること」として返し、それぞれ`correct`と`automate-me`に任せる。コミットやPRは作らない。利用者が頼んだときだけ動く。コピーはkotoの更新を受けないので、直すのは承認された箇所だけにする。

`correct`スキルは、利用先でAIが繰り返している間違いを、文章ではなく利用先のコードで防ぐ。コミット、取り消し、レビューコメント、会話記録の訂正（既定で直近30日）、AI向けの決まりを読み、同じ種類が2回起きたものを対象にする。作り、型・lint、テスト、文章の順に、効くうちいちばん上の段で直す。案を出して承認を受けてから、1種類1コミットで直し、足した確認が過去の実際の間違いで失敗することを示す。pushとPRは頼まれたときだけ行う。決まりと防いでいる仕組みの対応表は、利用先の`CLAUDE.md`（無ければ`AGENTS.md`）に置く。Knowledgeには置かない。Knowledgeは判断と制約の記録で、AIへの決まりではないからである。`reflect`の「後でやること」は受け渡さない。`correct`は同じ会話記録を自分で読むからである。利用者に訂正されたら、`koto-mode`は対応表を確かめ、仕組みの無い決まりの繰り返しなら`correct`を勧める。自分からは呼ばない。

スキルには、できるだけ自由に進める働き方を書く。MCPツールの利用や外部への操作をスキルの本文で制限しない。止めるべき操作は、権限設定、組織の管理設定、MCPを接続しないことなど、プラグインの外で止める。

モデルの選択は、Claude Codeの`Agent`ツールが受け付ける`model`・`effort`で、役割ごとに指定する。役割と既定の値は中核スキルの「サブエージェント」の節に書く。委任用エージェントの既定は、エージェント定義のfrontmatterの`model`・`effort`に書く。役割ごとのモデル設定を書き出すセットアップスキル（pstackの`setup-pstack`）は中核に含めない。利用先の保存領域を作る`setup`スキルはこれとは別のものである（「利用先の保存領域」の節）。作るかどうかは後で判断する。

## 利用先の保存領域（`.space/`）

kotoが利用先のプロジェクトに残すファイルは、プロジェクトのルートの`.space/`にまとめる。セッションや作業ツリーより長く残す記録の置き場所であり、`/tmp`や作業フォルダの直下には置かない。

`.space/`は`setup`スキルが作る。`setup`は何度実行しても同じ結果になり、既存のファイルを上書き・削除しない。プロジェクトのルートは、Gitリポジトリならその最上位、そうでなければ利用者が指定したフォルダとする。

```text
{project}/.space/
  tickets/
    <ticket-id>/
      ticket.md        チケット本体
      decisions.tsv    このチケットの判断ログ（show-me-your-work）
  kb/
    index.md           Knowledgeの目次
    decisions/         判断
    constraints/       制約
    documents/         参照
    references/        参照の写し
```

- `tickets/`は、`ticket.md`も`decisions.tsv`もコミットする。チケットと判断の経緯は、利用者やチームが共有し、後からレビューする情報である。
- `kb/`もすべてコミットする。
- `setup`は`.gitignore`を作らない。

## Tickets

Tickets（チケットの管理）は、セッションをまたいで残る仕事の単位を扱う。名前の由来の「Task」とは別に、機能の名前はTicketsとし、Claude Codeのタスクリスト（セッション内の手順）と呼び分ける。

| 記録 | 答える問い | 置き場所 |
| --- | --- | --- |
| チケット | 何を、なぜ、どこまでやれば終わりか。いまどの状態か。中断したならどこから再開するか | `.space/tickets/<ticket-id>/ticket.md` |
| 判断ログ | どう進め、何を選び、何を根拠にしたか | `.space/tickets/<ticket-id>/decisions.tsv` |
| タスクリスト | このセッションでどの手順まで進んだか | Claude Codeのタスクリスト |

チケットは目的、終了条件、状態、依存関係、成果物への参照、checkpoint（現在地と次の操作）を持ち、判断の履歴は持たない。形式はMarkdownとし、`ticket.md`を正本とする。AIも人も本文を直接編集する。`ticket`スキルの補助スクリプト（`scripts/ticket.ts`）は、チケットの作成、frontmatterを読んだ一覧、状態と`updated`の書き換えだけを行い、ファイルの外に台帳や状態を持たない。

状態は`pending`、`running`、`paused`、`done`、`cancelled`の5つとする。子チケットは`parent`で親を指し、フォルダは入れ子にしない。依存先が`done`でなければ`running`にできず、子チケットが終わっていなければ親を`done`にできない。

チケットの形式と操作手順は`ticket`スキルに書く。チケットを作るかどうかは、koto-modeのプレイブックごとに決める。チケットを作らないプレイブックには、チケットについて何も書かない。

| 区分 | プレイブック | チケットの扱い |
| --- | --- | --- |
| 作る | Bug fix、Feature、Refactoring、Perf issue、Visual parity、Hillclimb、Autonomous run、Multi-phase plan、Autopilot-full、Autopilot-stack | 手順の中でチケットを作るか、同じ仕事の既存のチケットを使う。目的と終了条件を書く。Visual parity・Multi-phase plan・Autopilotは、全体を親、担当やPRごとを子にする |
| 使う | Pause safely、Session pickup、Opening a PR | 作業のチケットがあれば読み書きする。checkpointの更新、`paused`・`running`への変更。Opening a PRは、PRのURLを書いてチケットを`done`にする |
| 関わらない | Babysit、Shipping、Investigation、Runtime forensics、Trace forensics、Prototype、Worktree cleanup、Authoring a skill、Eval | 何も書かない |

PRで出す仕事のチケットは、PRを開いた時点で`done`にし、その更新をPRに含める。チケットは作業ブランチ上のファイルなので、マージ後に閉じようとすると`main`へ直接コミットすることになるからである。PRを開いた後のレビュー対応やマージではチケットに触れず、差し戻されて作業し直すときは`pending`に戻す。

show-me-your-workとHillclimbは、判断ログをチケットのフォルダの`decisions.tsv`に、show-me-your-workの列で書く。

作業の状況を拾い直す役目は、`recall`スキルとSession pickupのプレイブックが持つ。どちらも、チケット（checkpoint）、判断ログ、会話記録、Gitの状態から現在地を組み立てる。`recall`は「どこまでやっていたか」に答えるもので、関係するチケットや会話をまたいで読み、現在地と次の一手を報告して終わる。何も書き換えない。Session pickupは「この作業の続きをやって」に答えるもので、引き継ぐ1件を読み、チケットを`running`に戻して、残りを該当するプレイブックへ回す。どちらもKnowledgeは読まない。Knowledgeが持つのは終わった判断と制約であり、作業の状況はチケットと会話記録にある。Knowledgeは、フックと計画の段で別に届く。

`recall`は、チケットや話題の指定があればそれに絞り、無ければ会話記録を直近7日まで読む。GitHubのPR・Issueは`git`と`gh`で調べ、エラー監視やチャットなどの共有の記録は、接続（MCP）があるときだけ調べる。使えない接続は飛ばし、飛ばしたことを報告に書く。報告はpstackの形（要約、筋ごとの状態、繰り返し起きている問題、次の一手）とし、筋の状態はチケットの状態とPRの状態から付ける。

## Knowledge

Knowledge（知識の継承）は、コードにもGitの履歴にも残らず、次に作業する自分とAIが知らないと困ることを、チケットより長く残す。Claude Codeの自動メモリーや`/memory`コマンドと取り違えないよう、機能の名前はMemoryではなくKnowledgeとする。

### 記録の振り分け

情報の行き先は、「その情報を、あとで誰がいつ必要とするか」で決める。無人の作業でも協働の作業でも同じ基準を使い、変わるのは誰が承認するかだけである。次の順に当てはめ、最初に当てはまった場所に残す。

| 順 | 情報 | 行き先 |
| --- | --- | --- |
| 1 | コードやGitの履歴を読めばわかる | 残さない。コードを読むか、`why`で掘り起こす |
| 2 | 型・lint・テストで防げる | 仕組みにする |
| 3 | 次も同じ手順を踏む | スキル |
| 4 | これからやる仕事、いまの現在地 | チケット |
| 5 | その作業をレビューするためだけに要る経緯 | 判断ログ（`decisions.tsv`） |
| 6 | 次の作業でも、知らないと困る | Knowledge |

利用者の好みや作業スタイルはKnowledgeに入れず、`CLAUDE.md`と、`automate-me`で作る個人用スキルに置く。Claude Codeの自動メモリーには、kotoからは書かない。利用者が自由に使う。社外秘の資料は扱わない。

### 種類

| `type` | 入れるもの | 読んだAIの態度 | 本文の見出し |
| --- | --- | --- | --- |
| `Decision`（判断） | 設計の判断、見送った案 | 正しい状態として扱い、変えるよう提案しない | 結論 / 理由 / 見送った案 |
| `Constraint`（制約） | 外から来た制約（契約、法律、ほかのチームとの取り決め）と、受け入れた妥協（既存のコード、範囲、時間など内側の事情） | その場では変えず、見直す条件を満たしたときにだけ変える提案をする | 制約 / 出所 / 守り方 / 本当はどうしたいか（任意。妥協のときに書く） |
| `Reference`（参照） | 文書への参照。資料が扱う関心事ごとに1件とし、資料の長さでは分けない | その関心事に触れたときに読む | 要点 / 読む場面 / 開き方 / 目次 |

妥協は、理想ではないと分かったうえで受け入れているという点で、AIに取ってほしい態度が制約と同じなので、制約にまとめる。

コードへの参照は種類にせず、判断・制約に付ける`code_refs`（効く場所）で表す。1件と1件の関係は、OKFに従って本文のMarkdownリンクで表し、関係の意味はリンクの前後の文章で伝える。妥協を生んだ制約があれば、妥協の「出所」からその制約へリンクする。

### 形式

1件は、[OKF v0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)の形式で、YAMLのfrontmatterとMarkdownの本文を持つ1ファイルとする。frontmatterには次のキーを使う。

- 必須
  - `type`：`Decision`・`Constraint`・`Reference`のいずれか。
- OKFの推奨
  - `title`：短い名前。目次の見出しになる。
  - `description`：1文の要約。目次に出る1行で、起動時にAIが読むのはここまで。
  - `tags`：関心事（auth、billingなど）を表す文字列の配列。
  - `resource`：`Reference`だけで使う。元の資料のURL。
- OKFの任意
  - `status`：`stable`（確定）・`draft`（未確認）・`deprecated`（役目を終えた）。AIが書いた1件も`stable`にする。人がすべてを確かめるのは現実的でないので、人の確認を確定の条件にしない。`draft`は、中身に自信がなく後で確かめたいときだけ使う。
  - `generated`：`{ by, at }`。誰がいつ書いたか。
  - `verified`：`[{ by: human:…, at }]`。人が中身を確かめた記録。利用者が残すよう頼んだときや、候補を承認したときに足す。無くてもよい。`Reference`では、元の資料と照らした日にもなる。
  - `sources`：出どころ。チケットのパス、PRのURLなど。
  - `stale_after`：見直す期限が日付で言えるときだけ使う。
- kotoが足すもの
  - `code_refs`：リポジトリのルートからのパス・globの配列。効く場所を表し、編集の直前に出す1件を選ぶのに使う。
  - `review_when`：見直す条件を文章で書く。日付で言えない条件（「呼び出し側を移行するとき」など）に使う。

### 置き場所

Knowledgeは`.space/kb/`に置き、フォルダを種類で分ける。関心事は`tags`で表す。ファイル名（slug）は英語にする。

- `index.md`：OKFの目次。補助スクリプトが、1件を書くたびに作り直す。手では編集しない。
- `decisions/<slug>.md`：判断。
- `constraints/<slug>.md`：制約。
- `documents/<slug>.md`：参照。本文は目次・要点・読む場面。
- `references/<slug>/`：参照の写し。OKFの`references/`の慣習に従う。資料はMarkdownに変換して置き、元のファイルは置かずに`resource`で元の場所を指す。図や表が要点になる資料は、その画像も置く。

OKFの更新履歴（`log.md`）は持たない。Gitの履歴で足りる。

### 書き込み

| 入口 | いつ | 流れ |
| --- | --- | --- |
| チケットを閉じるとき | チケットを`done`または`cancelled`にするとき | `ticket.md`と`decisions.tsv`を読み返して候補を選び、利用者に残すかを聞く。協働なら利用者がその場で残すかを選び、承認した記録を`verified`に残す。無人ならAIが選んで書く。どちらも`stable`とする。取りやめたチケットも、取りやめた理由が見送った案として残ることがあるので同じに扱う |
| 利用者が残すよう頼んだとき | いつでも。チケットのない作業でも | `knowledge`スキルで1件を書く。作業の途中で、AIの側から残すよう提案はしない |
| no-commentsがコメントを消すとき | コメントを整理するとき | コメントの中身を振り分ける。受け入れた妥協と外から来た制約は、`code_refs`付きの制約として書いてから消す |

チケットを閉じるときに書くので、PRで出す仕事のKnowledgeは、チケットの更新と同じPRに入る。PRがマージされなければ、そのKnowledgeも`main`に入らない。Knowledgeには結論と効く場所を書き、詳しい経緯は`sources`のチケットから辿る。

no-commentsでのコメントの振り分けは次のとおりとする。

| コメントの中身 | 行き先 |
| --- | --- |
| コードが何をしているか | 消す。名前や構造で表す |
| 仕組みで守れる注意 | 型・実行時の確認・テストにしてから消す |
| この変更をした理由 | コミット・PRに残して消す |
| 受け入れた妥協、外から来た制約 | Knowledgeの制約（`code_refs`付き）にしてから消す |
| 自分たちが変えられないものへの注意（ライセンス表示、ツールが読む指示など） | コードに残す |

### 読ませ方

| 場面 | 仕組み | 出すもの |
| --- | --- | --- |
| 会話の開始、サブエージェントの開始 | `SessionStart`・`SubagentStart`のフック | `index.md`をそのまま。`draft`の1件には印を付ける。目次が長くなりすぎたら（目安は100件）、種類ごとの件数と、`knowledge`スキルで探すよう案内する文だけにする |
| 修正や実装を計画するとき | Bug fix・Feature・Refactoring・Perf issueのプレイブックの計画の段 | 触るファイルが決まったら`knowledge.ts for-path`で確かめ、計画に反映する。委任するときは、該当する1件のパスを依頼文に書く |
| 指摘や変更の提案の前 | koto-modeの決まり | その箇所の1件を確かめてから提案する |
| ファイルを読んだ直後 | `PostToolUse`（`Read`）のフック | `code_refs`が一致する判断・制約の本文。`Edit`は先に読むことが前提なので、編集を考える前に届く |
| ファイルを編集する直前 | `PreToolUse`（`Edit\|Write\|NotebookEdit`）のフック | 同じ本文。読まずに書く場合の予備 |

`SessionStart`の`additionalContext`はメインの会話にだけ届き、サブエージェントには`SubagentStart`で届く。`PreToolUse`の`additionalContext`はどちらにも届く。

`PreToolUse`の`additionalContext`は、ツールが実行された後に結果と一緒にAIに届くため、その編集を止められない。そのため、編集の前に効かせる役目は計画の段と`Read`の直後に持たせ、編集の直前は予備とする。編集を一度断る形（`permissionDecision: "deny"`）は、読ませるために拒否を使うことになり、断った記録の管理も要るので採らない。`Read`の直後のフックは読むたびに呼ばれるが、1回あたり0.01〜0.02秒（Knowledgeが300件のときに測定）で、文脈が足されるのは`code_refs`が一致したときだけである。

委任用エージェントには、エージェント定義の`skills`で`knowledge`スキルを読み込ませる。そのため`knowledge`スキルにも`disable-model-invocation: true`を付けない。

### 見直し

見直しと片付けは、利用者が気が向いたときにコマンドで行う。`review_when`・`stale_after`の点検、役目を終えた1件の`deprecated`への変更、`code_refs`の指す先が消えていないかの確認、`draft`の1件の確定を扱う。

### 補助スクリプト

`knowledge`スキルの補助スクリプト（`scripts/knowledge.ts`）は、1件の作成（雛形と名前の検査）、検索（種類・`tags`・`status`・語句）、`code_refs`の照合、目次の生成、検査（形式、リンク切れ、`code_refs`の指す先、期限切れ）だけを行う。1件の更新・削除・関連付けは、チケットと同じくAIがファイルを直接編集する。外部パッケージには依存しない。

## 未決事項

実装や試験の中で見つかり、まだ決めていない事項である。決めたらこの節から消し、該当する節に書く。

- **Autopilotの親チケットを閉じる場所。** 子チケットは各担当がPRを開くときに閉じる。親チケットは「子チケットがすべて終わったら閉じる」としか決めておらず、担当がクラウドで並行して動くため、どのPRの中で閉じるかが決まっていない。実際にAutopilotを動かして決める。
- **automate-meの扱い。** `reflect`と`correct`は決めた（「土台の構成」の節）。`automate-me`が作るスキルをどこに置くかを決めていない。`automate-me`は、利用者の好みと作業スタイルの置き場所になる。
- **実際に動かして確かめていないプレイブック。** チケットを作るプレイブックのうち、Bug fixとMulti-phase plan以外（Feature、Refactoring、Perf issue、Visual parity、Hillclimb、Autonomous run、Autopilot）は、手順を揃えただけで動かしていない。PRが差し戻されてチケットを`pending`に戻す流れも試していない。
- **スクリプトのテストの置き場所。** kotoで書いたスクリプトのテストは`tests/`に置き、配布しない。pstackからコピーした`koto-mode/scripts/watch-pr/`と`statechart/scripts/`のテストは、配布物の中に残っている。どちらに揃えるかを決める。

## 検証

配布物の完成条件は、利用先のClaude Codeでプラグインとして読み込めて、スキル・エージェントが意図どおりに動くことである。

- 構文：`claude plugin validate`でマーケットプレイスとプラグインの定義を検証する。
- スクリプト：`bun test tests`で、配布するスクリプトのテストを実行する。
- 読み込み：`claude --plugin-dir plugin`で起動し、スキル・エージェントが一覧に出ることを確認する。
- 振る舞い：中核スキルとプレイブックは、実際の依頼で意図した手順を踏むかを確認する。
