# kotoの目的と配布設計

koto（コト）は **Knowledge-Oriented Task Orchestration** の略であり、知識の継承とタスクの管理を名前の軸とする。AIエージェントが利用する道具を、Codex・Claude Code向けに配布するためのリポジトリである。

この文書を、何を作るか・正本をどこに置くか・どう配布するかの判断基準とする。設計方針と現行実装を区別し、実装状況・検証結果は[現状資料](current-state.md)と個別の開発記録に置く。

## 対応製品と現在の整理

2026-10-31のユーザー指示により、対応先をCodex・Claude Codeの2製品に限定する。Copilot対応は削除する。製品ごとに配布物とカタログを生成し、ソースとともにGitで管理する。続くユーザー指示により、今回のmonorepo機能は`main`から作る`develop`へ統合する。元のコミット履歴を保持するマージコミットを使い、スカッシュや履歴の書き換えは行わない。

ユーザーが削除した旧スキルと付属CLI、削除済みスキルを呼ぶエージェントと指示テンプレート、setup用マニフェストは一括して復元しない。続く依頼で、新しいmonorepo・Tasks・Memory CLIとそれぞれの利用手順を持つスキルを追加する。さらにユーザーがMITライセンスでの再利用を了承したため、devlow・recall・tdd・blast-radius・interrogateの5スキルを既存資産から取り込み、現在の3つのCLIに合わせる。著作権表示と許諾文を保持し、出典と変更記録はdocsへ置く。スキルのない構成でも配布物を生成できる機能は維持し、既存の共通知識は保持する。

以前のdevlow・OKF・orch・setup等の設計と検証は開発履歴としてdocsに残すが、その記録だけを現行機能や再実装の指示として扱わない。以前の[配布設計](https://github.com/sori883/koto/blob/77b4d4f87a4c575ccb4b243f2a62acd17cd446a2/docs/architecture.md)、[配布整理](issue-23-packaging-reset.md)、[今回のスキル連携](devlow-cli-integration.md)を区別する。新しい機能・配置への移行は依頼された範囲で進める。

## 統合ワークスペースの構想

2026-10-30に共有された方針を基準とし、Memory・Tasks・Workspaceを独立した責務のツールとして開発する。当初はすべて別リポジトリを想定していたが、2026-10-31のユーザー指示により、Workspaceに続いてTasks・Memoryも現在のkotoリポジトリ内で所有・開発する。Memoryはユーザー指定のagent-memory試作を参考にする。共通Coreや中央の統合CLIを必須にせず、AIエージェントが必要なツールを個別に利用する。

| ツール | 責務 |
| --- | --- |
| Memory | OKFによる知識・経験・設計判断の保存、検索、更新、検証 |
| Tasks | タスク、依存関係、進捗、成果物、チェックポイント |
| Workspace（モノレポ管理） | setupによる初期設定、プロジェクト、Gitリポジトリの登録・同期・削除、Worktree、作業環境 |

プロジェクトを情報管理とアクセス境界の単位とし、プロジェクト間で情報やGit管理領域を暗黙に共有しない。対象指定がなければdefaultを選び、明示した対象が存在しない場合やアクセス拒否時は別プロジェクトへ切り替えない。安定したproject_id・task_id・repository_idで相互参照する。

ワークスペース全体のGit管理を必須とせず、独立したリポジトリを必要に応じて組み合わせる。想定配置は`.space/<project>/memory/`・`tasks/`・`checkpoint/`、`repositories/<project>/`、`workspaces/<project>/<task>/<repository>/`とする。Git管理領域はBare Repositoryを基本とし、タスクごとにWorktreeを分ける。一つのタスクで複数リポジトリを扱えるようにする。

各ツールに用意するCLIは非対話実行とJSON入出力に対応し、特定の言語やAI製品に依存しない構成を目指す。Workspaceの初期設定・管理操作はCLIを中心に実装し、スキルは利用手順、AIは依頼の解釈と結果の説明を担う。パスの境界、シンボリックリンク、認証情報、並行更新、異常終了、再実行時のデータ保護を考慮する。CLIの対象選択と実際のアクセス認可を区別し、必要な隔離は実行環境側でも行う。

Workspaceのパッケージ名は`@koto/monorepo`、実行コマンドは`koto-monorepo`とする。Tasksは`@koto/tasks`、実行コマンドは`koto-tasks`とする。正本はそれぞれ`cli/monorepo/`・`cli/tasks/`に置き、スキルから独立して直接実行できる。Memoryは`@koto/memory`、実行コマンドは`koto-memory`、正本は`cli/memory/`とする。既存の利用先データを暗黙に移動・削除しない。

### モノレポ管理から着手する

2026-10-31のユーザー指示により、最初にWorkspaceを開発し、setupの役割をその中に含める。setupは独立したツールにせず、モノレポを使い始めるための初期設定を担う操作とする。管理ルートとdefaultプロジェクトの準備から、リポジトリ登録、作業場所の作成、状態確認までを一つのツールで扱う。

リポジトリ削除は登録解除として実装し、Git管理領域は残す。作成途中を含む作業環境や、Git上のWorktreeがあれば拒否する。続くユーザー指示により、Worktree整理を追加する。対象タスクの全Worktreeを事前検査し、未保存・未追跡・無視対象のファイル、リモートで保存を確認できないコミット、Gitの作業中状態やロックがあれば停止する。削除は既存Gitに委ね、強制削除をせず、ブランチとGit管理領域を保持する。途中失敗後の再実行に対応する。Memoryの知識操作とTasksのタスク管理は、それぞれ独立したツールの責務を維持する。setupはWorkspaceの管理情報と保存先だけを作り、共通知識・他ツールのデータ・クライアント指示は配置しない。詳細は[CLIの設計](monorepo-cli-design.md)で定める。

プロジェクト追加も管理機能に含める。setupで用意するdefaultと、後から追加するプロジェクトは同じ管理規則に従う。方針に含まれる機能と追加候補、未確定の範囲は[機能一覧](workspace-feature-inventory.md)に整理し、一覧全体を初期版の実装範囲とは扱わない。

### Tasksの追加

monorepoの初版完成後、ユーザーはTasksの開発を指示した。BunのCLIとし、旧orchの設計・実装を参考にする。外部依存を少なくするが、依存ゼロを絶対条件にはしない。実装難易度と保守負担を比較し、判断が難しい依存の採否は相談する。旧orchの担当権限・通知・承認等を一括して復元する指示とは扱わない。

Tasksはタスク・依存関係・進捗・成果物参照・チェックポイントを所有する。正本は`.space/<project>/tasks/state.json`。チェックポイントは正本へ保存したスナップショットを`.space/<project>/checkpoint/<task>/<id>.json`にも出力し、出力だけが失敗しても同じ操作から再開できるようにする。操作IDによる再送、versionによる古い更新の拒否、プロジェクト単位の排他、依存先の版の照合を行う。

TasksとWorkspaceは管理ファイルや実装モジュールを共有せず、同じproject_id・task_id・repository_idを参照する。タスクの完了、成果物の検証、Worktreeの削除は別々の結果として扱う。Tasksの変更は`develop`から作業ブランチを切り、検証後に履歴を残して`develop`へマージする。[Tasks CLIの設計](tasks-cli-design.md)を参照する。

### Memoryの追加

Tasksのdevelop統合後、ユーザーはMemoryの開発を指示し、試作のagent-memoryを参考にkoto内へ実装する方針を確認した。MemoryはOKF v0.2のMarkdownを`.space/<project>/memory/`へ保存し、ルール・原則・知識・手順・判断を扱う。タスクの進捗やGit管理を引き取らず、他のCLIの内部実装や管理ファイルに依存しない。

初期化・保存・検索・参照・更新・関連付け・削除・検証・中断した書き込みの復旧はCLIが担当する。AIは知識の内容と根拠を整理し、スキルはCLIの選択・入力・結果確認を案内する。検索はローカルの語句検索と属性・コード参照の照合を使い、外部の検索サービスや埋め込みを必須にしない。

更新にはプロジェクト単位の排他と内容のハッシュ照合を用意する。複数ファイルの更新予定を先に残し、失敗後は既存の変更と照合して続きから復旧する。コード参照の存在検査も選択したプロジェクト内に限定する。人間の確認記録を自動生成せず、形式検証と知識の正しさを区別する。詳細は[Memory CLIの設計](memory-cli-design.md)に定める。Memoryもdevelopから作業ブランチを切り、検証後に履歴を残してdevelopへ統合する。

### 開発フローと専門スキル

devlowは、依頼の終了地点に合わせて工程を選び、monorepo・Tasks・Memoryの利用順序と結果の受け渡しを定める。開始、継続、中断、再開、完了、依頼された片付けを扱い、各CLIの処理・保存規則を重複実装しない。最新の進捗はTasks、実際の作業場所はmonorepo、長期的な知識はMemoryが所有する。

recallは、現在のTasks、過去のcheckpoint、実際のコードやGit、必要なMemoryを読み取り専用で照合する。現在地と残件、再開条件を返し、続行の依頼があればdevlowが次の操作を選ぶ。checkpointを最新状態とみなしたり、状態確認だけで初期化・再開・片付けを行ったりしない。

各工程の詳細は参照資料へ分ける。tddは局所的な不具合の再現と修正、blast-radiusは変更の影響調査、interrogateは許可された独立担当によるレビューを担う。全スキルを毎回必須にせず、変更と検証の必要性に応じて選ぶ。固定名の専用エージェントや特定モデルは必須にしない。

旧orch CLI、旧OKF CLI、setupスキル、他の削除済みスキルとエージェントはこの追加に含めない。Gitのcommit・push・merge・PR操作は依頼された範囲で既存ツールを使う。3つのCLIの独立性、プロジェクト境界、利用者が許可した範囲を維持する。

### 実現方法と利用環境

2026-10-31の追加指示により、機械的に判定・実行できる初期設定と管理操作はCLI中心に作る。対象と設定が明示された後の、初期化、プロジェクト管理、リポジトリ登録・取得・更新取得・削除、Worktree作成、状態確認はCLIが担当する。複数リポジトリを扱う際の処理順序、一部失敗、排他制御、再実行もCLIが管理する。実際のGit処理は既存Gitを呼び出す。

スキルはAIが読むCLIの利用手順であり、独立した処理エンジンとして扱わない。必要な入力、操作の選択と順序、結果とエラーの扱いを定義する。AIは自然言語の依頼を入力へ変換し、曖昧な対象を確認し、結果を説明する。CLIに持たせたパス算出・状態更新・削除条件をスキルへ重複実装せず、AIが管理ファイルを直接編集して検証を迂回する運用にはしない。

CLIはAIを介さず人間からも実行できる。すべての判断や案内を専用コマンドにすることは求めない。既存の状態や外部Gitの応答は実行時に観測し、確認できない結果を成功と扱わない。各機能の[CLI・スキル・AIの分担](workspace-feature-inventory.md#cliスキルaiの責務)を明示する。

利用環境はCodex・Claude CodeのデスクトップおよびCLIを想定する。各環境のAIがスキルを読み、必要な専用処理と既存ツールを呼び出す。製品ごとの接続・読込・実行方法は実装段階で確認し、対応予定を動作確認済みとは扱わない。

Git操作の補助はWorkspaceの機能に含めない。commit・push・merge・PR操作等は既存ツールへ委ね、独自の同等機能を作らない。リポジトリの取得・更新取得・Worktree操作に既存Gitを使うことは、管理機能を実現する手段として残す。

移動・共有・保管は本ツールの対象から外す。管理ルートやプロジェクトの移動、共有・構成の受け渡し、バックアップ・復元、アーカイブは実装候補に含めない。プロジェクト境界と既存データの保護は維持する。

## 製品と開発環境を区別する

リポジトリ内のスキル・エージェント定義・ルール・原則・指示テンプレートは開発対象であり、このリポジトリでの作業ルールとして適用しない。開発時はルートの[AGENTS.md](../AGENTS.md)とユーザーの指示に従う。

配布物には、その配布物を保守する人向けの記述を一切含めない。利用者または利用先で実行するAIに必要な内容だけを記載する。保守方針、原版との差分、変更経緯、開発時の検証記録は、配布対象外のdocs等で管理する。

配布元の絶対パス、開発リポジトリの依存パッケージ、配布物に含まれない資料への参照に依存させない。開発用の`.agents/skills/`・`.codex/agents/`、旧`templates/AGENTS.md`は配布元として使わない。

## 正本・配布物・利用先

| 場所 | 役割 |
| --- | --- |
| `packaging/codex/`・`packaging/claude-code/` | 製品別のプラグインとカタログの定義 |
| `space/default/` | 保持する共通知識・原則の正本 |
| `cli/monorepo/` | `@koto/monorepo`の実装・パッケージ定義・利用者向け手順の正本 |
| `skills/monorepo/` | CLIを使うAI向け手順の正本 |
| `cli/tasks/` | `@koto/tasks`の実装・パッケージ定義・利用者向け手順の正本 |
| `skills/tasks/` | Tasks CLIを使うAI向け手順の正本 |
| `cli/memory/` | `@koto/memory`の実装・パッケージ定義・利用者向け手順の正本 |
| `skills/memory/` | Memory CLIを使うAI向け手順の正本 |
| `skills/devlow/`・`skills/recall/` | 開発フローと作業の現在地を再構成する手順の正本 |
| `skills/tdd/`・`skills/blast-radius/`・`skills/interrogate/` | 必要な工程で使う専門手順の正本 |
| `scripts/build.ts` | 正本から配布物とカタログを生成する開発用の入口 |
| `dist/<製品>/koto/` | 生成物。Gitで管理し、手編集しない |
| ルートの`package.json`・`bun.lock` | 生成・検証の開発依存と配布版数 |
| `docs/` | 開発者向けの設計・実装状況・検証記録。配布しない |
| 開発リポジトリ自身の`.space/` | このプロジェクト固有の知識・作業記録。配布しない |

2026-10-31のユーザー指示により、共通知識の正本は`space/default/`、生成先は各製品の`space/default/`とする。これは配布用ディレクトリの改名であり、既存の利用先データの移動や、将来のmemory・tasks・checkpoint階層の実装は含めない。

正式名称、リポジトリ名、プラグイン名、マーケットプレイス名はkotoとし、GitHubの参照先はsori883/kotoとする。共通知識の正本と配布先のコピーを混同せず、共通文書の変更はspaceから生成物へ反映する。

## 生成と配布

| 製品 | カタログ | 配布物 |
| --- | --- | --- |
| Codex | `.agents/plugins/marketplace.json` | `dist/codex/koto/` |
| Claude Code | `.claude-plugin/marketplace.json` | `dist/claude-code/koto/` |

buildは製品別定義と共通ソースを組み合わせ、ルートの版数を各配布物・カタログ・同梱CLIのパッケージ定義へ反映する。monorepo・Tasks・Memory CLIは両製品の`cli/monorepo/`・`cli/tasks/`・`cli/memory/`へ、スキルはそれぞれの`skills/`配下へコピーする。CLIに開発環境の依存パッケージを要求しない。スキルがない場合はプラグイン定義からskillsパスを省く。旧setupのマニフェストは生成しない。

スキルを追加した場合は、本文と必要な付属資料・実行ファイルを配布する。テスト、開発資料、利用先の記録、node_modules、実行時キャッシュは含めない。生成時に配布内のMarkdownリンクを確認し、シンボリックリンクを拒否する。

ソース変更と生成結果を同じ変更に含める。別のリリースブランチへ生成物を送る構成は作らない。公開・インストール・利用先への配置は別の操作として扱い、ローカルの生成成功だけで完了済みにしない。

## 検証と変更時の判断

型検査、生成処理のテスト、正本と生成物の全ファイル照合をCIで行う。照合では変更・不足だけでなく、未追跡を含む余分な生成物も検出する。削除した配布対象は再生成時にdistから取り除く。

製品への読込・実行、利用先のデータ更新は、その機能を実装した段階で実経路を確認する。未確認の結果を成功と扱わない。形式検証と利用先での動作確認を区別する。

既存実装だけを根拠に設計方針を変えない。現行実装との差は未実装・移行事項として扱い、ユーザーが方針を変更した場合は本文にも反映する。抽象化・共通基盤・新機能の追加は具体的な必要性に基づき、依頼範囲を守る。
