# Workspace（モノレポ管理）の機能一覧

2026-10-31。ユーザーの統合ワークスペース構想と、setupをWorkspaceへ含める指示、登録リポジトリの削除、プロジェクト追加の要望を基に整理した。初期版の全機能を確約するものではなく、対象範囲を検討するための一覧である。初期設定・管理操作はCLI中心に実装する。スキルはCLIの利用手順を定め、AIは依頼の解釈と結果の説明を担う。既存のGit等はCLIの内部から必要に応じて利用する。

初版の実装は[monorepo CLI設計](monorepo-cli-design.md)で具体化した。setup、プロジェクト追加・参照、リポジトリ登録・更新取得・登録解除、Worktree作成・参照、状態確認、JSON入出力を扱う。続く依頼で[Worktreeの片付け](monorepo-cleanup-design.md)と[指示ファイルの更新](instruction-setup-design.md)を追加した。登録解除ではGitデータを残す。以下の「状態」は要求の位置づけを表し、実装したものはその旨を明記する。設定変更、表示名変更、Git管理領域の物理削除などの候補を実装済みと扱わない。

設計方針の正本は[architecture.md](architecture.md)。以下の追加候補は採用済みの仕様として扱わない。

## 対象と状態の読み方

- 管理ルート：複数プロジェクトを置くワークスペース全体の場所。
- プロジェクト：リポジトリ・知識・タスク・作業環境の所属とアクセス境界の単位。
- 登録リポジトリ：プロジェクトが利用するGitリポジトリと、そのローカル管理領域。
- 作業環境：作業IDに対応する、一つ以上のリポジトリの編集場所。Git Worktreeを使う。
- setup：この管理環境を使い始めるための操作。Workspaceの責務に含める。

| 状態 | 意味 |
| --- | --- |
| 方針 | 会話・全体構想で対象となった責務。詳細仕様や初期版への採用順は別途決める |
| 具体化案 | 方針を実際の操作へ分解した提案。操作単位や名称は未確定 |
| 追加候補 | 利用上考えられる機能。採用は未決定 |
| 保留 | 会話で範囲が未確定の機能 |

計34項目・6領域。横断的な保護条件は後段に分ける。コマンド名、保存ファイル名、実装言語はこの一覧では決定しない。

## CLI・スキル・AIの責務

2026-10-31の追加指示により、初期設定を含む機械的に判定・実行できる管理操作はCLI中心に作る。CLIは人間から直接実行でき、AIの利用を必須としない。Codex・Claude Codeのデスクトップ／CLIから使う場合も同じ処理を呼び出す。各利用環境での接続は今後検証する。

スキルはAIが読む利用手順であり、CLIと並ぶ独立した処理エンジンではない。次の3つを区別する。

| 担当 | 責務 |
| --- | --- |
| Workspace CLI | 入力検証、初期化、管理情報の読み書き、Gitの呼び出し、状態取得、削除条件の判定、排他制御、途中失敗と再実行への対応。人間向け表示とJSON出力を提供する |
| スキル | どの依頼で何を確認し、どのCLI操作をどの順序で使い、結果やエラーをどう扱うかを定義する。パス算出・状態更新・削除判定等の実装を重複して書かない |
| AI | 自然言語の依頼を対象・入力へ落とし込み、曖昧な点を確認し、必要な操作を選び、観測した結果を説明する。CLIの出力にない成功や状態を推測しない |

### 中心機能の分担

以下は合意した中心機能と、それを支える処理の分担。具体的なコマンドは[CLI手順](../cli/monorepo/README.md)に記載する。

| 機能 | CLIが実行すること | スキルに定義すること | AIが判断・説明すること |
| --- | --- | --- | --- |
| 初期設定 | 管理ルート・default・設定の作成、既存状態の検査、再実行時の保護 | 必要な入力と初期化操作、結果の確認手順 | 依頼された保存場所の特定、不足する入力の確認、結果の説明 |
| 環境確認 | Gitの利用可否、必要な設定や書き込み条件を検査し、結果を返す | 診断結果に応じた案内手順 | 不足の説明と、定型手順で解消しない問題の調査 |
| プロジェクト管理 | 追加・一覧・詳細、IDと名前の管理、対象指定とdefaultの適用、重複や不明な対象の拒否 | 依頼から対象を指定する方法と操作手順 | 名前・対象が曖昧な場合の確認、一覧や結果の説明 |
| リポジトリ管理 | 登録・取得・一覧・更新取得、所属と保存場所の管理。Gitの処理は既存Gitを呼ぶ | 登録に必要な入力、操作と結果確認の順序 | 依頼されたリポジトリと所属プロジェクトの特定、不明点の確認 |
| 作業場所の準備 | 指定された作業ID・リポジトリ群・開始地点・ブランチからWorktreeを作り、並行作業との競合、一部失敗、再実行を管理する | 必要な対象と開始条件の確認、作成結果の読み方 | 依頼に対応する作業ID・リポジトリ等の整理と、選択が未確定な場合の確認 |
| 状態確認・再アクセス | 登録情報、実際のパス、Gitの状態を取得し、既存の作業場所を返す | どの情報を確認し、未確認・失敗をどう区別するか | 結果の要約と、利用者が次に行う操作の説明 |
| 登録リポジトリ削除 | 初版は利用中のWorktreeがないことを確認して登録解除する。Gitデータは残す | 削除対象・範囲の指定、事前確認結果と失敗理由の扱い | 利用者の削除意図の特定、影響や削除できない理由の説明 |
| 中断・失敗後の対応 | 実行済みの部分を照合し、定めた規則で再試行・再開する。未完了を成功として返さない | エラー種別ごとの次の操作と、手順で扱えない場合の報告方法 | エラーと未完了範囲の説明、未知の原因の調査や対応案の提示 |

### 判断基準

- 明示された入力と観測した状態から、規則で判定できる処理をCLIへ置く。結果が変化し得るネットワークやGitの状態は実行時に確認し、観測結果と成功・失敗を返す。
- 複数リポジトリの作成や更新も、対象が決まった後の処理順序・途中状態・再実行はCLIで扱う。AIに個別コマンドと台帳の整合性を手作業で管理させない。
- スキルはCLIを利用するための手順とする。AIが管理ファイルを直接編集し、CLIの検証や排他制御を迂回する運用を前提にしない。
- 登録・取得・更新取得・Worktree操作の内部で既存Gitを使う。対象外としたcommit・push・merge・PR操作の独自機能は追加しない。
- 以下の追加候補・保留事項は、この分担を示しただけでは採用済みにならない。人間が対象や削除範囲を決める必要がある場合、その入力をAIが勝手に補わない。

## 横断的に必要な条件

以下は機能数に含めず、操作ごとの成功・失敗条件へ落とす。全体構想にあるデータ保護・アクセス境界・検証可能性を具体化したもの。

| 条件 | 確認する内容 |
| --- | --- |
| プロジェクトの境界 | 指定外プロジェクトへ暗黙にアクセス・切り替え・共有しない。認証情報と実行環境の権限を尊重する |
| パスの境界 | IDを使った領域外への移動や、シンボリックリンク経由の領域外書き込みを防ぐ |
| 既存データの保護 | 同名ディレクトリ、未管理のファイル、他者の作業を上書きしない |
| 削除前の確認 | 利用中Worktree、未コミット変更、未追跡・無視対象を含む保存すべきファイル、ローカルだけの履歴への影響を評価する。単に作業ツリーがきれいなだけで、削除可能とは判断しない |
| 並行実行 | 同じ登録情報・リポジトリ・作業環境に対する競合を検出し、必要な範囲で書き込みを排他する |
| 中断と再実行 | 実行済みの部分と未完了を照合できるようにし、Git操作と台帳更新が一度に成功する前提にしない |
| 他ツールとの責務 | Memory・Tasksの文書や台帳をWorkspaceが独自に書き換えない。必要な初期化の受け渡しは明示的なインターフェースで定める |
| 結果の確認 | 成功、失敗、一部完了、未確認を区別し、対象・結果・次に必要な操作を返す。ログやJSONへ認証情報を漏らさない |

## 検討時の論点

以下は一覧作成時の論点。初版はWorkspace自身の管理情報だけを初期化し、新しいBare Repositoryへの取得、登録解除のみの削除、Worktree作成までを採用した。その後、依頼に基づくWorktree整理を追加した。既存cloneの参照登録、プロジェクト削除、他ツールの初期化は含めない。

1. setupの配置物：Codex・Claude Code向け指示は別途instructions操作として追加した。共通知識の配置範囲は未確定。
2. リポジトリ削除：登録解除とローカルデータの削除を別操作にするか。利用中のWorktreeやローカル履歴をどう保護するか。
3. プロジェクト削除：初期版で提供するか。他ツールの所有データとの境界をどう扱うか。
4. Worktree整理：手動削除を初期版に入れるか。作業完了時の自動整理は別の判断とする。
5. CLI仕様：上記の分担に沿って入力・出力・失敗条件・再実行を具体化する。リポジトリ同期で扱う範囲を明示し、commit・push・merge等の補助は追加しない。
6. 既存環境の取り込み：新規管理領域への取得だけから始めるか、既存cloneの登録も必要か。
7. setupとプロジェクト追加の保存配置：共有された`.space/<project>/memory/`等の構想に対し、Workspace自身の管理情報をどこへ置き、他ツールの初期化とどう分担するか。

## 対象外

2026-10-31のユーザー指示により、次の機能は候補からも外す。

- Git操作の補助：commit・push・mergeやPR操作等の独自コマンド・補助機能は作らない。必要な作業は既存のGit・GitHub CLI等で行う。リポジトリ取得・更新取得・Worktree操作に既存Gitを使うことは、Workspaceの管理機能を実現する手段として残す。
- 移動・共有・保管：管理ルートやプロジェクトの移動、共有・構成の受け渡し、バックアップ・復元、アーカイブを本ツールの機能に含めない。プロジェクト境界と既存データの保護は引き続き必要とする。

GitHub等でのリモートリポジトリの作成・削除、タスクの進捗管理、知識の検索・編集、OSのアクセス制御そのものの実装もWorkspaceの対象に含めていない。
