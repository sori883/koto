## 対象と根拠

試作リポジトリには未コミットの実装とテストがあるため、HEADだけで参考にした内容を表せない。[参照元ファイルのSHA-256](memory-prototype-source.json)を記録した。試作のsrc・testsだけを参照し、利用先データ、開発設定、旧スキル、依存パッケージは取り込まない。試作側での書き込みや依存導入は行わない。

独立したCLIを`cli/memory/`、AI向け手順を`skills/memory/`へ置く。配布は両製品の同じ相対位置にコピーする。利用者向け資料はCLI内、保守・差分・検証記録はこのdocs内に置く。Tasksとmonorepoの実装・状態・排他領域を共有しない。

## 機能と分担

| 項目 | CLI | スキルとAI |
| --- | --- | --- |
| 初期設定 | 明示した管理ルートとprojectのMemory、分類目次、ログを準備 | 管理ルートと初期化の目的を確認 |
| 記録 | ID・属性の検証、Markdown保存、目次・ログの更新 | 知識の分類、本文・根拠・適切な粒度の判断 |
| 検索・参照 | 日本語を含む語句検索、属性・コード参照フィルタ、詳細・関連参照 | 問いと対象の選択、記録と現在の事実の照合 |
| 更新・関連付け | 属性保持、ハッシュ照合、関連リンクの追加 | 変更の意味と対象の判断 |
| 削除 | 参照元への影響の事前確認、管理リンク除去、削除ログ | 依頼範囲と影響の確認 |
| 検証 | OKF属性・リンク・目次・期限・コード参照の検査 | 根拠の再確認、人間の確認記録の扱い |
| 中断からの復旧 | 予定と実体の照合、未適用部分の再実行 | 原因の特定、別の変更がある場合の判断 |

パッケージ名は`@koto/memory`、入口は`koto-memory`。Bun 1.4.2以上、追加の実行時npm依存はない。YAMLはBunの組込みAPI、日本語の語分割はIntl.Segmenter、パス照合はBun.Globを利用する。既存の実装で必要な処理を満たせるため、外部の検索エンジン、データベース、埋め込みサービスは導入しない。

## データと互換性

`.space/<project>/memory/`のMarkdownを正本とする。OKF v0.2、5分類、目次とログ、任意のJSON互換属性、generated・verified・sources・stale_after・code_refsを扱う。値のない更新は変更日時やログを増やさない。YAMLのコメントや表記自体の保存は保証せず、値と本文を保持する。人間のverifiedをAIが自動付与する処理はない。

試作のMarkdown形式、語句検索、属性フィルタ、Markdownリンク解釈、削除時の本文保持の処理を利用した。kotoへの取り込みでは、名称、パッケージ、JSON契約、プロジェクトID、コード参照の範囲、復旧、内容ハッシュの照合を変更した。CLIの旧axram互換ラッパーや既存データの自動移行は作らない。

プロジェクトIDは他のkoto CLIと同じ小文字ASCIIの規則。試作の大文字IDは自動改名しない。コードの存在確認は`.space/<project>`・`repositories/<project>`・`workspaces/<project>`配下に限る。古いルート相対code_refsは属性として保持できるが、選択領域外であればdrift検証時にエラーとなり、探索を開始しない。プロジェクト自体の登録はWorkspaceの責務であり、Memoryはその登録情報を読まず独立して初期化できる。通常操作は未知・未初期化のMemoryを作らない。

## 保存と復旧

既存のファイル検証、O_NOFOLLOWによる読取、UTF-8・サイズ検査、inodeと更新時刻の照合、書き込み排他を利用する。書き込み前に全変更先のbeforeと現在値を照合する。ロックはMemory内の`.okf-write-lock`で、pid・token・開始時刻を記録し、所有権が変わったものを削除しない。

変更予定はschemaVersion・project・changesを持つ`.memory-pending.json`に先に保存する。各変更は相対パス・before・after。新規はbeforeなし、削除はafterがnull。予定ファイルを同期して公開後、各ファイルを一時ファイルから置換・削除し、親ディレクトリを同期する。全変更が終わってから予定を削除する。更新予定は64 MiB、個別本文は16 MiBまで。メモリ内の計画・復旧用読取もこの上限で制限する。

複数ファイル全体の原子的な切替ではない。途中の失敗はwritten_pathsとともに返し、通常の操作は残った予定を検出してRECOVERY_REQUIREDで止まる。recoverはすべての対象がbeforeかafterのどちらかであることを確認してから、まだbeforeのものだけを書き込む。内容が違えば一件も追加書込みせずRECOVERY_CONFLICT。元のログ内容と時刻を保持するため、削除自体が済みログだけ未保存の場合も完了できる。dry-runはロックやファイルを作らない。

プロセスが強制終了されて残ったロックは自動削除しない。停止と排他の確保を人間が確認して整理し、その後recoverを実行する。OSによる隔離を置き換える仕組みではなく、ロックを無視する外部の編集者への完全な排他や悪意ある同一ユーザーのOS操作の防御は保証しない。全プロジェクトを同時に読むスナップショット機能は持たない。

showは内容のSHA-256を返し、update・relate・deleteのifHashはロック内で読み直した対象と照合する。古い内容を基にした上書きを防ぐため、スキルはこの指定を使う。成功済みの削除の再送はnot foundとなる。Tasksのような操作ID台帳を導入する必要はなく、未完了の複数ファイル更新は復旧予定で再開する。

## 入出力

CLI引数に加え、単独の`--input-json`でJSONオブジェクトまたは標準入力を受ける。commandは文字列配列で、利用者向けREADMEに各フィールドの型を明記する。未知フィールド、誤った型、重複フラグ、コマンドに適用できないフラグはエラーにする。入力は16 MiBまで。

JSONは`{ok,data}`を基本とし、異常は`{ok:false,error:{code,message,details}}`。検証失敗には検証結果dataを返す。終了コード0は成功、1は入力・書込・検証の失敗、2は読取の失敗。部分書込、ハッシュ競合、中断予定、復旧競合を区別して扱える。スキルは形式検証と内容の正しさ、Memory保存とTasks完了・Git保存を分けて報告する。

## 検証

取り込み直後の試作由来テストは217件・687 assertionsが成功した。その後、kotoのJSON契約・プロジェクト規則・復旧の挙動へ既存テストを適合し、JSON入力、古いハッシュ、削除後のログ復旧、復旧前の全対象検査、初期化中断、コード参照のプロジェクト境界、復旧予定の形式とパスを追加検証した。

Memory単体では224件・785 assertionsが成功した。元の試作には実I/Oエラー、FIFO、シンボリックリンク、同時書き込み、強制終了した書き手のロック保持、変更前後の内容と更新時刻の比較が含まれる。これらを維持し、復旧対象については予定を保持して再開する期待値へ変更した。

統合後のローカル検証は全261件・1627 assertions、型検査、生成物の全ファイル照合、git diff --checkが成功した。両製品の配布物は134ファイル。生成対象から開発資料・テスト・node_modulesを除外し、バンドルした版数をCLIが返すことを確認した。

開発用ソースと他のCLIを取り除いた一時ディレクトリでも、両製品のMemoryで初期化・保存・検索・参照・ハッシュ付き更新・検証・削除が成功した。三つのCLIを組み合わせたテストでは、Memoryの操作がTasksとWorkspaceの状態を変えず、Tasks操作とWorktree削除が知識を変えないことを確認した。Worktree削除後、残したcode_refsはdrift検証で不存在として報告された。

Codex 0.164.0のapp-serverによるplugin/readでは、配布物のkoto:memory・koto:tasks・koto:monorepoをすべてenabledとして認識した。Claude Code 2.1.307のセッション限定plugin-dir読込でもmemory・monorepo・tasksの3スキルを認識した。skill-creatorの形式検証も成功。元の試作19ファイルのSHA-256は読み始めた時点と一致した。

Memoryの実モデルによる自然言語操作、デスクトップ画面の操作、導入済みプラグインの更新は今回行っていない。ローカルの実行環境はBun 1.4.4。GitHub CIのBun 1.4.2での結果は別途記録する。
