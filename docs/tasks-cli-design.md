# Tasks CLIの初版

2026-10-31。ユーザーの指示により、Tasksもkoto内で開発する。`develop`から`codex/tasks-cli`を作り、検証後にコミット履歴を保持するマージで`develop`へ統合する。Memoryは今回実装しない。

## 目的と範囲

`@koto/tasks`、実行名`koto-tasks`をBunで動く独立CLIとして作る。正本は`cli/tasks/`、AI向けの利用手順は`skills/tasks/`。Codex・Claude Codeの両配布物へ同梱する。

初版は次の操作を提供する。

| 操作 | 内容 |
| --- | --- |
| setup | 指定プロジェクトのTasks管理領域を明示的に初期化する |
| task add/list/show/update | 安定したID、題名、説明、状態、版を管理する |
| task start/set/complete/reopen | 着手、待ち・中断・中止、結果を伴う完了、理由を伴う再開 |
| dependency add/remove | 同一プロジェクト内の依存を管理し、循環や存在しない対象を拒否する |
| workspace link | 同じtask_idと指定repository_id群を持つ作業場所への参照を記録する |
| artifact add/list | 成果物の参照と説明、記録した試行を保持する |
| checkpoint save/list/show | 状態のスナップショット、要約、次の操作を保存・参照する |
| history/status/doctor | 操作履歴、集計、データとチェックポイント出力の整合性を確認する |

JSON入出力と非対話実行に対応する。タスク削除、エージェント起動、通知、レビュー承認、工程の強制、Memory操作、Git操作は含めない。旧orchを丸ごと復元しない。

## 旧orchから引き継ぐ考え方

Gitの`77b4d4f`にある旧orchのmodel・store・CLIと、[設計記録](skills/devlow/orchestrator-cli-design.md)を確認した。操作IDによる再送、版の照合、排他と一時ファイルからの置換、依存先の版の固定、過去の結果を残す考え方を引き継ぐ。担当セッションの権限モデル、提出と受け入れ、通知台帳等は初版へ持ち込まない。

操作主体の`actor`は履歴用の自己申告であり、認証・アクセス認可には使わない。ユーザーは「ゼロトラスト」を訂正しており、要求は依存を必要以上に増やさないことである。

## 依存の判断

引数処理は`node:util`、保存はBunが提供する標準のファイルAPIで実装する。既存の小規模なJSON CLIと同じ方法で実現できるため、初版に外部実行時ライブラリを追加しない。Tasksはmonorepoのコードや管理ファイルを読み書きせず、共通Coreも作らない。

これは外部依存を一律に禁止する判断ではない。独自の汎用バリデーター、データベース、スケジューラー等を作る必要が出る場合は、既存パッケージ・組み込み機能と実装難易度を比較し、判断が難しいものはユーザーへ相談する。

## 保存と境界

- 管理ルートは`--root`、プロジェクトは`--project`で選ぶ。省略時は現在のフォルダと`default`。setup以外は未初期化の対象を作らず、他プロジェクトへ切り替えない。
- 正本は`.space/<project>/tasks/state.json`。タスク・操作IDと応答・成果物・チェックポイントのスナップショットを一つのJSONへ保存する。
- チェックポイントは`.space/<project>/checkpoint/<task>/<checkpoint>.json`にも出力する。このファイルは正本内のスナップショットから再生成できる。本文や履歴の唯一の保存先にはしない。
- チェックポイント出力だけ失敗した場合は、保存済みであることと再送方法をエラーで返す。同じ操作の再送で正本を増やさず出力を完了する。異なる既存ファイルは上書きしない。
- プロジェクト単位のロック、一時ファイルの同期と置換を使う。生きているロックの強制取得や、未知の形式の暗黙修復はしない。
- 管理パスのシンボリックリンクと領域外のIDを拒否する。成果物参照は同じプロジェクトの管理領域・作業場所、またはHTTP(S) URLとする。登録はファイルやURLの取得・内容の検証ではない。

## 更新と依存

setup以外の更新には操作IDを指定する。同じIDと同じ入力は以前の応答を返し、異なる入力は拒否する。既存タスクの更新には現在のversionを要求し、古い読み取りに基づく上書きを防ぐ。チェックポイント保存はタスク自体の版を進めない。

状態はpending・running・waiting・paused・completed・cancelled。start時に依存先の有効な完了とその版を確認・固定する。再開・完了時にも照合し、依存先のやり直しがあれば再確認を求める。推移的な依存の失効も表示し、以前のcompletedを有効な完了として後続へ渡さない。

completeはrunningから実行し、結果の説明を必須にする。reopenは理由を記録し、新しい試行のpendingへ戻す。過去の結果と成果物は履歴に保持する。依存関係の変更はpendingでだけ受け付ける。

## 検証計画

CLIを子プロセスで実行し、初期化・プロジェクト分離、状態遷移、依存の循環と版の失効、古い更新と再送、並行更新、成果物とチェックポイント、パス・形式の拒否を検証する。保存の異常終了を想定し、一時ファイルの置換前の失敗とチェックポイント出力の再開を確認する。

配布物は開発リポジトリ外でも直接動かす。monorepoとTasksを同じ管理ルートに用意し、同じIDを介した作業場所の参照と、他ツールのデータを変更しないことを検証する。型検査・配布照合・既存テスト・GitHub CIを実施する。

## 実装と検証

2026-10-31、macOS、Bun 1.4.4、Git 2.50.1（Apple Git-155）で上記の範囲を実装した。外部実行時ライブラリは追加しておらず、既存の開発依存とロックファイルも変更していない。

- Tasks専用9テストと配布検証2テストを追加。既存のmonorepoを含む全36テスト・754 assertionsが成功した。型検査も成功した。
- 初期化・再実行・プロジェクト分離、状態遷移と過去の結果の保持、依存の循環、先行タスクの再開による推移的な完了の失効、成果物参照の境界を確認した。
- 4つのCLIプロセスから同じversionを更新し、成功するのが1件だけであることを確認した。同じ操作の再送、古いversion・異なる入力の拒否、プロジェクトごとのロックの独立性も確認した。
- 正本の置換直前の失敗、チェックポイント出力だけの失敗を注入した。前者では以前の正本を保持し、後者では保存済みのスナップショットから再送で出力を完了した。異なる既存出力は上書きしなかった。
- 開発リポジトリ外の両製品の配布物から、monorepo CLI・ソース・依存インストールなしでTasksを直接実行した。
- 実Gitを使う両製品の連携試験で、タスク作成、Worktree作成、作業場所の参照、着手、成果物・チェックポイントの登録、完了、Worktreeの片付けまで確認した。互いの操作で相手の台帳を変更せず、片付け後もTasksとチェックポイントの記録が保持された。
- 配布対象は100ファイル。Tasksスキルの形式検査も成功した。検証用データは一時フォルダに置き、試験後に削除した。
- Codexのapp-serverのplugin/readで、ローカル配布物のkoto:tasksがenabled=trueで認識された。Claude Codeのセッション限定plugin detailsでもmonorepo・tasksの2スキルを認識した。導入済みキャッシュやユーザー設定は変更していない。

この試験はCLIの操作と配布物の実行を確認する。Codex・Claude Codeモデルへの自然言語依頼、デスクトップ画面の操作、長期間の大容量運用、ネットワーク共有上の保存、OSの強制終了や電源断の耐久性は確認していない。旧orchの通知・承認・担当セッション管理を再実装したものではない。
