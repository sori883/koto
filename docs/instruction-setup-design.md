# 利用先の指示ファイルを追加・更新する

## 依頼と実装範囲

2026-11-01、旧setupのAGENTS.md・CLAUDE.md追加更新機能を現在のkotoに合わせて引き継ぐ依頼を受けた。既存の「setupはmonorepoに含める」という方針に従い、`koto-monorepo instructions plan|apply|status`を追加する。作業ブランチは`codex/instruction-setup`。検証後は履歴を残してdevelopへ統合する。

対象は指示ファイルの管理部分と、その更新を保護する記録。旧setupのスキルコピー、共通知識の配置、専用エージェント、Copilot対応は含めない。利用先への実適用は対象指定を伴う操作とし、開発リポジトリ自身のAGENTS.mdやMacの導入済みプラグインをこの開発で書き換えない。

再利用の基準は[旧setupの更新処理](https://github.com/sori883/koto/blob/77b4d4f87a4c575ccb4b243f2a62acd17cd446a2/skills/setup/scripts/lib/setup.ts)。管理マーカーと旧記録のハッシュ互換性を維持し、現在のmonorepoの排他・保存関数に接続した。旧配布マニフェストや他のCLIの内部実装は取り込んでいない。

## 入力と配置

- `--root`・`--project`はmonorepoの既存管理ルート・登録プロジェクトを選ぶ。
- `--target`に指示ファイルを置く既存ディレクトリの絶対パス、`--product`にcodexまたはclaude-codeを必須指定する。
- 配布元はCLIの配置から求める。`--source`で別のkotoソース／配布ルートを明示できる。必要なスキル・CLI・テンプレートがない場合は停止する。
- 指示テンプレートの正本は既存の`templates/AGENTS.md`を更新して使い、両製品へ同梱する。製品ごとの配置先はAGENTS.md／CLAUDE.md。リンク先は使用した配布元の実在する絶対パスとする。
- 更新記録は管理ルートの`.space/<project>/instructions/<対象パスのSHA-256>/<product>.json`。同じ場所に途中の書き込み予定を保存する。

対象が管理ルート内の別プロジェクトのworkspaces配下なら拒否する。`.space`・`repositories`内へは配置しない。ルート以外の共通祖先へプロジェクト固有の指示を置かない。外部の既存リポジトリも明示したtargetとして扱える。同一ファイルを別root/projectから無断で引き継がない。

## 更新と保護

旧setupの管理マーカー、UTF-8検証、管理部分のハッシュ比較を引き継ぐ。管理部分以外のバイト列を保持する。既存管理部分の独自編集・削除・マーカー破損は衝突とし、上書きしない。改行形式と既存ファイルのrwx権限を保つ。

旧kotoのブロックは、利用先の`.space/setup/koto-<product>.json`にある該当ファイルのハッシュと一致する場合に移行できる。旧記録と他の配置物は残す。旧setupの未完了操作やロックがある場合は止める。証拠のない既存ブロックを自動採用しない。

plan/statusは読み取り専用。applyは管理ルートと対象ディレクトリで排他し、最新内容を再確認する。指示ファイルと更新記録は一括で原子的に変更できないため、予定を先に保存し、指示ファイル、管理記録の順に置換して予定を削除する。再実行では適用前後のハッシュを照合し、想定外の編集を保護する。生きたロックの削除や強制上書きは提供しない。

## 指示の内容

対象root/projectを明記し、コード変更前のTasks登録・既存タスク再利用を要求する。devlowがフロー、recallが現在地の復元、各CLIスキルが操作手順を担う。一行の変更や調査途中からのコード変更も対象とし、コードを変更しない調査・相談・設計などは自動でタスク化しない。長期化や報告書の保存だけを登録理由にしない。必要なタスクを記録できない場合はコードを編集せず、原因と進められる調査範囲を説明する。

コード変更ではTasksとPR／MRを相互参照する。原則は必要な検証と全PR／MRのマージ確認後に完了とする。ユーザーの明示的な完了指定も受け付け、その指示と実際のマージ・検証状態、未実施事項を残す。それ以外のレビュー・マージ待ちはwaitingへ記録する。引き渡し範囲とタスクの完了、操作の承認の区別はdevlowの手順へ委ねる。

指示ファイルはAIへの入口であり、編集を機械的に禁止する機能ではない。管理ルートへ置いたプロジェクト固有の設定を別プロジェクトの仕事に流用しない。既存の指示、入れ子の指示、実行環境側の権限との関係は利用先で確認する。

## 検証方針

CLIの実プロセスで初回配置、冪等性、配布元更新、ブロック外の編集保持、管理部分の編集・削除・不正マーカー拒否、旧setup移行、途中失敗後の再実行、排他、パス境界を確認する。Codex・Claude Codeの両配布物だけを一時フォルダへ持ち出して同じ操作を確認する。型検査、全テスト、配布物照合、GitHub CIを通す。

## 検証結果

- 指示更新専用の12テストで、初回配置と冪等性、CRLFとrwx権限、更新時のローカル文章保持、管理部分の編集・削除・不正UTF-8とマーカー、旧setupの一致・不一致・未完了操作・ロックを確認した。
- 既存ファイルと管理記録の置換を別々に失敗させ、保存予定からの再実行と、途中に別の編集が入った場合の拒否を確認した。故障の注入は隔離したテスト子プロセス内で行い、製品へ検証用の分岐や環境変数を追加していない。
- プロジェクトの選択、別projectから同じ外部対象への更新拒否、別projectへの別名経由のアクセス拒否、シンボリックリンク、未知の管理形式と不整合、JSON入力を確認した。
- 配布テストでは、両製品の配布物を生成後に元ソースを取り除き、plan・apply・status・再適用を実行した。生成された5つのスキル参照が配布先の実ファイルを指し、開発リポジトリへ依存しないことを確認した。
- 型検査、配布生成・照合、monorepoスキルの形式検査、開発文書の参照先確認が成功した。配布物は192ファイル。

今回の実行確認はCLIとファイルの実結果が対象であり、Codex・Claude Codeのモデルが生成指示を必ず選択・遵守することの保証ではない。指示の自動読込は起動位置や利用先の他の指示にも影響される。koto自身のAGENTS.md、ユーザー設定、導入済みプラグインは変更していない。
